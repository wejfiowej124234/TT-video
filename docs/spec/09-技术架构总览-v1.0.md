# 1. 项目技术定位

TravelTrust 是一个：

- 基于 EVM 的去中心化托管协议（Escrow）
- Rust 驱动的企业级后端
- 分布式数据库（CockroachDB）支撑的全球可扩展系统
- Web3 DApp + 3D 展示型前端

核心原则：

> **链为资金真相**  
> **DB 为业务检索与可重建投影**  
> **所有链状态必须可回放**  
> **所有资金终态必须可审计**

## 2.8 Rust 后端方案（匹配 Web3 DApp + 3D 前端）

后端与前端/DApp 对齐的子系统与技术栈；职责与 01/02/04 一致。

| 子系统 | 职责（和前端对齐） | Rust 技术栈 | 关键数据/产物 |
|--------|--------------------|-------------|----------------|
| API Gateway | 向前端提供业务 API：订单、导游、争议、证据、状态 | Axum + tower | OpenAPI、x-request-id、审计日志 |
| Auth & RBAC | 邮箱登录、JWT；角色：游客/导游/仲裁员/运营/执行器 | axum + jwt + rbac middleware | rbac_snapshot_hash、权限审计 |
| DB 层 | 业务真相：行程、证据、评价、用户、导游、工单 | Postgres + SQLx | 迁移、索引、审计表 |
| 缓存/幂等 | 幂等键、限流、session、热点数据 | Redis | 幂等键表、限流策略 |
| Queue/Jobs | 异步：索引、对账、重试、通知、病毒扫描 | NATS / Redis Streams / RabbitMQ | messageId、重试、DLQ |
| EIP-712 验签服务 | 验签前端 typed data：Created、Accepted、证据哈希 | alloy + ethers-core（可选） | signed_action 表、signature_audit |
| Indexer（事件索引器） | 读链上事件 EscrowCreated/Paid/DisputeOpened/ResolutionExecuted；finality 12 块、reorg 回退 | alloy + 自研 consumer | event_log、checkpoint(block, logIndex) |
| Projection（投影器） | 链事件 → 业务状态（Paid/Released/Refunded/Slashed）；链为准 | Rust job + SQL | orders.chain_state、重建日志 |
| Reconciler（对账器） | 三段式对账（自动/半自动/人工）；链为准 | Rust job + SQL | reconciliation_report、correction_log |
| Executor（执行器） | 上链 executeResolution；白名单、限额、双人审批、幂等 | alloy + RBAC + policy | approvals、resolutionId、executed[] |
| Evidence Pack（证据包） | 可审计证据包、manifest + SHA256 | Rust + sha2 | evidence-pack/manifest.json |

# 3. 分布式数据库设计（CockroachDB）

## 3.1 设计原则

- 强一致事务
- 避免单行热点
- Append-only 优先
- 投影可重建
- 纠偏只追加不覆盖

## 3.2 核心表分组

### 业务真相（DB 为准）

- users
- guides
- orders
- disputes
- evidence_objects
- audit_log

### 链事件真相（链为准）

- event_log（append-only）
- checkpoints_sharded（分片 checkpoint）
- escrow_mapping

### 投影与对账

- orders_projection（可重建）
- reconciliation_reports
- correction_log

### 执行器

- executor_approvals
- executor_executions
- executed_resolutions

### 幂等与风控

- idempotency_keys
- risk_flags

## 3.3 分布式热点规避

- 不使用自增主键
- 主键采用 (chain_id, order_id)
- checkpoint 分片设计
- 投影 UPSERT 幂等
- 大文件存对象存储

# 4. 数据流闭环

## 4.1 支付流程

用户点击支付 → wagmi 写链 deposit → Polygon 打包 → 12 confirmations → Indexer 写 event_log → Projector 更新 orders_projection → API 返回最新状态 → 前端刷新。

**资金状态永远来源于链事件。**

## 4.2 争议执行流程

仲裁员裁决 → 后端审批 → Executor 发 executeResolution → 链上事件 → Indexer → Projection → 状态更新。

`resolutionId = keccak256(chainId, orderId, resolutionSeq, decisionHash)`

---

# 5. Finality 与 Reorg 策略

- **finalityN = 12**
- event_log 记录 blockHash + logIndex
- 检测 txHash 不同 blockHash → 触发 reorg
- 回退安全高度 → 重放事件 → 投影重建
- 副作用幂等

详见 [01 §5](01-总库总览.md)、[02 §七](02-架构设计.md)、[08-1 C1](08-1-战略与合规风险检查清单.md#c1-reorg-与-finality)。

---

# 6. 对账机制（三段式）

1. 自动修复（小额差异）
2. 半自动修复（人工确认）
3. 人工冻结 + 工单

**链为准，DB 不可直接改资金状态。** 见 [01 §9](01-总库总览.md)、[04](04-后端与API.md)。

---

# 7. 执行器安全模型

- 双人审批
- 单笔/单日限额
- resolutionId 幂等
- executeResolution 原子执行
- pause 白名单
- 所有执行记录 append-only

见 [01 §7](01-总库总览.md)、[08-4 第 2 章](08-4-对外口径包.md)、[Runbook §7](../ops/RUNBOOK.md)。
