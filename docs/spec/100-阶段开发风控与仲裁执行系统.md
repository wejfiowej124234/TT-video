## 一、文档定位

本文定义 TravelTrust 在 100 阶段的“风控与仲裁执行系统”开发规范。

本系统是订单与托管资金安全的执行中枢，不是单一“风控页面”或“仲裁页面”。

它直接承接并执行以下业务硬约束：

- 订单存在改行程、取消、超时、争议、双方确认等复杂状态变化。
- 向导存在锁档期约束，必须防止乱接单与并发冲突接单。
- 平台必须对高风险行为进行命中、拦截、处置、审计闭环。
- 仲裁结论必须可验证并可回写链上执行，不能停留在链下口头结论。

- 业务与风控：`docs/spec/03-业务流程与风控.md`

## 二、系统目标

100 阶段目标是形成“可执行、可回放、可审计”的风控与仲裁闭环：

1. 风险可识别：把订单、账户、设备、行为的异常信号标准化。
2. 规则可执行：风险规则命中后自动触发对应处置，而不是人工补救。
3. 工单可追踪：争议工单全生命周期可跟踪、可复核、可审计。
4. 证据可固化：关键证据不可篡改、可验证、可回放。
5. 裁决可落链：仲裁结果有明确回写链上路径，形成资金终态。

## 三、范围定义（五大执行模块）

### 3.1 风控规则引擎

核心能力：

- 规则分层：准入规则、交易规则、争议规则、结算规则。
- 规则版本化：每次规则变更必须有版本号与生效时间。
- 风险评分与标签融合：规则命中和风险分共同决策。
- 规则执行模式：阻断、降级、人工复核、放行带审计。

最小规则集（P0）：

- 超时规则：接单超时、支付超时、完成超时。
- 取消规则：短时高频取消、异常取消率。
- 档期规则：向导锁档期时禁止接新单。
- 争议规则：高频争议账户升级审查。
- 评价规则：防刷评、防互刷、防异常突增。

验收要求：

- 每次命中必须产生 `risk_hit_id`、规则版本、命中证据。
- 每次处置必须有 `action`、执行结果、执行人或系统身份。

### 3.2 风险命中与处置系统

核心能力：

- 命中分级：low/medium/high/critical。
- 处置编排：按风险等级映射处置动作。
- 自动化与人工联动：自动处置后可升级人工复核。
- SLA 机制：高风险工单必须在设定时限内处理。

处置动作库（最小）：

- 限制下单
- 限制接单
- 限制改行程
- 强制二次验证
- 强制仲裁前置
- 临时冻结交易能力

验收要求：

- 命中到处置链路可追踪（一条 trace）。
- 处置结果可回放且能关联到订单/用户/向导主体。

### 3.3 争议工单系统

核心能力：

- 工单生命周期：open -> triage -> evidence_collecting -> hearing -> resolved -> executed。
- 工单角色分工：客服初筛、风控复核、仲裁裁决、审计复盘。
- 双方陈述窗口与超时策略。
- 工单与订单状态机严格联动。

硬约束：

- 一个有效争议工单对应一个订单主争议流。
- 争议中订单不得绕过仲裁进入资金终态。
- 工单关闭必须有裁决理由与证据索引。

验收要求：

- 工单可导出完整时间线（谁、何时、做了什么、依据什么）。
- 工单状态跳转仅允许白名单迁移。

### 3.4 证据固化与可验证链

核心能力：

- 证据入库前标准化：类型、来源、时间戳、哈希。
- 证据不可变标识：`evidence_hash`、`receipt_id`。
- 证据完整性验证：校验哈希与签名。
- 证据访问控制：按角色最小权限访问。

证据来源：

- 聊天记录与关键消息
- 行程版本快照
- 操作日志与风控命中日志
- 上传文件（图片/文档/录音）
- 链上事件与交易回执

验收要求：

- 关键证据必须可在争议仲裁时快速检索。
- 任一证据变更都必须触发审计告警（理论上应无变更）。

### 3.5 仲裁结果回写链上执行

核心能力：

- 仲裁结果结构化：`resolution_type`、`refund_ratio`、`slash_guide`、`resolution_id`。
- 回写执行队列：确保幂等、可重试、可告警。
- 执行结果落库：tx_hash、block_number、log_index、finality_n_used。
- 执行失败处理：重试、死信、人工介入。

硬约束：

- 仲裁结论不是终点，链上执行成功才是资金终态依据。
- 同一 `resolution_id` 只能成功执行一次。

验收要求：

- 仲裁结论到链上交易可一键追踪。
- 任何失败场景都有可操作恢复路径。

## 四、业务硬约束落地（与文档串联一致）

以下四项是强制执行约束，直接来自文档体系硬规则：

1. 超时：必须有自动触发与状态推进，不允许长期悬挂单。
2. 取消/退款：必须走规则校验与资金路径校验，禁止越权退款。
3. 争议人工裁决：争议终局由人工裁决结论驱动执行，不可跳过。
4. 评分公平：评分必须受防刷规则约束，禁止短期操纵信誉系统。

补充约束：

- 向导锁档期期间不得接新单，必须由规则引擎强制拦截。
- 改行程必须受订单状态、双方确认状态与风控状态共同约束。

建议新增或扩展：

- `evidence_items`
- `evidence_receipts`

字段级硬要求：

- 执行链路必须含 `x_request_id`、`trace_id`。

## 六、API 与权限建议

最小接口面：

- Risk Engine API：规则管理、规则试运行、命中查询。
- Risk Action API：处置执行、处置回滚、处置审批。
- Dispute API：工单创建、状态流转、仲裁结论提交。
- Evidence API：证据上传、校验、回执、索引查询。
- Resolution API：结论出队、链上执行、执行状态查询。

概念 API 与权威路由映射（对齐 `04 §3.4`、`14`）：

| 概念 API | 当前路由锚点（已登记） | 能力现状（非阶段验收状态） |
|---|---|---|
| Risk Engine API | `GET /api/v1/admin/policies`、`POST /api/v1/admin/policies/:id/publish` | Target |
| Risk Action API | `POST /api/v1/admin/approvals/:id/approve`、`POST /api/v1/internal/process-resolution-outbox` | Partial（审批基线已落地，风险动作编排待补） |
| Dispute API | `GET /api/v1/disputes`、`GET /api/v1/disputes/:id`、`POST /api/v1/orders/:id/dispute`、`POST /api/v1/disputes/:id/resolve` | Implemented（最小争议闭环） |
| Evidence API | `GET/POST /api/v1/orders/:id/evidence` | Implemented（最小证据链路） |
| Resolution API | `POST /api/v1/disputes/:id/execute-resolution-intent`、`POST /api/v1/internal/process-resolution-outbox` | Partial（执行出队基线有，完整执行流水线待补） |
| Admin Observability API | `GET /api/v1/admin/indexer/reconcile-report/:id`、`GET /api/v1/admin/observability/overview`、`GET /api/v1/admin/audit/operations` | Partial（已最小可读，完整导出与关联报表待补） |

口径说明：本节用于能力分层与审计映射，表中 `Target/Partial/Implemented` 仅表示能力落地进度，不等同于本阶段整体验收结论；具体发布判定以 `04 §3.4` 状态列与实现证据为准。

RBAC 原则：

- CS：可创建/查看工单，不可提交仲裁终局。
- Risk：可执行风险处置，不可直接改资金终态。
- Arbiter：可提交仲裁结论，不可修改原始证据。
- Ops：可监控执行队列，不可越权裁决。
- Auditor：全链路只读导出。

## 七、阶段实施计划（100 阶段）

### 7.1 P0（必须）

- 风控规则引擎最小可用版本（超时/取消/档期/争议/评分）。
- 风险命中与处置流水打通。
- 争议工单全生命周期状态机落地。
- 证据哈希固化与回执机制落地。
- 仲裁结果到链上执行最小闭环。

### 7.2 P1（增强）

- 规则灰度发布与回滚。
- 风险处置审批流（高风险动作双人复核）。
- 争议听证模板与标准化裁决书。
- 执行队列告警与自动重试策略优化。

### 7.3 P2（规模化）

- 规则策略可视化编排。
- 风险与信誉联合模型。
- 跨区域争议规则差异化治理。
- 仲裁与执行全链路 KPI 看板。

## 八、发布门禁（分层：P0 必须全过）

### 8.1 P0（最小可发布门禁，必须全过）

1. 五大模块均可独立演示并串成一条完整交易风控链。
2. 至少演示 3 个真实场景：超时、取消退款、争议裁决上链。
3. 向导锁档期拦截在接口与前端均可验证。
4. 证据可验证、可追溯、不可篡改。
5. 仲裁结果执行链路具备幂等与失败恢复机制。
6. 全部关键动作具备审计日志与证据指针。

### 8.2 P1/P2（增强门禁，按阶段收口）

1. 索引/对账联动核查在 `110` 与 `120` 的 `P0` 门禁完成后，升级为强制门禁。
2. 风控看板、跨区域规则差异化治理和联动告警闭环完成后，进入规模化门禁。

### 8.3 门禁执行锚点（仓库现有入口）

| 门禁类别 | 执行入口 | 证据落点 |
|---|---|---|
| 风控与不变量快速核查 | `scripts/check-invariants.sh` | `evidence/GO_YYYYMMDD/` |
| 争议与执行链路核查 | `POST /api/v1/disputes/:id/resolve` + `POST /api/v1/internal/process-resolution-outbox`（内网） | 审计日志 + `evidence/GO_YYYYMMDD/` |
| 索引/对账联动核查（跨阶段增强） | `POST /api/v1/internal/indexer-reconcile`、`GET /api/v1/admin/indexer/reconcile-report/:id` | `evidence/GO_YYYYMMDD/` |

执行说明：若 CI 中存在同名或等效 Job，以 CI 结果作为发布门禁主证据；本地脚本用于复核与复现。跨阶段锚点在依赖阶段未达成前仅作增强辅证，不作为 P0 单独放行条件。若任一 P0 门禁证据缺失，按 fail-closed 处理，不进入发布候选。

## 九、与现有阶段文档的衔接
