## 0. 核心原则（继承现有架构）

基于现有系统共识：

- **链为资金真相，DB 为业务投影。**
- 本角色体系必须满足：
  - **不**改变订单 / 托管 / 争议的**状态机语义**；
  - **不**改变链上资金路径（Escrow 主路径）；
  - **只**作用于：**权限**、**业务入口**、**收益分配叙事与治理绑定**。

若实现与本文冲突，**以 01 / 03 / 53 / 04 / 14 已定稿条为准**，并应回溯修订本文或走 **[07 §二 2.4](07-开发流程与顺序.md)** 变更说明。

### 1.4 产品扩展：旅行收购（跨境捎带诉求榜 · Target）

**业务叙事（产品）**：一方在平台发布 **收购任务**（目标地区/国家、品类、预算或单价区间、交割约定等），另一方（多为即将 **入境该地区** 的 **旅行者**）浏览是否可 **顺路捎带** 并完成交割，以获取约定对价。典型场景包括境内用户发布「从美国捎带某类商品入境」等；**药品、贵金属、禁限品** 等须以 **强制披露 + 风险提示** 呈现，**不构成**对任何跨境行为的合规背书（与 **03** 风控、法务定稿同路径）。

**与协议四类角色的关系（技术约束）**：

- **不**在本文件新增 **`users.role` 枚举值**；**Traveler / Guide / Shop / Region Steward** 四类 **SSOT 不变**（**§1.1～§1.2**）。
- **旅行收购** 作为 **独立产品能力**（任务发布、浏览、接单、履约与榜单），与 **DID 排行榜** 第四脊签 **「旅行收购」** 对齐（**[30 §3.2](30-DID排行榜-页面规范.md)**）；链下数据模型、RBAC 与 **多重身份 / 附加能力开关** 须在 **04 / 90** 明确后出现（与 **§10.3** 一致），**禁止**仅凭本文宣称已落库。

**多重身份与申请（产品 + 工程口径）**：

- 同一账户可在 **主角色**（四类之一）之外，**申请开通**：**旅行收购任务发布**（委托方）、**旅行收购履约 / 接单**（受托方，通常与 **旅行者** 动线叠加以免重复注册）等 **附加能力**；准入、风控与展示以 **头像菜单 / 账户中心「身份与能力」** 统一入口（实现期与 **90**、**13-1** 同批）。
- 上述能力 **不改变** Escrow 主订单状态机 **§3.1** 的既有参与方定义；若未来将收购履约 **并入** 托管单，须走 **53 / 14 / 07 §二 2.4** 专批，**不**默认扩展本文订单表。

**Backlog 互证（文档对齐 / 非实现封口）**：[任务母表 B-463](../任务母表.md) · [TT-DOC-B463-TRAVEL-ACQUISITION-SPEC-ALIGN-001](../AI任务卡索引.md#tt-doc-b463-travel-acquisition-spec-align-001)（**87 / 30 / 04 附录** 三处 **对齐** 与 **药品·禁限品·海关** 口径 **同步** 的台账条目）。

|------|----------------------|

## 5. Region Steward（核心升级点）

### 5.1 在系统中的位置

- **订单系统（Escrow）**：**不参与**（不持有订单内「操作者」语义）。
- **收益系统（FeeRouter）**：**参与**（路由与区域分配叙事）。
- **DAO / 治理**：**参与**（参数与权限边界见 **83** / **governance-token**）。

### 5.2 绑定逻辑（示例）

```solidity
mapping(bytes32 => address) public regionSteward;
```

实现形态以 **contracts/** 与 **14** 为准；上表为**语义 SSOT**。

### 5.3 收益路径（叙事）

**订单支付 → 平台费 → FeeRouter → Region Steward（按区域规则）**

**注意：** 不改变 Escrow 合约内 **用户资金安全** 的主路径语义；FeeRouter 为 **费用拆分与治理分配** 层（与 **83 §3**、**Runbook §7.1** 对齐）。

## 10. 不变量（写死）

### 10.1 资金不变量

**Escrow 托管资金的操作主体**在订单主链上限于：**Traveler**、**Guide**（按状态机允许的动作）。

### 10.2 治理隔离

**Region Steward** **不得**被文档或产品表述为「可直接操作用户订单托管余额」；其权力在 **FeeRouter / 治理参数** 边界内。

**治理权限与计票真值**见 **[governance-token/02 §4.5](governance-token/02-对内技术规格-草案.md)**：**产品角色**（含 **[89 §5](89-治理UI-全球旅游市场治理控制台设计规格.md)** 视角下的旅行者/向导/服务商/**地区代理商** 等）**仅**影响 **UI 信息优先级、准入与业务入口**；**链上 propose / 计票** 仍以 **Governor、`getPastVotes`**（及委托规则）为唯一数学来源，**不以身份直接改变投票数学**。

### 10.3 角色唯一性

- 一个账户的 **主角色**（四类之一）在 SSOT 中 **唯一**。
- **子角色 / 扩展**（例如同一人多身份、**§1.4** **旅行收购** 发布/履约等 **附加能力开关**）仅允许在 **04 / 90** 明确建模后出现，**不**在本文件未约定情况下默认。

## 12. 最终结论

协议级角色体系**锁死**为四类：

1. **Traveler（旅行者）**  
2. **Guide（向导）**  
3. **Shop（商铺）** — API/DB 字段 **`provider`**  
4. **Region Steward（区域主理人）** — **非**订单操作者，**是**收益与治理绑定角色  

定位从「旅游平台」叙事升级为 **Web3 旅游协议（Protocol 级）** 时，对外与对内文档应与本篇 **§1.2** 一致，避免 UI 写 Shop、API 写 `merchant` 等漂移。
