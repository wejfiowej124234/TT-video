## 二、系统目标

160 阶段目标是建立“可增长、可治理、可审计”的社区内容闭环：

1. 内容模型统一：帖子、评论、互动、标签、媒体、举报、审核具备统一数据模型。
2. 审核链路闭环：举报提交、审核处置、申诉复核、处罚执行全链路可追踪。
3. 反作弊可执行：反垃圾、反刷评、反机器灌水有规则和阈值，不靠人工兜底。
4. 分发可解释：排序与推荐有策略、可回放、可降级。
5. 风控可联动：内容风险与账户风险、交易风险、运营处罚联动。

## 三、范围定义（六大模块）

### 3.1 社区内容模型

核心能力：

- 统一内容实体：帖子（图文/短视频/攻略）、评论、回复、话题、地点、标签。
- 互动实体：点赞、收藏、转发、关注、屏蔽、拉黑。
- 媒体资产实体：图片、视频、封面、转码状态、内容指纹。
- 治理实体：举报单、审核单、处罚记录、申诉单。

最小要求（P0）：

- 帖子、评论、举报、审核四类核心实体必须具备稳定主键和状态机。
- 社区内容与用户身份（旅行者/向导）和订单场景可关联，但权限边界清晰。

验收要求：

- 内容状态可追溯（草稿/发布/下线/删除/冻结）。
- 评论状态可追溯（可见/折叠/屏蔽/删除）。

### 3.2 举报与审核流

核心能力：

- 举报入口覆盖帖子、评论、私信线索（如适用）。
- 举报分类标准化：诈骗、骚扰、广告、违法违规、恶意引战、仇恨/歧视等。
- 审核台支持自动预审 + 人工复审。
- 处罚动作标准化：警告、限流、下架、删帖、禁言、封禁、升级人工调查。

最小要求（P0）：

- 举报单必须入库并生成唯一工单号。
- 审核结果必须包含判定理由、证据快照、责任人、处理时限。

验收要求：

- 举报到处理完成的 SLA 可统计。
- 支持误判申诉与复核，复核过程有审计日志。

### 3.3 反垃圾与反刷评

核心能力：

- 账号行为风控：新号高频发帖、异常评论速率、短时批量互动检测。
- 文本与媒体风控：关键词命中、重复文本、相似内容簇、媒体指纹复用。
- 关系网络风控：互刷团伙、异常互赞圈、跨账号模板评论。
- 策略执行动作：限流、延迟发布、验证码挑战、人工复核队列。

最小要求（P0）：

- 评论频率阈值、相似度阈值、重复举报阈值写入参数表并可灰度调整。
- 反刷评命中后需有明确动作，不允许仅打日志不处置。

验收要求：

- 误杀率与漏杀率可观测并持续优化。
- 重大活动期间具备临时加严策略与一键回退能力。

### 3.4 排序与推荐

核心能力：

- 多路召回：最新、关注、热门、目的地相关、兴趣相关。
- 排序信号：内容质量、互动质量、时效、作者可信度、违规风险惩罚。
- 去重与多样性：避免单一作者刷屏、避免同质内容霸屏。
- 冷启动策略：新用户/新内容有可控曝光，不被完全淹没。

最小要求（P0）：

- 至少支持 `latest`、`hot`、`following` 三类排序。
- 排序策略版本化，可切换，可回滚，可审计。

验收要求：

- 推荐结果可解释到关键特征维度（不泄露敏感权重细节）。
- 推荐故障时可降级到可用排序（如 `latest`）。

### 3.5 内容风控

核心能力：

- 违规类型库：违法、色情、暴力、欺诈、仇恨、侵犯隐私、诱导交易。
- 风险分层：低风险（提醒）、中风险（折叠/限流）、高风险（下架/封禁）。
- 联动处置：与账户风控、订单风控、仲裁系统联动。
- 证据固化：内容快照、命中规则、模型分数、审核意见可追溯。

最小要求（P0）：

- 高风险命中必须进入优先审核队列。
- 涉及交易诈骗类内容必须联动 100 阶段风控策略。

验收要求：

- 风险处置策略与对外口径一致。
- 内容风控事故可复盘、可问责、可改进。

### 3.6 运营治理与审计

核心能力：

- 运营后台：举报池、审核池、处罚池、申诉池统一看板。
- 指标体系：举报量、处理时长、误判率、复发率、反刷拦截率。
- 审计体系：审核动作、策略变更、权限操作全留痕。
- 发布门禁：策略变更必须带回归测试与灰度计划。

最小要求（P0）：

- 审核与处罚操作必须 RBAC 控制并留存操作者信息。
- 高风险规则调整必须走双人复核。

验收要求：

- 月度治理报告可输出并对齐运营目标。
- 审计抽查可在规定时间内回放任意工单处理链路。

## 四、核心硬约束（必须写死）

1. Moderation First：举报与审核链路不可缺省，社区上线不得绕过治理。
2. Evidence by Default：每一次判定必须有证据快照与规则依据。
3. Anti-Abuse as Gate：反垃圾与反刷评策略失效时不得放量。
4. Ranking with Safe Fallback：推荐故障必须自动降级到安全排序。
5. Risk Linkage Required：内容风险必须与账户/交易风险联动。
6. Policy Changes Are Audited：策略、阈值、处罚规则变更必须可审计、可回滚。

## 七、发布门禁（分层：P0 必须全过）

### 7.1 P0（最小可发布门禁，必须全过）

1. Feed/发帖/评论/点赞/收藏主链路可用，并完成基础回归。
2. 举报/审核/处罚/申诉闭环达到最小可运行：至少具备工单入库、审核决策、处罚落账、申诉复核的可追踪链路。
3. 反馈闭环（`GET|POST /api/v1/community/feedback`）可用，内网官方回复链路可追踪。
4. 排序故障降级（至少 `latest` 兜底）可演练、可复现。
5. 关键操作具备审计留痕与证据指针，发布前抽样可回放。

### 7.1.1 量化门禁基线（P0，必须写入 CI 并按 fail-closed 执行）

- 主链路可用性：`feed/create_post/comment/like/collect` 的集成用例通过率 = 100%。
- 治理闭环可追踪性：举报工单抽样 10 条中，`report -> moderation -> penalty/appeal` 全链路可回放率 = 100%。
- SLA 合规：举报到首次处置 P95 <= 30 分钟；高风险工单进入优先队列延迟 <= 5 分钟。
- 排序降级演练：`latest` 兜底演练成功率 = 100%，且 1 次演练必须附证据。
- 证据完整性：社区治理发布证据（见 §7.4）任一核心字段缺失即阻断发布。

证据文件绑定（最小集合）：
