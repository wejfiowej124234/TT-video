## 一、文档定位与原则

本文定义 TravelTrust 运营后台（Admin Console）的产品与工程落地规范，适用于当前混合架构（旅游业务 + 链上 Escrow）：

- 资金与托管真相（SSOT）：链上合约状态与事件为最终真相。
- 后台检索与运营效率：后端 API/DB 为业务投影与查询加速层。
- 冲突裁决顺序：链上事件/合约状态 > 后端 API 投影 > DB。
- 审计原则：后台所有操作必须可追溯、可复核、可归档。

文档语义约定（避免误读）：

- 本文默认描述的是 **目标态规范**（Target State），不是“全部已上线事实”。
- 当前仓库实际实现状态以本文件 `3.1`、`8.4`、`9.2` 的证据表为准。
- 若与代码冲突，按 `链上/代码事实 > 本文目标描述` 处理，并在迭代中回填文档。

与现有文档体系关系：

- 权威层级与冲突规则：见 **[07-开发流程与顺序.md](07-开发流程与顺序.md) §零、§五**（[00-文档体系与阅读串联.md](00-文档体系与阅读串联.md) 兼容壳）。
- 风控与业务规则：见 `docs/spec/03-业务流程与风控.md`。
- 后端与 API：见 `docs/spec/04-后端与API.md`。
- 数据库与审计域：见 `docs/spec/04-数据库架构与表分类.md`。
- 系统级不变量：见 `docs/spec/10-系统级不变量白皮书-v1.0.md`。

## 一点五、Vault 转出投影专项离线包 · Admin 运维 SOP（P5-2-C3）

**定位**：**只读**、**不**改后端导出实现、**不**触索引器/投影写入；与 **B-115 / B-116 / P5-1 / P5-5** **已封口实现** **正交**。第三方仅凭本文 + **[04 · P5-2-A / P5-2-C2](04-后端与API.md#p5-2-a--vault-专项对账导出规格冻结--epic-p5-2)** + **[Runbook §2.55](../../ops/RUNBOOK.md#255-indexer-tick重放与对账internal--admin-只读)** + **[scripts/README](../../scripts/README.md)** 应能独立完成 **一次** 拉取与归档。

| 步骤 | 执行说明 |
|------|----------|
| **1 · 谁执行** | 须使用具备 **`admin`** 或 **`super_admin`** 的 **Admin Console** 账号（与 **[04 §3.5](04-后端与API.md#35-admin-api对齐-70-收口)** **RBAC** 一致）。**组织上** 通常为 **财务对账 / 内部审计 / 索引器值班（SRE）** 中被授权操作 **Admin 只读导出** 的角色；**禁止**用 **`INTERNAL_API_SECRET`** 或 **无 Admin 角色的 Bearer** 冒充本流程（本 API **仅** **Admin** 闸）。 |
| **2 · 调用哪条已封口 API** | **`GET /api/v1/admin/region-vault/forwarded-events/export`**（**`format`**=`csv` 或 `json`；可选 **`chain_id`**、**`limit`** 1～2000）。契约与响应头 **SHA256 / 可选 Ed25519 / truncated** 见 **[04 §3.5](04-后端与API.md)** 表行及 **P5-2-A**；封口证据 **[GO_P5_2_B_CLOSE](../../evidence/GO_P5_2_B_CLOSE.md)**。 |
| **3 · 用 C1 脚本组包（推荐）** | 项目根执行 **`bash scripts/vault-forwarded-export-fetch.sh`**（Windows：**`.\scripts\vault-forwarded-export-fetch.ps1`**，须 **Git Bash**）。**必填** 环境变量 **`ADMIN_BEARER_TOKEN`**（与浏览器 **Admin** 会话 **Bearer** 同源 **token 串**，**不含** `Bearer ` 前缀；**勿**入库）。可选 **`API_BASE_URL`**（默认 `http://127.0.0.1:8080`）、**`VAULT_EXPORT_FORMAT`**、**`VAULT_EXPORT_CHAIN_ID`**、**`VAULT_EXPORT_LIMIT`**、**`VAULT_EXPORT_OUT_DIR`**。脚本成功时落盘 **体文件**、**`.export.headers.txt`**、**`.export.sha256`**（及条件 **Ed25519/truncated** 侧车），见 **[scripts/README](../../scripts/README.md)** 表行与 **Runbook §2.55**。 |
| **4 · 补全机读 manifest（C2）** | 在包根增加 **`vault-forwarded-offline.manifest.json`**，字段须满足 **[04 · P5-2-C2](04-后端与API.md#p5-2-c2--vault-专项离线包目录与-manifest-机读规范规格冻结)** 最小表；可复制 **[evidence/vault-forwarded-offline-manifest.example.json](../../evidence/vault-forwarded-offline-manifest.example.json)** 后 **替换** 占位 **`body_bytes_sha256_hex`**、**`headers_echo`**、**`fetched_at_rfc3339`**、**`api.query`** 等为 **本次** 真实值，并 **核对** **`response.body_bytes_sha256_hex`** **=** **`headers_echo.x-traveltrust-reconcile-export-sha256`**。 |
| **5 · 校验 SHA256** | **自动化**：C1 脚本退出码 **0** 已校验 **体文件 sha256** **=** **头** **=** **`.export.sha256`**。**人工复核**：对 **体文件** 执行 **`sha256sum`** / **`shasum -a 256`**，与 **`.export.sha256`** 单行 hex **逐字符**一致。 |
| **6 · 可选 Ed25519** | 若 **`.export.headers.txt`** 或 manifest 中 **`x-traveltrust-reconcile-export-ed25519`** **存在**：用 **`bash scripts/verify-reconcile-export-ed25519.sh`** **`<体文件>`** **`<签名 hex>`** **`<GET /api/v1/meta → admin_exports.reconcile_export_ed25519_public_key_hex>`**（**OpenSSL 3+**；见 **Runbook §2.55**）。未配置服务端签名种子时 **无** 该头，**跳过** 本步。 |
| **7 · 证据存放位置** | 推荐 **`evidence/GO_YYYYMMDD/artifacts/vault-forwarded-offline-<UTC>/`**（**`<UTC>`** 与拉取时刻一致；**`GO_YYYYMMDD`** 与当次 **Gate/演练/发版** 证据目录同批）。包内须含 **C2** 所列 **体**、**侧车**、**`vault-forwarded-offline.manifest.json`**；可将 **脚本标准输出** 另存 **`vault-forwarded-export-fetch.log`** **同目录**。与 **[evidence/README](../../evidence/README.md#目录约定)** **目录约定** 对齐。 |

**验收（本 SOP）**：第三方 **不读** **`crates/api`** 实现，仅按上表 **1～7** 与链上文档完成 **一次** 成功拉取 + **manifest** 填全 + **SHA256** 复核（及 **Ed25519** 若存在）。

## 二、角色与职责（RBAC）

**与 [87](87-TravelTrust-角色体系技术文档-融合架构版.md) 区分**：**87** 描述前台协议用户的**四类角色**与链上/投影语义；本节 **SuperAdmin / Ops / CS / …** 仅描述**运营后台**权限，**不**等同于 Traveler、Guide、`provider` 或 Region Steward。

后台角色建议采用最小权限原则：

| 角色 | 核心职责 | 权限边界 |
|------|----------|----------|
| SuperAdmin | 平台级配置、角色/权限治理、高危审批 | 全量管理权限；高危操作双人审批 |
| Ops（运营） | 运营配置、内容治理、通知编排、向导审核 | 不可直接执行资金类链上动作 |
| CS（客服） | 用户/订单查询、纠纷协助、会话证据整理 | 默认只读，导出与冻结需审批 |
| Risk（风控） | 黑名单、风险规则、处置决策、仲裁协同 | 可触发风控动作与仲裁流程 |
| Finance（财务） | 对账、费率、分账、异常资金排查 | 仅财务域主写，链上执行需审批链 |
| Auditor（审计） | 全链路审计查看、导出审计报表 | 严格只读，不可改配置和业务状态 |

RBAC 粒度要求：

- 维度 1：功能权限（读/写/导出/审批/执行）。
- 维度 2：资源范围（国家/城市/业务线/渠道）。
- 维度 3：数据敏感级别（PII/财务/证据/风控规则）。
- 维度 4：操作风险级别（普通/高危/监管敏感）。

### 2.2 Job / Scheduler 角色映射（对齐 250/260）

为满足 `250`、`260` 文档同步门禁，后台需纳入如下最小角色映射：

| 阶段域角色 | 对应后台角色基线 | 权限说明 |
|---|---|---|
| `JOB_VIEWER` | Auditor / Ops（只读） | 查看队列、任务状态、失败记录 |
| `JOB_OPERATOR` | Ops | 单任务重试、暂停/恢复 worker（受审批策略约束） |
| `JOB_REPLAY_MANAGER` | Risk / Finance（受控） | 批量回放与补偿执行，必须审批 |
| `JOB_AUDITOR` | Auditor | 仅审计导出与证据校验 |
| `SCHED_VIEWER` | Auditor / Ops（只读） | 查看计划、运行记录、锁状态 |
| `SCHED_OPERATOR` | Ops | 手动触发、停用/启用计划 |
| `SCHED_RETRY_MANAGER` | Risk / Finance（受控） | 批量补跑与失败重跑，必须审批 |
| `SCHED_AUDITOR` | Auditor | 仅审计导出与证据校验 |

约束：资金相关任务的手动触发、批量重试、批量回放均需双人复核，并满足 `No Self-Approval`。

### 2.3 文件/证据角色映射（对齐 270）

为满足 `270` 文档同步门禁，后台需纳入如下最小角色映射：

| 阶段域角色 | 对应后台角色基线 | 权限说明 |
|---|---|---|
| `MEDIA_VIEWER` | Ops / CS（受限只读） | 查看对象目录、上传记录、版本历史 |
| `MEDIA_OPERATOR` | Ops | 上传处置、对象标记、签名链接发放 |
| `EVIDENCE_REVIEWER` | Risk / Compliance（受控） | 争议证据查看、证据归档、导出审批发起 |
| `MEDIA_AUDITOR` | Auditor / Compliance | 访问审计检索、导出验签、证据链复核 |

约束：争议证据、审核截图、内部附件为受限对象，默认私有；批量删除/导出必须审批并留痕。

### 2.1 财务与结算角色细粒度矩阵（对齐 200）

说明：`Finance` 在本文件是角色域总称；执行时必须细分为财务子角色，避免“有财务权限但职责不清”。

| 财务子角色 | 可读 | 可写 | 可审批 | 可导出 | 禁止项 |
|------|------|------|------|------|------|
| FINANCE_VIEWER | 对账报表、结算明细、差异列表 | 否 | 否 | 否 | 任何修正、执行、配置变更 |
| FINANCE_OPERATOR | 对账任务触发、差异标注、修正草稿 | 是（草稿） | 否 | 否 | 直接生效修正、仲裁执行 |
| RECON_MANAGER | 对账批次发布、差异归因确认 | 是 | 是（对账域） | 受限导出 | 费率修改、密钥相关 |
| SETTLEMENT_MANAGER | 结算批次执行、退款结算确认 | 是 | 是（结算域） | 受限导出 | 越权审批自己发起单 |
| FINANCE_AUDITOR | 全财务域只读、审计导出 | 否 | 否 | 是（审计导出） | 任何写操作 |

执行约束：

- 高危动作必须同时满足 `RBAC + 审批 + 审计` 三门禁。
- 审批链必须满足 `No Self-Approval`，申请人与审批人不可同人。
- 导出动作必须记录 `approval_no`、`change_ticket_no`、`export_signature`。

## 四、两条硬约束（必须写死）

### 4.1 链为准 + 强对账视图

后台每个订单详情页必须同时展示：

- DB 状态（业务投影状态）。
- 链上状态（合约状态机阶段）。
- 链上事件列表（至少含 eventName、blockNumber、txHash、logIndex、timestamp）。
- 区块确认数（confirmations）。
- Reorg 风险提示（低确认场景）。
- Finality 参数与确认规则（默认 `finalityN=12`，如变更需走配置评审与审计记录）。
- 事件消费 checkpoint（`blockNumber,logIndex`）及回退重放状态（最近一次 rewind/replay 时间与范围）。
- 事件表写入策略（append-only）与投影版本号（projection version）。

目的：客服、财务、风控在处理资金问题时可解释、可复核、可追溯。

### 4.2 后台操作全审计

以下动作必须纳入审计链路（至少 DB 审计表 + hash/证据指针）：

- 封禁/解封用户或向导。
- 费率修改与分账规则变更。
- 仲裁执行（release/refund/penalty）。
- 导出聊天证据包。
- 风控阈值与黑名单规则修改。

最小审计字段集（目标态 v2）：

- who（操作者）
- when（时间）
- where（IP/设备/终端）
- what（动作与对象）
- before/after（字段级 diff）
- why（工单号/理由）
- result（成功/失败/失败码）
- trace（x-request-id / trace_id）
- onchain（txHash，可空）
- evidence（hash/对象存储指针）
- legal-proof（record_hash_fingerprint / export_signature）
- approval-link（approval_no / change_ticket_no）

合规与保全补充（目标态）：

- 导出链路必须有签名校验（export signature）与导出过期治理。
- dispute 证据保全需记录保全时间戳、访问审计、留存策略版本。
- 敏感数据导出必须带脱敏策略版本（masking policy version）与审批单号。

当前已落地审计字段（v1 基线）：

- `action`、`resource_type`、`resource_id`
- `actor_id`、`request_id`
- `payload`
- `created_at`

对应迁移：`crates/api/migrations/20250312000018_admin_audit_logs.sql`

| 动作类型 | 示例 | 审计失败策略 | 说明 |
|------|------|------|------|
| 高危写 | 角色变更、费率变更、仲裁执行、风控阈值变更 | **硬失败（拒绝执行）** | 防止“执行成功但不可审计” |
| 导出类 | 证据导出、审计报表导出、DSAR 导出 | **硬失败（拒绝导出）** | 必须保证法律可采纳性 |
| 低危写 | 非敏感配置草稿保存 | 建议硬失败（可按域策略） | 允许过渡期按域分级 |
| 只读查询 | 后台列表查询、详情查询 | best-effort（过渡期） | 不得据此宣称审计完态 |

强制要求：

- 任何被标记 `Implemented` 的高危写/导出动作，必须满足“审计失败硬失败”。
- 读链路若仍为 best-effort，状态只能标 `Partial`。

## 五、后台核心页面规范（P0）

### 5.1 订单详情页（强制双视图）

订单详情必须包含左右或上下双视图：

- 业务投影视图：订单信息、角色动作、工单进度、客服备注。
- 链上真相视图：Escrow 状态、事件流、确认数、交易回执、重试与告警。

必备字段：

- `orderId`、`escrowId`、`chainId`、`contractAddress`
- `dbStatus`、`onchainStatus`
- `lastEvent`、`lastEventBlock`、`confirmations`
- `funds`（金额、币种、费率、分账）
- `riskFlags`、`disputeStatus`

### 5.2 争议仲裁页（证据闭环）

- 工单、证据、规则引用、仲裁结论、链上执行回执必须同屏可见。
- 仲裁执行动作前必须二次确认，执行后必须落 `txHash`。

### 5.3 对账页（链上到账本）

- 按批次展示链上事件到账本映射。
- 差异项支持分类（延迟、重复、缺失、金额不一致、状态不一致）。
- 每次修正动作都要记录修正人、修正原因、关联证据。

### 5.4 故障处理与灾备演练（Admin 运行面）

后台必须具备以下故障处理入口与演练留痕：

- RPC 不可用：自动降级 + 手动切换节点 + 影响范围记录。
- Indexer 落后：lag 监控、重放入口、checkpoint 回退证据。
- Reorg 触发：受影响订单列表、回滚范围、恢复确认。
- 执行器卡单：死信列表、重试、人工介入审批链。
- Token 冻结/黑名单冲突：风控与财务联合处置工单。

演练记录最小字段（对齐 140/380）：

- `drill_id`、`scenario`、`owner`、`started_at`、`finished_at`
- `rpo_result`、`rto_result`
- `postmortem_link`

## 六、数据与接口落地要求

### 6.1 数据分层

- L1：链上事实层（Escrow 合约状态与事件）。
- L2：后端投影层（可查询的 API 聚合状态）。
- L3：存储层（DB 表，服务 L2，不可反向覆盖 L1 真相）。

补充约束（与 02 架构文档对齐）：

- L1->L2 仅接受达到 finality 的事件（默认 `finalityN=12`），严禁未确认事件直接覆盖资金终态。
- 事件消费 checkpoint 必须至少包含 `blockNumber+logIndex`，reorg 时按 checkpoint 回退并重放。
- 事件明细表 append-only；投影视图可重建；需保留“DB 全丢重建最小产物”脚本与证据路径。

## 七、权限与审批流（建议模板）

高危动作（封禁、费率、仲裁执行、导出证据、风控阈值）采用四段式：

1. 发起：操作者提交动作与理由。
2. 审批：审批人（同域上级或双人）确认。
3. 执行：系统执行写操作或链上动作。
4. 归档：自动生成审计记录与证据指针。

审批必要字段（目标态）：

- `approval_flow_id`
- `initiator`
- `approver`
- `risk_level`
- `business_reason`
- `ticket_no`
- `expire_at`

审批流强约束（目标态，来自 360）：

- `No Self-Approval`：申请人与审批人不可同人。
- `Step Integrity`：审批步骤不可跳过、不可越级覆盖。
- `Expire and Revalidate`：审批超时后必须重新拉取上下文并重新审批。
- `Audit Mandatory`：每个审批节点必须留痕且可导出。

执行器高危动作附加字段（目标态，适用于 release/refund/penalty/executeResolution）：

- `resolution_id`（执行器幂等主键）
- `idempotency_key`（接口幂等键）
- `amount_limit_snapshot`（审批当刻单笔/单日额度快照）
- `approver_quorum`（双人审批最小法定人数）
- `resolution_type`、`amounts_json`
- `chain_id`、`contract_address`

执行器门禁（必须写死）：

- 无 `resolution_id` 或重复 `resolution_id` 时拒绝执行。
- 未满足双人审批或超出单笔/单日额度时拒绝执行。
- 执行成功后必须回填 `tx_hash`、`block_number`、`log_index`。

### 7.1 审批流适用范围白名单（高危动作）

以下动作默认进入强审批流，不得绕过：

- 角色与权限变更（含 role 升降级、策略发布）
- 财务修正与结算生效（含费率、批次修正、退款结算）
- 仲裁执行链上动作（release/refund/penalty/executeResolution）
- 合规导出（审计导出、DSAR 导出、证据包导出）
- 风控策略与阈值变更（封禁/解封规则、额度阈值）
- 索引器重放与回退（checkpoint 回退、replay 计划执行）

不在白名单中的写动作，仍需审计；是否审批由风险等级策略决定。

当前已落地审批字段（v1 基线，角色变更审批）：

- `action`、`resource_type`、`resource_id`
- `requested_by`、`approved_by`
- `status`、`reason`、`approve_reason`
- `before_payload`、`after_payload`
- `created_at`、`approved_at`

对应迁移：`crates/api/migrations/20250313000019_admin_approval_requests.sql`

## 九、验收清单（上线门禁）

### 9.1 目标态门禁（上线前必须全部满足）

- 订单详情页可同时看到 DB 状态 + 链上状态 + 事件 + 确认数。
- 订单详情页可看到 finality 参数、checkpoint 与 reorg 回放状态。

- 审计报表可按 `requestId -> messageId -> txHash -> logIndex -> jobId` 串联请求链路。
- 导出证据包具备 hash 与工单号关联。
- 仲裁动作可回溯到 `txHash` 与仲裁规则引用。
- 仲裁执行满足 `resolutionId` 幂等、双人审批、单笔/单日额度门禁。
- 审批流满足 `No Self-Approval`、步骤完整性、过期重校验。
- 对账批次可复算并可追踪修正历史。
- 风控规则变更可查版本、查审批、查回滚点。
- 事件表 append-only 且具备“DB 全丢重建最小产物”的可复现证据。

- DSAR（数据导出/删除请求）具备审批、时限、导出签名与证据归档闭环。
- 数据权限策略（policy/scope/filter）变更可审计、可回滚。
