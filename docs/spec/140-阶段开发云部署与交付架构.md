## 一、文档定位

本文定义 TravelTrust 在 140 阶段的“云部署 / DevOps / CI-CD / 灾备”开发规范。

140 阶段解决的问题不是“应用怎么写”，而是“系统如何稳定交付、可控上线、可恢复运行”。

若缺失交付架构，系统将面临：

- 环境漂移导致“本地可用、线上失败”。
- 发布不可控导致大面积回归或资损风险。
- 配置与密钥治理薄弱导致安全事故。
- 故障后无法快速恢复导致长时间中断。

## 二、系统目标

140 阶段目标是建立“可重复、可审计、可回滚、可灾备”的交付闭环：

1. 环境可分层：local / dev / staging / prod 职责清晰且可复制。
2. 发布可流水线：CI/CD 自动化构建、测试、部署、验收。
3. 配置可治理：配置中心统一管理，变更可追踪。
4. 密钥可保护：Secret 不落地明文，权限最小化。
5. 故障可恢复：备份、恢复、跨区容灾策略可演练。

## 三、范围定义（八大交付模块）

### 3.1 环境分层（local / dev / staging / prod）

核心能力：

- 环境职责边界定义：
  - local：开发与调试。
  - dev：日常联调与功能验证。
  - staging：预发布回归与演练。
  - prod：生产服务与审计留痕。
- 各环境配置隔离（DB、RPC、队列、缓存、日志、告警）。
- 环境一致性基线（镜像、依赖、迁移版本一致）。

验收要求：

- 关键服务在四层环境均有明确部署清单。
- 同一提交在不同环境行为差异可解释、可追踪。

### 3.2 CI/CD 流水线

核心能力：

- CI 阶段：lint、单测、集成测试、合约测试、构建、制品签名。
- CD 阶段：按环境自动/半自动发布、健康检查、门禁验证。
- 发布记录：commit、镜像 digest、部署批次、责任人、时间。

最小流水线（P0）：

- Pull Request：静态检查 + 测试门禁。
- Merge 到主干：构建镜像 + 生成制品清单。
- staging 自动部署 + 冒烟验证。
- prod 需审批发布 + 发布后自动回归。

验收要求：

- 流水线失败可阻断发布。
- 任一线上版本可追溯到源码提交与构建制品。

### 3.3 配置中心（Configuration Management）

核心能力：

- 配置集中管理（环境级、服务级、功能开关级）。
- 配置版本化与变更审计。
- 配置发布策略（灰度生效、回滚机制、生效校验）。

配置治理原则：

- 业务参数、风控阈值、finality、告警阈值必须集中治理。
- 禁止通过临时手工改容器内文件作为长期方案。

验收要求：

- 配置变更有审批记录与变更单关联。
- 配置回滚可在分钟级完成。

### 3.4 Secret 管理（密钥与凭据）

核心能力：

- Secret 托管于 KMS/Secret Manager/Vault 类系统。
- 服务通过短期凭据或受控注入获取密钥。
- 密钥轮换、吊销、最小权限策略。

必须纳管的 Secret：

- 数据库凭据、消息队列凭据、缓存凭据。
- RPC key、签名服务凭据、第三方 API key。
- 执行器相关敏感凭据与审批令牌。

验收要求：

- 仓库、镜像、日志中不得出现明文密钥。
- 密钥泄漏演练有标准响应流程。

### 3.5 灰度发布与回滚策略

核心能力：

- 灰度策略：按流量比例、用户组、区域、功能开关分批发布。
- 健康判定：错误率、延迟、关键业务成功率、告警状态。
- 自动回滚：超过阈值自动停止扩量并回退。

最小发布策略（P0）：

- 5% -> 20% -> 50% -> 100% 分批。
- 每一批次有最短观察窗口。
- 任一批次触发 P1 告警立即回滚。

量化门禁基线（P0，必须写入 CI/CD 策略并按 fail-closed 执行）：

- 观察窗口：每批次至少 10 分钟，且不少于 500 个有效请求样本。
- 错误率阈值：`5xx_rate <= 1%`，连续 3 个 1 分钟窗口超阈值即阻断扩量。
- 延迟阈值：`p95_latency` 相对上一稳定批次劣化不超过 20%。
- 业务成功率阈值：核心写路径成功率不低于 99%。
- 自动回滚阈值：命中 P1 告警或同时命中任意两项阈值失败时，立即回滚到上一稳定批次。

阈值来源与发布约束（必须）：

- 告警与健康阈值来源：以 `docs/spec/120-阶段开发观测告警日志与审计链路.md` 的规则定义为主。
- 参数发布来源：阈值变更须通过 `docs/spec/220-阶段配置中心-Config-Center.md` 的版本发布流程生效。
- 一致性要求：阈值来源、发布版本号与证据快照必须可相互追溯。

门禁责任与执行入口（必须绑定）：

- 门禁 Owner：`Release Manager`（主责） + `SRE Oncall`（备份）。
- 执行入口：`Build`（backend/frontend/e2e）、`Contract ABI Gate`、`Internal Drill Gate`、`Indexer Reconcile Gate`。
- 执行策略：任一必过门禁失败即阻断发布（fail-closed），不得人工绕过。

验收要求：

- 每次发布有灰度轨迹与决策记录。
- 回滚脚本与回滚演练通过。

### 3.6 数据备份与恢复（Backup / Restore）

核心能力：

- DB 定期全量备份 + 增量备份。
- 配置、审计日志、关键证据包归档备份。
- 恢复演练（RPO/RTO 目标验证）。

最小要求（P0）：

- 每日备份、跨存储介质保留。
- 每月至少一次恢复演练。
- 恢复后数据一致性校验流程。

验收要求：

- 恢复结果可通过对账验证。
- 备份不可用或恢复失败必须触发高优先级告警。

### 3.7 多区域部署与灾备策略

核心能力：

- 单区域主用 + 跨区域热备或冷备方案。
- 流量切换策略（DNS/LB/Gateway 级）。
- 跨区域数据复制一致性策略。

最小策略（P0）：

- 明确主区域与灾备区域。
- 明确故障切换触发条件与审批机制。
- 明确恢复回切流程。

验收要求：

- 每季度至少一次跨区切换演练。
- 切换过程具备业务影响评估与复盘。

### 3.8 WAF / LB / CDN / 网关边界治理

核心能力：

- WAF：基础攻击防护、速率限制、规则治理。
- LB：健康检查、连接管理、跨可用区分流。
- CDN：静态资源加速与边缘缓存策略。
- 网关：统一鉴权、限流、路由、internal 路径隔离。

硬约束：

- `/api/v1/internal/*` 禁止公网直连。
- 对外入口必须经过 WAF + LB + 网关链路。
- 关键路由具备速率限制和异常拦截。

验收要求：

- 网络边界规则有版本化配置与审计记录。
- 内外网隔离策略可通过安全扫描验证。

## 四、发布与交付硬约束（必须写死）

1. No Env Drift：环境配置差异必须显式可见，不得隐式漂移。
2. Pipeline First：未通过 CI/CD 门禁不得手工绕过发布。
3. Config as Managed Asset：配置必须可版本化、可审计、可回滚。
4. Secret Zero-Plaintext：敏感信息不得明文出现在仓库、镜像、日志。
5. Canary Before Full Release：生产必须先灰度后全量。
6. Backup is Testable：备份策略必须通过恢复演练验证。
7. DR is Operational：灾备不是文档条款，必须定期演练并留痕。
8. Edge Security Mandatory：WAF/LB/CDN/网关是正式组成，不是可选增强。

## 六、实施计划（140 阶段）

### 6.1 P0（必须）

- 四层环境分层标准落地。
- CI/CD 最小流水线打通并接入测试门禁。
- 配置中心与 Secret 托管最小能力上线。
- 灰度发布与自动回滚最小流程上线。
- 备份与恢复演练最小闭环完成。

### 6.2 P1（增强）

- 多服务统一交付模板（IaC/Helm/Terraform 等）。
- 多区域热备与自动切换策略增强。
- 边界安全策略自动化校验（WAF/Gateway 规则检测）。
- 发布风险评分与自动审批建议。

### 6.3 P2（规模化）

- 全链路发布编排平台化。
- 多区域主动-主动或主动-被动标准化。
- 灾备演练自动化与审计报表自动出具。
- 成本与容量联动优化（FinOps + SRE）。

## 七、发布门禁（分层：P0 必须全过）

### 7.1 P0（最小可发布门禁，必须全过）

1. local/dev/staging/prod 分层标准与部署清单齐备。
2. CI/CD 主流水线稳定运行，且测试门禁有效。
3. 生产发布采用灰度策略并具备回滚证据。
4. 备份恢复演练达标（RPO/RTO 达成）。
5. `/api/v1/internal/*` 内外网隔离策略通过校验并有证据留痕。
6. `indexer-replay/indexer-reconcile` 回放与对账门禁通过，且具备 `finalityN/reorg` 相关演练证据。
7. 合约接口与 ABI 门禁通过（`Contract ABI Gate`），且证据可追溯到当前发布候选。
8. 发布门禁由 `.github/workflows/build.yml`、`.github/workflows/contract-abi-gate.yml`、`.github/workflows/internal-drill-gate.yml`、`.github/workflows/indexer-reconcile-gate.yml` 联合判定，任一失败即阻断发布。

### 7.2 P1/P2（增强门禁，按阶段收口）

1. 配置中心与 Secret 管理纳管率达到目标值后，再执行全量纳管门禁。
2. 多区域灾备演练与自动切换能力完成后，再执行跨区发布门禁。
3. WAF/LB/CDN/网关的自动化策略校验闭环完成后，再执行规模化门禁。

## 八、与 20 云部署架构的强绑定

140 阶段将 20 文档中的部署架构从“设计图”升级为“交付系统”：

- `20` 定义了正式组成：CDN/WAF、LB、CockroachDB、Redis、NATS、多区域扩展。
- `140` 负责把这些组成转化为可交付、可运维、可恢复、可审计的工程能力。

结论：在 TravelTrust 中，云部署与 DevOps 不是锦上添花，而是正式系统组成与发布前置条件。

| 外网探测日志 | `evidence/GO_YYYYMMDD/internal_external_probe.log` | 外网入口探测返回拒绝（403/404/ACL deny），不得出现 2xx |
| 内网探测日志 | `evidence/GO_YYYYMMDD/internal_internal_probe.log` | 内网入口可受控访问并返回预期状态 |
| 审计样本 | `evidence/GO_YYYYMMDD/internal_audit_sample.json` | 至少包含请求时间、调用来源、request_id/trace_id |

执行建议（示例）：

- 外网探测：`curl -i https://<public-host>/api/v1/internal/indexer-status`
- 内网探测：`curl -i http://<private-host>/api/v1/internal/indexer-status`
- 策略导出：保存网关/WAF 配置快照或规则导出文本并归档。

### 9.3 发布/备份/灾备证据模板（最小集合）

为避免“门禁存在但取证口径不一致”，发布候选必须补齐以下证据包（与 9.2 共同归档）：

| 证据项 | 文件命名（示例） | 最低要求 |
|---|---|---|
| 灰度批次与回滚轨迹 | `evidence/GO_YYYYMMDD/canary_batches.json` | 包含 5%/20%/50%/100% 各批次开始时间、观察窗口、阈值判定、是否扩量/回滚 |
| 发布门禁判定快照 | `evidence/GO_YYYYMMDD/release_gate_snapshot.md` | 记录错误率、P95、核心成功率、告警状态与最终放行/阻断结论 |
| 备份作业记录 | `evidence/GO_YYYYMMDD/backup_job_report.json` | 至少包含全量/增量备份时间、介质、校验结果 |
| 恢复演练记录 | `evidence/GO_YYYYMMDD/restore_drill_report.json` | 至少包含场景、恢复时长、RPO/RTO 实测、对账结论 |
| 跨区切换演练记录 | `evidence/GO_YYYYMMDD/dr_failover_drill.md` | 至少包含触发条件、切换步骤、业务影响、回切结果、复盘链接 |
| 对账与回放报告 | `evidence/GO_YYYYMMDD/reconcile_diff_report.json` | 至少包含 replay/reconcile 任务结果、差异分类、处理结论 |

统一字段要求（所有证据文件必须具备）：

- `change_ticket`：关联变更单或工单号。
- `approved_by`：审批人与审批时间。
- `commit_sha`：对应源码提交。
- `image_digest`：对应部署镜像摘要（如适用）。
- `generated_at`：证据生成时间（UTC）。

字段校验入口（必须）：

- CI 校验：`check-08-consistency` 与 `check-08-evidence-pointer` 工作流作为证据字段与路径一致性门禁入口。
- 本地校验：`scripts/check-08-consistency.sh`、`scripts/check-08-evidence-pointer.sh` 作为提交前自检入口。

执行建议（示例）：

- 生成灰度轨迹：由 CI/CD 在每批次结束时写入 `canary_batches.json` 并附 commit/image digest。
- 生成恢复报告：演练结束后输出 `restore_drill_report.json`，并关联 `postmortem_link`。
- 生成对账报告：由 `indexer-reconcile` 流程输出 `reconcile_diff_report.json` 并归档。
