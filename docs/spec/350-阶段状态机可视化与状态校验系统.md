## 一、文档定位与权威链路

本文定义 TravelTrust 在 350 阶段的“状态机可视化与状态校验系统”开发规范，目标是把多域状态从“描述性规则”升级为“可执行治理”。

本阶段必须满足以下串联关系：

- 业务与资金状态口径：以 `01/03` 为硬约束。
- 状态写入边界与 API 契约：以 `04 §3.4/§3.5` 与 `14` 为准。
- 链上事件事实与投影对齐：依赖 `110`（finality/reorg/checkpoint）。
- 管理后台承接与审计：以 `70` 状态口径与发布门禁为准。

## 三、状态域范围与单一事实源

至少纳管以下状态机：

- 行程状态
- 订单状态
- Escrow 状态
- 争议状态
- 仲裁状态
- AI 状态
- 审核状态
- 向导档期状态

单一事实源约束：

- 资金终态相关状态（Escrowed/Released/Refunded/Slashed 等）必须以链上事件投影为准。
- 链下业务状态（草稿、聊天子状态、运营审核子状态）必须通过统一迁移规则写入，不得绕过守卫直接改库。
- 前端展示状态必须来自后端聚合结果，不得前端本地推断资金终态。

### 3.1 关键状态机最小迁移表（执行锚点）

为避免“合法迁移”口径漂移，订单、争议、Escrow、档期状态机至少按以下最小集合执行（与 `01/03` 一致，冲突时以 `01/03` 为准；具体命名以实现定稿为准）：

| 状态机 | 当前状态 | 合法下一状态 | 禁止示例 |
|--------|----------|--------------|----------|
| 订单 | `Created` | `Accepted`、`Cancelled` | `Created -> Escrowed`（跳过接单） |
| 订单 | `Accepted` | `Escrowed`、`Cancelled` | `Accepted -> Completed`（跳过托管） |
| 订单 | `Escrowed` | `Completed`、`Disputed` | `Escrowed -> Cancelled` |
| 订单 | `Disputed` | `Refunded`、`PartiallyRefunded`、`Slashed`、`Completed` | `Disputed -> Accepted` |
| 订单 | `Completed/Refunded/PartiallyRefunded/Slashed/Cancelled` | 无（终态） | 终态再迁移到非终态 |
| 争议 | `Open` | `Assigned`、`Resolved` | `Open -> Executed` |
| 争议 | `Assigned` | `Resolved` | `Assigned -> Open`（无审计回放上下文） |
| 争议 | `Resolved` | 无（终态） | `Resolved -> Assigned` |
| Escrow | `PendingFunding` | `Funded`、`Cancelled` | `PendingFunding -> Released`（跳过入金） |
| Escrow | `Funded` | `Released`、`Refunded`、`PartiallyRefunded`、`Slashed` | `Funded -> PendingFunding` |
| Escrow | `Released/Refunded/PartiallyRefunded/Slashed/Cancelled` | 无（终态） | 终态再迁移到非终态 |
| 档期 | `Available` | `SoftHeld`、`Locked` | `Available -> Released` |
| 档期 | `SoftHeld` | `Locked`、`Released` | `SoftHeld -> Completed` |
| 档期 | `Locked` | `Released`、`Completed` | `Locked -> Available`（绕过释放） |
| 档期 | `Released/Completed` | 无（终态） | 终态再迁移到占用态 |

执行要求：

- 状态迁移实现必须同时输出 `machine_code`、`from_state`、`to_state`、`rule_expr`、`risk_level`。
- 任何不在白名单中的迁移，必须写入 `state_anomalies` 并触发告警。

## 四、风险说明（不建设 350 的后果）

- `DB 状态 != 链状态`，资金页与后台视图长期漂移。
- 后端出现“跨状态直跳”，导致订单卡死或重复副作用。
- 前端显示状态与后端不一致，触发错误操作与用户投诉。
- 事故恢复无法判断“正确目标状态”，修复动作不可审计。

## 五、系统能力目标（必须具备）

- 状态图定义（State Graph Definition）
- 状态校验器（State Validator）
- 非法跳转检测（Illegal Transition Detector）
- 修复工具（Repair Toolkit）
- 修复审批与审计串查（Approval + Audit Trace）

## 六、模型与校验设计（最小契约）

建议最小实体：

- `state_machines`
- `state_transitions`
- `state_validation_runs`
- `state_anomalies`
- `state_repairs`

字段级最小要求：

- `state_machines`：`machine_code`、`domain`、`version`、`active`、`owner_role`、`updated_at`。
- `state_transitions`：`machine_code`、`from_state`、`to_state`、`rule_expr`、`side_effect_code`、`risk_level`。
- `state_validation_runs`：`run_id`、`machine_code`、`checked_count`、`anomaly_count`、`started_at`、`finished_at`。
- `state_anomalies`：`entity_id`、`expected_state`、`actual_state`、`source`、`detected_at`、`severity`。
- `state_repairs`：`repair_id`、`entity_id`、`before_state`、`after_state`、`approved_by`、`approval_no`、`audit_ref`。

## 七、核心硬约束（可执行）

1. Single State Spec：状态定义集中管理，禁止多处硬编码。
2. Transition Guard：所有状态变更必须经过合法迁移校验。
3. Chain Alignment：资金终态与链上事件校验一致，禁止“仅 DB 写终态”。
4. Repair With Approval：状态修复必须审批并留痕，禁止直接热修状态。
5. Side-Effect Idempotency：状态回放不得重复触发副作用（通知、占档、解档、计费）。
6. Visual First：订单/争议/Escrow 三类关键状态机必须有可视化版本图谱。

## 八、Admin 契约锚点（与 04/14 对齐）

`GET /api/v1/admin/lifecycle/state-machines` 最小契约（**Implemented（基线）**，与 `04`、`14` 对齐）：

- 最小响应字段：`items[].machine_code/domain/version/entity_type/current_state/expected_state/anomaly_flag/anomaly_type/last_transition_at/source_of_truth/repairable`，`meta.generated_at` / `meta.source` / `meta.checkpoint` / `meta.note` / **`meta.build`**（与 **`GET /meta.build`** 同源）。
- 最小错误码：`401 login_required`、`403 admin_required`、`400 invalid_lifecycle_anomaly_flag_filter`（**可无 DB**）、`200 ok`、`503 admin_db_required`。
- 状态口径：DB 台账可读；种子 `current_state` 等为占位，真实对齐与非法跃迁检测以本文 §三～§五 后续阶段为准。

## 十一、发布门禁（量化）

1. 关键状态机图谱覆盖率：`100%`（订单/争议/Escrow/档期至少四域）。
2. 非法跳转告警漏报率：`<= 1%`（以抽样回放校验）。
3. 资金相关状态链路一致性：`100%`（抽样窗口内 DB 与链投影一致）。
4. 状态修复审批覆盖率：`100%`（修复记录必须具备 `approval_no + audit_ref`）。
5. 回放与重跑幂等校验通过率：`100%`（不得重复副作用）。

### 11.1 量化门禁统计口径（必须写死）

为确保门禁可复核，统计口径统一如下：

- 统计窗口：默认按 `7d` 滚动窗口；重大变更发布前补跑 `30d` 回溯窗口。
- 最小样本量：迁移样本 `N >= 1000`（不足则不得判定门禁通过）。
- 数据源：以 `indexer` 事件投影、`reconciliation_reports`、`state_validation_runs` 为主证据。
- 责任角色：`Admin-Backend`（状态迁移）、`Admin-Risk`（异常与修复）、`Admin-SRE`（回放与幂等）。
- 失败策略：任一量化项不达标按 `fail-closed` 处理，不进入发布候选。

### 11.2 量化门禁公式（分子/分母写死）

- 图谱覆盖率 = `已发布且具备迁移白名单的关键状态机域数 / 应覆盖关键域总数`。
- 非法跳转告警漏报率 = `复盘确认非法跳转但未告警数 / 复盘确认非法跳转总数`。
- 资金状态链路一致性 = `抽样窗口内 DB 与链投影一致的资金状态样本数 / 抽样资金状态样本总数`。
- 状态修复审批覆盖率 = `包含 approval_no + audit_ref 的修复记录数 / 修复记录总数`。
- 回放与重跑幂等通过率 = `无重复副作用的回放任务数 / 回放任务总数`。

## 十二、文档同步门禁（与权威层级对齐）

- 冲突优先级：与 `01/03` 冲突时以 `01/03` 为准。
- API/契约变更：新增、删除、改名接口或状态口径变更，必须同步 `04 §3.4/§3.5` 与 `14`。
- 后台治理口径变更：必须同步 `70` 与 Runbook。
- 文档串联变更：必须同步 **[07-开发流程与顺序](07-开发流程与顺序.md)（§零～§五正文）**、[00-文档索引](00-文档索引.md)；[00-文档体系与阅读串联](00-文档体系与阅读串联.md) 为兼容壳（涉及 CI 关键词如 `82` 时须核对）。

## 十三、结论

状态机可视化与状态校验系统是跨域稳定性的基础设施层，不是可选优化项。350 阶段未形成可执行门禁前，不得将状态治理宣称为 `Implemented`。
