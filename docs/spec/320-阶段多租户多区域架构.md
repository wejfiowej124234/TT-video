## 一、文档定位

本文定义 TravelTrust 在 320 阶段的“多租户与多区域架构”开发规范。

320 阶段用于提前建立全球化扩展骨架，避免后期因合规、运营与数据主权要求导致系统级重构。

与权威层关系：

- `01`：全球化边界与合规约束总则。
- `02`：多区域分层与数据边界架构锚点。
- `220`：区域与租户策略配置治理单源。
- `04/14`：对外/后台 API 契约单源与状态口径。
- `70`：后台“租户与区域治理”模块与数据权限承接。

## 二、业务背景

全球旅游平台后续通常会出现：

- 不同国家不同规则
- 不同地区不同合规
- 不同运营团队
- 不同数据库分区
- 不同节点集群

必须具备核心维度：

- `tenant_id`
- `region_id`
- `country_code`
- `jurisdiction`

## 三、风险说明

若不提前设计 320 阶段，后期会高概率出现：

- 欧洲 GDPR 与现有数据流冲突。
- 美国与亚洲策略冲突无法隔离。
- 支付、风控、通知、密钥等区域策略互相污染。
- 数据跨区流动违规，审计不可过。

## 四、系统目标

1. 多租户隔离：租户级配置、数据、权限、计费可隔离。
2. 多区域自治：区域级部署、服务路由、故障隔离可执行。
3. 合规可落地：按司法辖区控制数据驻留与访问边界。
4. 运营可分权：不同运营团队只操作所属租户/区域。
5. 扩缩容可控：新增租户或区域不需全系统重构。

## 五、架构范围

### 5.1 租户层（Tenant Layer）

- 租户主数据、租户配置、租户权限域。
- 租户级资源配额与账单边界。

### 5.2 区域层（Region Layer）

- 区域路由（流量入口、API 网关、消息系统）。
- 区域服务集群与灾备策略。

### 5.3 合规层（Jurisdiction Layer）

- 数据驻留规则。
- 跨区访问审批与审计。
- 隐私删除与脱敏策略。

### 5.4 数据层（Data Partition Layer）

- 按租户、区域、国家分区策略。
- 热点租户独立分库/分片能力。
- 跨区数据同步与一致性等级定义。

## 六、数据模型建议

建议最小实体：

- `tenants`
- `regions`
- `tenant_region_bindings`
- `jurisdiction_policies`
- `tenant_data_partitions`
- `tenant_audit_scopes`

字段级要求：

- `tenants`：`tenant_id`、`tenant_code`、`status`。
- `regions`：`region_id`、`region_code`、`cloud_zone`。
- `tenant_region_bindings`：`tenant_id`、`region_id`、`country_code`、`jurisdiction`。
- `jurisdiction_policies`：`jurisdiction`、`data_residency_rule`、`cross_border_rule`。

命名与隔离口径对齐（与 `530/70`）：

- 作用域键建议统一为：`tenant_id + region_id + scope + filter`。
- `tenant_region_bindings` 负责租户-区域-国家/法域绑定；`jurisdiction_policies` 负责法域策略版本与生效规则。
- 后台策略页、审批页与审计页中的字段命名不得与 `70` 的 `scope/filter/policy` 口径漂移。

## 七、核心硬约束

1. Tenant First：所有核心数据必须可追踪到 `tenant_id`。
2. Region Aware：服务请求必须包含 `region_id` 或可解析区域。
3. Compliance Gate：跨区数据访问必须可审批可审计。
4. Isolation by Default：默认最小跨租户、跨区域权限。
5. Policy Versioned：合规与区域策略必须版本化可回滚。

## 九、后台模块要求

后台新增一级模块：`租户与区域治理`

子模块（必须）：

- 租户管理
- 区域管理
- 国家/司法辖区策略
- 数据分区映射
- 跨区访问审批

## 十、实施计划（320 阶段）

口径说明：本章是目标态计划，不代表当前已实现状态；发布与验收判定以 `11.2/11.3/11.4/11.5` 为准。

## 十一、发布门禁

1. 关键数据对象已带租户与区域维度。
2. 跨区访问有审批与审计记录。
3. 区域策略回滚演练通过。
4. 合规抽检可输出证据链。

### 11.1 门禁执行锚点（运维/后台）

- 租户作用域台账与发布：**`GET /api/v1/admin/tenants/scopes`**、**`POST /api/v1/admin/tenants/scopes/:id/publish`**（**`meta.build`** 与 **`GET /meta.build`** 同源，便于发布追溯）。
- 运行与审计锚点：`GET /api/v1/admin/audit/operations`。
- 灰度 / 区域投放（与 **240** 共有）：`GET /api/v1/admin/flags`、`POST /api/v1/admin/flags/:id/publish`。
- 数据隔离承接锚点：`docs/spec/70-管理员系统开发文档.md`（`320/530` 门禁行）。
- 证据归档路径：`evidence/GO_YYYYMMDD/`。

临时验收替代证据（`70` 对应条目仍为 `Target` 时）：

- 策略样本证据：`tenant_id/region_id/scope/filter` 组合策略样本与命中结果。
- 审批样本证据：跨区访问审批单与审批时间线。

## 十二、结论

多租户与多区域不是后期补丁，而是全球化平台的架构基线。没有 320 阶段，后期合规与运营扩展成本会指数级上升。
