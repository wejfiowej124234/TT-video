## 一、44 阶段目标与范围

| 维度 | 说明 |
|------|------|
| **阶段目标** | **每个国家单独成模块**：一国一文件（或一国一配置对象），修改某国定价时只改该文件，方便以后维护与扩展。 |
| **背景** | 各国房价、用车价格、城际交通、住宿费用、景区/餐饮单价、向导等级价均不同；若混在一处配置，易错、难扩展。 |
| **范围** | 前端 `lib/countries/` 下按国家拆分的定价配置；报价与表单逻辑根据 `form.country` 取对应国家配置。 |
| **不涉及** | 后端汇率、多币种展示、支付通道；本阶段仅限前端「按国家取定价配置」的结构与约定。 |
| **交付物** | ① `lib/countries/` 目录与类型定义；② 各国独立文件（cn/jp/th/…）；③ `getPricingForCountry(country)` 统一入口；④ 自定义行程弹窗报价与表单已接入国家配置；⑤ 本文 §五 验收表可勾选。 |

**判定「需按国家独立」的定价项**（以下均按国家区分）：

- **房价/住宿**：每间夜每人单价（不同国家差异大）。
- **用车价格**：市内轿车/SUV/商务车每日单价。
- **城际交通**：飞机、高铁（或铁路）每人单价。
- **景区/餐饮单价**：每人每处参考价。
- **向导等级建议日薪**：初级/中级/高级/专家，各国人力成本不同。

## 二、目录结构与单文件职责

### 2.1 推荐目录结构（与当前实现一致）

```
frontend/lib/countries/
  types.ts       # 国家定价配置类型与枚举
  index.ts       # BY_COUNTRY 映射、getPricingForCountry、导出
  cn.ts          # 中国
  jp.ts          # 日本
  kr.ts          # 韩国
  sg.ts          # 新加坡
  th.ts          # 泰国
  ae.ts          # 阿联酋
  us.ts          # 美国
  au.ts          # 澳大利亚
  fr.ts          # 法国
  es.ts          # 西班牙
  it.ts          # 意大利（保留文件；当前不在产品期 BY_COUNTRY）
  uk.ts          # 英国（保留文件；当前不在产品期 BY_COUNTRY）
  README.md      # 目录职责与扩展说明（可选，建议保留）
```

### 2.2 单文件职责

| 文件 | 职责 |
|------|------|
| **types.ts** | 定义 `CountryPricingConfig` 及 `CityTransportType`、`TransportType`、`GuideLevel` 等类型；与业务表单/报价使用的类型对齐。 |
| **index.ts** | 维护「国家名 → 配置」映射表；导出 `getPricingForCountry(country: string)`，未知国家回退到默认（如中国）；导出类型与各国 config 便于单测或后台复用。 |
| **cn.ts / jp.ts / …** | 仅导出该国一份 `CountryPricingConfig`；不引用其他国家的文件，不包含业务逻辑。 |
| **README.md** | 简述本目录用途、入口、配置字段含义、新增国家步骤；方便后续接手与 Code Review。 |

### 2.3 与 geoOptions 的对应关系

- 国家名与 `lib/geoOptions` 的 `COUNTRY_OPTIONS`、`CITIES_BY_COUNTRY` 的 key **保持一致**（如「中国」「日本」「泰国」），以便 `form.country` 直接作为 `getPricingForCountry(form.country)` 的入参。
- **产品期十国锁死**：权威列表以 **`frontend/lib/productCountries.ts`** 与 Rust **`traveltrust_core::product_countries`**（及 **`GET /meta.product_countries`**）为准；后端写路径已校验向导 `country_code`（ISO）与 `POST /itineraries/custom` 的 `country`（中文名）。
- 新增国家时：须先改 **`productCountries.ts` + `traveltrust_core::product_countries` + `GET /meta`**，再同步 `geoOptions` / `lib/countries` / 文档 04/54。

## 三、配置约定（CountryPricingConfig）

### 3.1 字段说明

| 字段 | 含义 | 单位/说明 |
|------|------|-----------|
| **cityTransportPrice** | 市内用车：轿车 / SUV / 商务 每日单价 | 每车每日（元或当地币，与产品约定一致） |
| **intercityPricePerPerson** | 城际交通：飞机 / 高铁 每人单价 | 每人单程 |
| **perAttraction** | 景区单价 | 每人每处 |
| **perFood** | 餐饮单价 | 每人每处 |
| **hotelPerNightPerPerson** | 住宿 | 每间夜每人 |
| **guideLevelsSuggestedPerDay** | 向导等级建议日薪 | 初级/中级/高级/专家，按天 |

### 3.2 单国家文件示例（cn.ts）

```ts
import type { CountryPricingConfig } from "./types";

/** 中国：用车、城际、住宿、景区/餐饮、向导等级单价（人民币） */
export const pricingCN: CountryPricingConfig = {
  cityTransportPrice: { sedan: 80, suv: 120, van: 200 },
  intercityPricePerPerson: { flight: 400, rail: 150 },
  perAttraction: 18,
  perFood: 10,
  hotelPerNightPerPerson: 50,
  guideLevelsSuggestedPerDay: { primary: 150, intermediate: 280, advanced: 450, expert: 600 },
};
```

### 3.3 修改某国定价时

- **只改该国对应文件**（如只改 `jp.ts`），不改其他国家的 ts 文件，也不改类型定义（除非新增字段）。
- 改完后报价与表单会随 `form.country` 自动使用新配置，无需改业务组件逻辑。

## 四、操作步骤：新增国家与修改国家

### 4.1 新增一个国家

1. **geoOptions**：在 `COUNTRY_OPTIONS` 与 `CITIES_BY_COUNTRY` 中增加该国及其城市（国家名与 44 阶段用 key 一致）。
2. **lib/countries**：  
   - 新增 `xx.ts`（如 `de.ts` 德国），导出 `pricingDE: CountryPricingConfig`，按 §3.1 填齐各字段。  
   - 在 `index.ts` 的 `BY_COUNTRY` 中增加一行：`德国: pricingDE`（或当前使用的国家名 key）。  
3. **lib/cityDetails**（若需该国城市级数据）：若该国需要在行程中展示/点选**城市级景区、餐饮、酒店**，须在 `lib/cityDetails` 中补充该国城市数据（与 geoOptions 城市列表一致），详见 §十 与 cityDetails 分工。
4. **校验**：在自定义行程弹窗中选择该国、填行程，确认报价与向导「X/天」展示符合预期。

### 4.2 修改某国定价

1. 打开 `lib/countries/` 下该国文件（如 `jp.ts`）。
2. 仅修改该文件内数字（或新增字段时同步改 `types.ts` 与各国有默认值）。
3. 保存后报价与表单即按新配置计算，无需改 `useQuoteCalculation` 或表单组件。

### 4.3 回退与默认

- `getPricingForCountry(country)` 对未知或空字符串国家应返回**默认国家**（如中国）配置，避免报错或空白报价。
- 默认国家在 `index.ts` 中写死一处即可（如 `const DEFAULT_COUNTRY = "中国"`）。

## 七、总结

- **44 阶段核心**：把每个国家单独成模块（一国一文件 + 统一类型与入口），方便以后只改一国、不影响他国。
- **落地位置**：`frontend/lib/countries/`（types、index、cn/jp/th/…、README）。
- **使用方式**：业务侧通过 `getPricingForCountry(form.country)` 取配置，报价与表单逻辑与 42 一致，仅数据来源改为按国家模块化。

按本文 §二～§四 执行并勾选 §五 验收表，即完成 44 阶段「国家独立定价模块」的规范与落地。

#### 9.1 落地说明（单测与一致性校验）

实现 9.1 第 2、3 项时可按以下执行，便于 Code Review 与 CI 通过。

**单测（getPricingForCountry）**

- **文件**：`frontend/lib/countries/index.test.ts`（或项目约定的 `*.spec.ts`）。
- **用例要点**：
  1. **已知国家**：对 `BY_COUNTRY` 中存在的国家（如 `"中国"`、`"日本"`）调用 `getPricingForCountry(country)`，断言返回对象为该国的 config（如与 `pricingCN` 引用或深等）。
  2. **未知国家**：传入 `"未知国"`、`""`、`"   "` 等，断言返回为默认国家（中国）配置（与 `pricingCN` 一致）。
  3. **返回结构**：至少断言返回对象包含 `CountryPricingConfig` 全部必填字段（`cityTransportPrice`、`intercityPricePerPerson`、`perAttraction`、`perFood`、`hotelPerNightPerPerson`、`guideLevelsSuggestedPerDay`），且子对象结构正确（如 `cityTransportPrice.sedan` 为 number）。

**geoOptions ↔ countries 一致性校验**

- **位置**：可与上述单测同文件，或独立脚本（如 `scripts/check-countries-geo-consistency.ts`），在 CI 或 `npm test` 中执行。
- **断言要点**：
  1. **geoOptions → countries**：从 `lib/geoOptions` 取 `COUNTRY_OPTIONS` 的每个 option.value（国家名），断言该值在 `lib/countries` 的 `BY_COUNTRY`（或通过 `getPricingForCountry` 能取到非默认 config）中存在；若使用「默认国家」判断，则排除默认国后其余国家均须在 BY_COUNTRY 中。
  2. **countries → geoOptions**：`BY_COUNTRY` 的每个 key 须存在于 geoOptions 的国家列表（即 `CITIES_BY_COUNTRY` 的 key 或 `COUNTRY_OPTIONS` 的 value）中，避免前端选了某国却无城市列表。
- **说明**：两处 key 须完全一致（同一字符串），新增国家时两端同步，本校验用于 MR 阶段发现漏改。

## 十、与相关模块的约定

以下为 44 阶段与相关模块的**约定**，实现与 Code Review 时须遵守。

| 约定 | 说明 |
|------|------|
| **与 lib/cityDetails 分工** | **cityDetails**：按城市提供景区/美食/酒店**选项与详情**（getAttractions、getFood、getHotels 等），供表单点选。**countries**：按国家提供**定价配置**（用车、城际、住宿、景区/餐饮单价、向导等级价），供报价计算。二者均以「国家」为维度之一；新增国家时若需该国城市级数据，须同步维护 cityDetails 与 geoOptions。 |
| **消费方单一数据源** | 所有需要「按国家取定价」的代码**必须**通过 `getPricingForCountry(country)` 获取，不得在 CustomItineraryModal 或其它业务中再维护一份定价常量或映射表。 |
| **边界与回退** | 调用方不得假定 `country` 一定存在于 BY_COUNTRY；`getPricingForCountry` 对未知或空字符串返回默认国家配置，调用方无需再做判空或 fallback。 |
