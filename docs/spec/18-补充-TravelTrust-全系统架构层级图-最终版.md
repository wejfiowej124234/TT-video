## 二、关键主链路（非全模块同权重）

以下为项目**权重最高**的业务主链，与「订单与撮合」「行程与报价」文档串联一致：

```
游客创建需求
   ↓
AI / 自定义行程生成
   ↓
向导抢单 / 接单 + 沟通（含 TT 社区/订单聊天，见 53）
   ↓
向导确认接单 → 游客+向导双边确认最终行程
   ↓
confirm-final-plan（snapshotHash）
   ↓
创建 / 绑定 Escrow
   ↓
钱包支付托管
   ↓
旅游服务履约
   ↓
链下确认行程完成（confirm-completion，见 04 §3.4；非放款）
   ↓
订单进入完结路径或争议路径（状态机，01/03/53）
   ↓
（Happy）行程评分（若适用）→ 智能合约 release（Escrow.release）
（争议）裁决 / executeResolution；（取消等）refund / 处罚 — 以 01/03/53 为准
   ↓
结算 / 对账 / 审计归档
```

**与 [53-阶段开发技术文档](53-阶段开发技术文档.md)**：本主链路为 **18 与 53 共用口语**；**Happy 路径须理解为「链下确认行程完成 → 评分 → 释放」**（与 53 开篇、§3.2 步骤条、[18-TravelTrust-全系统架构图](18-TravelTrust-全系统架构图.md) §七 一致）。**`confirm-completion` ≠ `release`**，单源语义见 [04](04-后端与API.md) §3.4、[14](14-合约-API-ABI-前后端对齐.md)。页面与 API 细节以 **53、13-1、04** 为 SSOT。

## 三、企业级视角：五个中心

将全系统压缩为 **5 个运转中心**（与 [02 §十四](02-架构设计.md)「五中心」口径可对照，本文侧重产品/模块视角）：

| 中心 | 职责 | 核心对象（示例） |
|------|------|------------------|
| **1. 订单中心** | 把「旅游服务交易」组织起来 | itinerary / order / schedule / review |
| **2. 协议中心** | 把「最终确认后的交易」落到链上托管 | escrow / events / tx / finality / dispute |
| **3. 风控仲裁中心** | 真人交易的可信执行 | risk / blacklist / dispute / evidence / ruling |
| **4. AI 行程中心** | 行程生成、模板、国家规则、输出治理 | prompt / pricing / snapshot / generation / review |
| **5. 运营治理中心** | 后台管理、审计、财务、内容、发布与运维 | admin / audit / moderation / config / settlement |

## 四、最终分层结论：五层混合平台

| 层 | 含义 |
|----|------|
| **体验层** | Web + DApp + 社区 + 3D 展示 |
| **业务层** | 行程 / 订单 / 聊天 / 评论 / 仲裁 |
| **协议层** | Escrow 合约 / 链上事件 / Finality / 对账 |
| **平台层** | AI / 规则 / 配置 / 任务 / 搜索 / 推荐 / 审批 |
| **运行层** | 云部署 / 观测 / 安全 / 审计 / 发布 / 灾备 |

**定位结论**：目标形态不是「普通旅游网站」「普通 Web3 DApp」或「普通后台」的简单叠加，而是接近：

**旅游交易平台 + Web3 托管协议 + AI 行程引擎 + 企业级运营中台** 的混合体。
