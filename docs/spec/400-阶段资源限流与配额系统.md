## 一、文档定位

本文定义 TravelTrust 在 400 阶段的“资源限流与配额系统”开发规范。

400 阶段用于防止单用户或单租户滥用资源拖垮平台，建立统一 quota 与限流治理能力。

## 二、受控资源范围

必须纳管资源：

- AI 调用
- RPC 调用
- API 调用
- 通知发送
- 文件上传
- 查询次数

## 三、系统目标

1. 平台保护：防止异常流量冲垮核心服务。
2. 公平使用：按用户/租户/地区控制资源占用。
3. 成本可控：对高成本调用实施配额策略。
4. 策略可审：限流与配额命中可追踪。

## 四、数据模型（必须具备）

必须具备：

- `quota_rules`
- `quota_usage`
- `rate_limits`
- `throttle_logs`

字段级要求：

- `quota_rules`：`resource_type`、`scope_type`、`quota_limit`、`window`。
- `quota_usage`：`scope_id`、`resource_type`、`used_count`、`window_start`。
- `rate_limits`：`endpoint_or_action`、`qps_limit`、`burst_limit`。
- `throttle_logs`：`scope_id`、`resource_type`、`reason`、`occurred_at`。

## 五、限流与配额策略

### 5.1 多维限流

- 用户级
- 向导级
- 租户级
- IP 级
- 区域级

### 5.2 配额窗口

- 秒级限速
- 分钟级限额
- 日级配额
- 月级预算

### 5.3 处置动作

- 软限流（降级、排队）
- 硬限流（拒绝）
- 风险升级（触发审计或封禁流程）

## 六、核心硬约束

1. Protect Critical Path：核心 API 必须有硬限流。
2. Quota Before Expensive Ops：高成本操作必须先校验配额。
3. Observable Throttling：限流命中必须记录与告警。
4. Configurable Policy：限流配额策略可版本化与回滚。
5. Graceful Degradation：达到阈值时优先降级而非全站崩溃。

## 七、后台模块要求

后台新增一级模块：`配额与限流中心`

子模块（必须）：

- 配额规则
- 使用统计
- 限流策略
- 限流日志
- 异常告警

## 八、实施计划（400 阶段）

### 8.1 P0（必须）

- 建立四张核心表。
- 接入 AI/API/RPC/通知/上传/查询限流。
- 建立命中日志与告警。

### 8.2 P1（增强）

- 动态配额（按风险与信用调节）。
- 跨区域限流协同。

### 8.3 P2（规模化）

- 统一限流网关平台化。
- 智能自适应限流策略。

## 九、发布门禁

1. 核心资源均有配额与限流保护。
2. 高成本调用超限可阻断并可审计。
3. 限流策略演练通过。

## 十、结论

资源限流与配额系统是平台稳定与成本控制底线。没有 400 阶段，单用户滥用即可拖垮全站。
