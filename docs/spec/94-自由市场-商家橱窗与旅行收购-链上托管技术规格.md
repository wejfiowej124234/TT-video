## 1. 背景与目标

### 1.1 背景

自由市场当前包含「旅行预约 / 商家 / 旅行收购」子站入口。需在**不与主 `/market` 订单列表混用业务状态**的前提下，提供：

1. **商家橱窗**：酒店、餐饮、景区等门店以图文视频展示「可成交的旅游相关供给」，并进入与旅游一致的托管支付闭环。  
2. **旅行收购**：收购方发布「悬赏式」跨境带货需求（多媒体 + **自填验货与交割标准**），承接方接单履约，同样进入托管支付闭环。

### 1.2 支付与结算原则（硬约束）

- **结算代币**：**USDT、USDC**（及治理配置的其它 **ERC-20 稳定币**）；以链上 `settlement token` 与订单元数据为准。  
- **资金路径**：与现网一致——用户仅在**订单绑定的 Escrow 合约**上执行 **Approve / Deposit**；**不向平台或对私地址「直接打款」**完成订单（前端文案与 CTA 须与 `frontend/app/pay`、`frontend/locales` 中既有 `pay_*` / `escrow_*` 叙事一致）。  
- **真相源**：链上状态 + 后端投影；UI 以 **`/escrow/:orderId`** 为阶段主引导，**`/pay`** 为枢纽页（与现产品一致）。

### 1.3 非目标（本期可不实现）

- **默认不实现**：将 **「已缴商家/主理人准入费」** 作为 **`POST /api/v1/market/*/listings`** 的 **硬门禁** — 若产品改为 **必须**，**须** 本节升级为 **目标** 并与 **96-18 §11.5**、**04 §3.4**、**93 §8.4** 同批闭合（**当前仍** **未** 绑定）。  
- 法币支付通道、信用卡收单。  
- 平台中央资金池「代持」用户充值余额（与协议定位冲突）。  
- 完全自动化的海关 / 税务 / 跨境合规裁决（仅提供规则入口与人工争议接口）。

**说明**：具体前缀以 **04 §3.4** 登记为准；实现前禁止在多处文档使用互不兼容的 path。

### 2.2 全局 UI 要素

- **钱包连接状态**：子站常驻（与 DApp 分区一致，见 **92**）。  
- **筛选条**：见 **§2.3**（定稿）；与主 `/market` 的 `StickyFilterBar` 心智一致，但数据源为子站列表 API（当前演示数据）。  
- **合规提示条**：一行链到帮助中心 / 对外口径包（**08-4**）；收购页强调禁限带与自负责任。  
- **跳转既有能力**：「我的订单」「支付与托管」链到全站已有路由（见 04 前端路由表）。

### 2.3 子站列表顶栏：国家 / 分类 / 排序（定稿 · 与十国产品期对齐）

**目标**：用户在**不离开首屏认知**的前提下完成「选国 → 选类 → 看结果摘要 → 浏览卡片」；国家列表**仅十国**（与 `frontend/lib/productCountries.ts` → `GET /meta.product_countries` 同源），不出现未开放地区。

#### 2.3.1 垂直顺序（上 → 下）

1. 子站 **Tab**（旅行预约 / 商家 / 旅行收购）— 保持现状。  
2. **筛选主带（建议 Sticky）**：滚动瀑布流时仍可见；高度控制为**一行主控 + 一行 chips**，避免占半屏。  
3. **结果摘要行**（`text-meta`、低对比）：例：`日本 · 餐饮 · 共 1 条`；演示阶段须含「演示数据」提示，与 `market_subsite_filter_summary_line` 叙事一致。  
4. 瀑布流 / 空态（无结果时主带保留，空态区提供 **「重置筛选」**）。  
5. **列表底部收口（1.0.2）**：有结果时，瀑布流下方保留**一行说明 + 次级 CTA**（返回主 `/market`、再进入 DID 榜、条款/争议），避免滚到底「无引导」；实现见 `MarketSubsiteListFooterStrip`。

#### 2.3.2 国家

- **选项集**：十国 ISO（`CN JP KR SG TH AE US AU FR ES`）+ **`all`（全部十国）**。  
- **控件**：桌面端 **横向可滚 pill**（与 Tab 选中态区分：国家略小一号、未选中为半透明白边）；移动端国家过多时同一容器横向滑动。  
- **默认值策略（推荐 B）**：首次进入若 URL **无** `country` 参数，可从 **`localStorage`**（按子站分 key，如 `tt_market_subsite_country_pref_provider`）恢复用户上次选择；若需可分享深链，用户点选后**写回 URL** `?country=JP`。实现上允许「无参 = all」以避免首屏强制跳转闪动。  
- **详情页**：列表进入详情时 **Query 可透传**（`?country=JP&category=dining`）便于返回列表恢复上下文；详情元数据不必依赖 `country`。

#### 2.3.3 分类（两页差异）

| 子站 | 一级分类（chips） | 收入「更多」/ 二期的项 |
|------|-------------------|------------------------|
| 商家橱窗 | `hotel` / `dining` / `attraction` / `experience` | 价格区间（USDC）、标签（亲子/海景等） |
| 旅行收购 | `luxury` / `sneakers` / `electronics` / `health` / `accessories` | 路线方向、悬赏区间、紧急度、是否要求当面验货 |

- **单选 vs 多选（定稿）**：主带 **单选**（含 `all`），降低与分页 API 的组合复杂度；多选留二期或「更多」抽屉。

#### 2.3.4 排序

| 子站 | 选项 |
|------|------|
| 商家 | `recent`（默认，按发布时间或 `sort_key` 降序）、`price_asc`、`price_desc` |
| 收购 | `recent`、`bounty_desc`（按悬赏区间上界或托管意向高价降序） |

#### 2.3.5 URL 与 API 对齐

- **查询键（建议）**：`country`（`all` \| ISO）、`category`（`all` \| slug）、`sort`（上表枚举）。  
- **列表 GET（Target）**：`GET .../listings?country=JP&category=dining&sort=recent&cursor=` — 与 UI 同键，减少映射层。  
- **防抖**：筛选变更 **300ms** 防抖后再请求（演示阶段可仅客户端过滤）。  
- **无障碍**：筛选区域 `aria-label` 区分「服务国家」「品类」；结果数变化可用 `aria-live="polite"`。

#### 2.3.6 视觉（86 / 92）

- 容器：与 `MarketHubSubNav` 同级的 **玻璃横条** — `backdrop-blur`、细边框、`ring-ref-cyan` 轻光；**禁止**在金额/悬赏数字上使用强 glow（**92** 金融态）。  
- 国家选中：青绿渐变 pill，与 Tab 选中**同系但略弱**，避免完全同款。  
- 分类 chips：字号略小于国家；选中为描边 + 浅填充。

#### 2.3.7 列表底部收口（Implemented · 2026-04-20）

- **触发**：商家橱窗 / 旅行收购发现页在**有瀑布流结果**时，于 `MarketSubsiteMasonry` 之后渲染 `MarketSubsiteListFooterStrip`。  
- **内容**：`market_subsite_list_footer_notice`（演示数据口径 + 正式期与链上订单/DID/托管对齐预期）+ **DID 榜** + **返回自由市场** + **条款 / 争议** 文本链（与筛选带上方 CTA 形成「首屏主行动 / 列表尾次行动」分工）。  
- **空态**：无结果时不展示本带，避免与空态内「重置筛选」重复抢注意力。  
- **与主 `/market` 对齐**：主站筛选卡片摘要行在接口异常未关闭提示时追加不可用附注；排序写入 query `sort=latest|priceDesc|priceAsc`；`service` 多值与 `SERVICE_TYPE_OPTIONS` 白名单对齐（防脏 query）。

## 3. 领域模型

### 3.1 实体

| 实体 | 说明 |
|------|------|
| `Shop` | 商家门店：DID / 资质引用、简介、头图、联系方式策略（站内优先）。 |
| `MerchantListing` | 商家橱窗作品：媒体、富文本、价格或询价、服务结构化字段、关联 `Shop`。 |
| `AcquisitionListing` | 收购需求：媒体、富文本、**验货标准**结构化字段、悬赏金额、路线与时间窗、关联发布者。 |

| `Agreement` | 双边协议：版本、哈希、双方确认时间（与 53 一致）。 |
| `EscrowBinding` | 订单与链上 Escrow 实例绑定；阶段与 04 投影一致。 |

### 3.2 `Order` 扩展约定（Target）

- **参与者角色**：收购场景下建议映射为「需求方 ≈ traveler 资金义务方 / 承接方 ≈ guide 履约方」或引入显式 `buyer`/`carrier` 元数据；**须与 87 角色分层文档对读**，避免 UI 文案与 API 枚举冲突。  
- **里程碑模板 ID**：`MERCHANT_DEFAULT` / `ACQUISITION_DEFAULT` 等，驱动 Escrow 释放条件与举证要求（与 19 扩展字段对表）。

## 4. 链上用户旅程（与旅游对齐的 7 步）

以下适用于**商家成交单**与**收购履约单**：

1. **浏览**子站列表。  
2. **打开详情**：阅读多媒体、价格或悬赏、**协议摘要**（收购含验货标准）。  
3. **发起订单**：创建 `Order`，进入协议草稿。  
4. **双边确认协议**：双方签名 / 确认；生成协议版本与哈希展示。  
5. **绑定 Escrow**：部署或绑定合约地址；**仅在本订单 Escrow 详情页提示可充值**。  
6. **钱包 Approve + Deposit（USDC/USDT）**：遵循现有 tx 状态机（见 **35**）。  
7. **履约与里程碑举证 → Release / Dispute**：与旅游一致，争议走现有仲裁链路（**100**、**03**）。

**前端硬规则**：

- 列表页、详情页 **不得** 内嵌「向任意地址转账」；仅 **「打开托管详情」「去支付枢纽」** 等跳转到 **`/escrow/*`** 与 **`/pay`**。  
- **金额展示**：使用等宽数字；明确 **token 符号与链**；与 `pay_pageSubtitle_*` 类文案一致，防止用户提前充值。

| 需求详情 | 媒体画廊、悬赏条（含里程碑预览）、富文本、**「收购标准」大卡**、交割偏好、协议摘要、状态条、主 CTA（接单 / 关闭 / 去托管）。 |

### 6.2 `AcquisitionListing` 建议字段（Target）

**展示与检索**

- `title`, `summary`, `media[]`, `body_md`  
- `origin_region`, `destination_city`、`destination_country_iso`（十国之一，交割/需求方主标国，用于列表筛选）  
- `bounty_min`, `bounty_max`, `currency`  
- `deadline_at`, `urgency`  

**标准（须可映射进订单协议，禁止仅存在于富文本）**

- `inspection_standard`（长文，必填）  
- `authenticity_requirements`（票据、序列号、第三方鉴定等）  
- `condition_requirements`（成色、附件、膜是否可撕等）

- `handoff_preference`（枚举 + 说明）

### 6.3 状态机（业务侧，与 `Order` 联动）

建议枚举：`open` → `negotiating` → `agreement_pending` → `awaiting_deposit` → `escrow_active` → `fulfillment` → `inspection` → `delivery` → `completed` | `cancelled` | `disputed` | `expired`。

UI 须在详情页展示**当前状态**与**下一步唯一主 CTA**（与 Escrow 阶段条对齐）。

### 6.4 里程碑（建议）

示例：`deposit_secured` → `procurement_proven` → `inspection_passed` → `delivery_confirmed` → `release`。  
举证材料类型与 **270**（媒体证据存储）对齐：哈希、版本、可审计访问。

## 7. API 与索引（Target 纲要）

**原则**：新列表/详情接口须走 **04** 版本化与认证约定；不得绕开 RBAC。

建议方向（实现时写入 04）：

- `GET` 子站列表：分页、`cursor`、`country`、`category`、`sort`（与 **§2.3.5** 查询键一致）。  
- `GET` 详情：`listingId` → 聚合 `Shop` / 发布者 DID 摘要。  
- `POST` 从 Listing 创建 `Order`：返回 `order_id` 与下一步 `next`（`agreement` | `escrow` | `pay`）。

## 8. 安全、合规与风控

- **禁限带与跨境**：收购详情固定展示**规则入口**；发布前勾选「已阅读风险提示」（审计日志 **120**）。  
- **反欺诈**：重复发布限制、举报入口、与 **160** 社区治理衔接。  
- **资金区 UI**：遵循 **92**：金额、合约地址、网络切换、交易状态为 **F 区（金融态）**，禁用强装饰动效误导。  
- **链下奢侈品真伪**：平台可插入「验货指引模板」，**不**构成鉴定结论；争议结果以协议 + 仲裁为准。

## 9. 验收标准（节选）

1. **商家**：从橱窗详情可创建订单，经双边确认后，在 **`/escrow/:orderId`** 可见与旅游一致的阶段；可用 USDC/USDT 完成 Deposit（测试网可用既有 mock 路径若存在）。  
2. **收购**：验货标准字段**必填**且写入协议快照；列表卡展示自动生成的一行验货摘要。  
3. **全站一致**：任意支付引导最终落到 **`/pay`** 或 **`/escrow`**，无「私人地址收款」文案漏洞。  
4. **i18n / a11y**：与 **37** 清单一致；关键 CTA 具备 `aria` 与键盘路径。  
5. **观测**：关键转化埋点（`listing_view` → `order_create` → `agreement_signed` → `deposit`）带 `requestId`（**120**）。
