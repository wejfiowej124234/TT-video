## §一、项目整体数据架构概览

### 1.1 数据流总览

```
                    ┌─────────────────────────────────────────────────────────┐
                    │                    后端 (crates/api)                      │
                    │  ┌─────────────┐    启动时 hydrate      ┌──────────────┐ │
                    │  │  PostgreSQL │ ──────────────────────▶│ chain_off    │ │
                    │  │  (真源)     │ ◀──── 双写 (写时)       │ (内存 store) │ │
                    │  └─────────────┘                        └──────────────┘ │
                    │         │                                        │       │
                    │         │ list_* / insert_* / upsert_*           │       │
                    │         └────────────────┬───────────────────────┘       │
                    │                          │                                │
                    │                    API 层 (routes)                         │
                    │   GET/POST orders, discover/orders, itineraries/custom,   │
                    │   orders/:id/messages, community/...                     │
                    └──────────────────────────┬────────────────────────────────┘
                                               │
                    ┌──────────────────────────▼────────────────────────────────┐
                    │                    前端 (Next.js)                         │
                    │   我的订单、自由市场、订单详情、Escrow、聊天、社区、DID榜   │
                    └──────────────────────────────────────────────────────────┘
```

- **DB 为真源**：users, sessions, guides, orders, itineraries, order_messages, reviews, disputes, evidence_receipts；社区表 community_*。
- **启动时**：`hydrate_from_db` 将上述表灌入 chain_off store，供内存读写与 API 响应。
- **写时**：注册/登录、订单创建/状态变更、行程创建/修改、订单消息、评价、争议、证据等均**双写** DB + chain_off（有 `db_pool` 时）。

## §二、后端：双写与 hydrate 现状

### 2.1 启动时 hydrate（DB → chain_off）

`startup/hydrate.rs` 从 DB 读取并灌入 store 的实体：

| 表 | store 键/结构 | 说明 |
|----|----------------|------|
| users | store.users | 用户 |
| sessions | store.sessions (token → user_id) | 会话 |
| guides | store.guides, store.guides_by_user | 向导 |
| orders | store.orders | 订单 |
| reviews | store.reviews (Vec) | 评价 |
| disputes | store.disputes, store.disputes_by_order | 争议 |
| itineraries | store.itineraries (order_id → ItineraryBundle) | 行程 |
| order_messages | store.messages (order_id → Vec<MessageRow>) | 订单聊天 |
| evidence_receipts | store.evidence_receipts | 证据回执 |

### 2.2 写时双写（chain_off → DB）

| 业务动作 | chain_off 实现 | DB 调用 | 说明 |
|----------|----------------|--------|------|
| 注册/登录 | auth | insert_user, insert_session | 已双写 |
| 向导注册/更新 | guides | insert_guide | 已双写 |
| 订单创建/状态变更 | orders, orders_flow, disputes | upsert_order | 已双写 |
| 行程创建（含自定义） | itineraries | insert_itinerary + persist_order_if_db | 已双写（见下节注意） |
| 行程修改（PATCH itinerary） | orders.rs | update_itinerary_snapshot_hash 等 | 需核对是否全量 itinerary 更新落库 |
| 订单消息发送 | messages | insert_order_message | 已双写 |
| 评价提交 | reviews | insert_review | 已双写 |
| 争议裁决 | disputes | update_dispute_resolved | 已双写 |
| 证据上传 | evidence | insert_evidence_receipt | 已双写 |
| 社区发帖/评论/关注/私信 | routes/community | insert_post, insert_comment, insert_follow, insert_dm_message 等 | 社区直接写 DB，不经过 chain_off |

### 2.3 自由市场「可抢订单」数据链

- **API**：`GET /api/v1/discover/orders` → `chain_off::discover_orders_list_impl`
- **逻辑**：从 `store.orders` 中筛 `state == Draft`，并关联 `store.itineraries` 取 destination/city/days 等；支持 country/city 筛选。
- **结论**：自由市场列表与**真实账号创建的 Draft 订单**一致，只要订单与行程已正确落库并 hydrate，即与 DB 同步。前端已去除 MOCK_ORDERS/MOCK_GUIDES 填空，仅展示 API 返回数据。

## §六、自由市场行程与真实账号同步（最佳实践）

### 6.1 当前实现（已满足的）

- **创建入口**：真实账号在 Landing 或自由市场「自定义行程」弹窗提交 → `POST /api/v1/itineraries/custom`（或 POST /itineraries 等）。
- **后端**：`itinerary_custom_create_impl` / `itinerary_create_impl` 会：
  - 在 chain_off store 中插入 `orders` + `itineraries`；
  - 若有 `db_pool`：调用 `persist_order_if_db` 和 `db::insert_itinerary`，将订单与行程写入 DB。
- **发现列表**：`GET /api/v1/discover/orders` 从 store 读 `state == Draft` 的订单并关联 itineraries，即「可抢订单」= 已落库且已 hydrate 的 Draft。
- **前端**：已去除 MOCK_ORDERS、MOCK_GUIDES；仅展示接口返回数据，空即空。

### 6.2 最佳实践（落库）

| 步骤 | 建议 |
|------|------|
| 1. 订单与行程同事务或同批次写 | 当前为「先写 store，再 persist_order + insert_itinerary」；若需强一致，可考虑 DB 事务包住 orders + itineraries 插入。 |
| 2. Draft 订单的 guide_id | 当前自定义行程创建时 `guide_id = Uuid::nil()`；而 `orders.guide_id` 为 NOT NULL REFERENCES guides(id)。**55 需处理**：要么引入「占位向导」行（如系统向导）并写入其 id，要么 DDL 允许 guide_id 可空（并兼容 discover 筛选逻辑）。否则有 db_pool 时 upsert_order 可能因外键失败。 |
| 3. 启动时 hydrate 顺序 | 保持先 users/sessions → guides → orders → itineraries → order_messages，避免外键与关联缺失。 |
| 4. 前端不缓存假数据 | 已实现：API 返回空则展示空；错误时展示错误态并可重试。 |

### 6.3 55 需闭环的缺口

- **Draft 订单 guide_id 落库**：明确方案（占位向导 vs. 可空）并实现，确保 `persist_order_if_db` 在自定义行程创建时成功。
- **PATCH itinerary 全量写回**：若当前仅更新 snapshot_hash，需确认「行程日表/amount_breakdown」是否也写回 DB；若否，补充 update_itinerary 或等价写回。

### 8.6 八附续成文补充（G6/O8/O9/O11）

以下为 §八附续 缺口与优化项的**成文约定**，便于发版前勾选与后续实现对齐。

**G6 订单/发现列表分页**：**已闭环（55-S12 扩展）**。`GET /api/v1/orders`、`GET /api/v1/discover/orders` 支持**可选** **limit**、**cursor**（`crates/api/src/chain_off/pagination.rs`）；传 `limit` 或仅传 `cursor`（默认每页 50）时响应含 **page** `{ limit, next_cursor, has_more }`，排序 **`updated_at DESC, id DESC`**；**不传 limit 且不传 cursor** 时保持历史 **全量**（Discover 全量按 **created_at** 倒序）。契约单源 **04 §3.4**；社区 Feed、conversations 等分页仍见 04 表。

**O8 hydrate 部分失败策略**：`startup/hydrate.rs` 当前行为——**关键表**（users、sessions）：`map_err` 失败即整体返回 Err，**启动失败**。**可降级表**（guides、orders、reviews、disputes、itineraries、order_messages、evidence_receipts）：`if let Ok(...)` 加载，单表失败时**跳过并继续**，不阻断启动。建议：关键表失败时打错误日志并快速失败；可降级表失败时打 warning 并记录表名，便于监控与告警（09/Runbook 可引用本约定）。

**O11 55 与 04/53 变更同步规则**：55 阶段或后续凡涉及 **API 路由、表结构、订单/状态约定** 的变更，须**同步更新**：[04-后端与API](04-后端与API.md) §3.4、[53-阶段开发技术文档](53-阶段开发技术文档.md) 附录 A/B/C（含错误码、状态、路由）。以 **04/53 为契约单源**；与 53 文档 N7「附录与 04 同步机制」一致。新增迁移须同步更新本文 §1.2、04-数据库架构、41 接库范围（O10）。

```bash
# 根路径：健康 / 元数据 / 指标（快速验收与 smoke 脚本已覆盖）
curl -s -o /dev/null -w "%{http_code}\n" "BASE/health"
curl -s "BASE/meta" | jq '.service, .api_version, .strict_mode.strict_session_gate'
curl -s "BASE/metrics" | head -n 5

# 55-S10 / G1：反馈列表（需登录）
curl -s -H "Cookie: <session>" "BASE/api/v1/community/feedback" | jq '.status, (.items | length)'

# 55-S12 / G1：发现列表（可无登录，返回可抢订单）
curl -s "BASE/api/v1/discover/orders" | jq '.status, (.items | length)'

# 55-S12：发现列表分页（limit=1 时须含 page）
curl -s "BASE/api/v1/discover/orders?limit=1" | jq '.status, .page.limit, .page.has_more, (.items | length)'

# G1：DID 行程榜
curl -s "BASE/api/v1/did-rank/itineraries" | jq '.status, (.itineraries | length)'

# 31 / 04 §3.4：话题帖子数（合法 tag；无 DB 时 post_count 可为 0）
curl -s "BASE/api/v1/community/stats/posts-by-tag?tag=smoke" | jq '.status, .post_count'

# 55-S7：无 DB 时依赖 DB 的路由应返回不可用（不设 DATABASE_URL 启动 API 后）
curl -s "BASE/api/v1/community/feed" | jq '.message // .status'
```
