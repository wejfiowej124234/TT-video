## 一、行业标准符合度

### 1. 身份与资质

| 项目 | 行业常见要求 | 当前实现 | 符合度 |
|------|--------------|----------|--------|
| 身份凭证 | 护照/身份证等政府签发证件 | ✅ 统一要求护照、护照号、真实姓名 | 基本符合 |
| 证件影像 | 证件照上传供核验 | ✅ 注册页与向导申请页均可上传护照照片、语言证明；提交前先 `upload-doc` 落库，再随 `postGuide` 提交 URL | 符合 |
| 向导资格 | 部分地区要求向导证、培训合格 | ⚠ 可选 **`guide_license_url`**（API + DB）；是否强制必传由产品/合规定稿 | 待产品决策 |
| 语言能力 | 国际接待常要求英语等证明 | ✅ 可选语言能力证明上传，提交后以 language_cert_url 落库供审核 | 符合 |

### 2. 数据与隐私

| 项目 | 行业/合规常见要求 | 当前实现 | 符合度 |
|------|-------------------|----------|--------|
| 隐私同意 | 收集敏感信息前明确同意 | ✅ 已增加「同意隐私政策与服务条款」勾选 | 符合 |
| 敏感数据存储 | 加密、访问控制、保留期限 | 后端已接收 DID 字段：护照号 Keccak256 哈希存储、姓名与钱包落库；证件照经 upload-doc 落库。前端 session 仅用于注册/申请页预填，提交后清空。访问控制与保留期限待合规定稿。 | 部分符合 |
| 证件照持久化 | 需安全存储并供审核 | ✅ 已实现：`POST /api/v1/guides/upload-doc` 写入 data/guide_uploads，返回 url；提交向导时传 id_photo_url/language_cert_url | 符合 |
| 数据最小化 | 仅收集业务必需项 | ✅ 字段有明确用途说明 | 符合 |

### 3. 流程与体验

| 项目 | 说明 | 当前实现 |
|------|------|----------|
| 注册→登录→提交 | 先账号、再 DID/向导信息、登录后提交 | ✅ 流程清晰 |
| 未登录提示 | 避免填完才报错 | ✅ 向导申请页有登录态检查与禁用提交 |
| 钱包格式 | 避免无效地址 | ✅ 前端已做 0x+40 位十六进制校验 |

## 二、DID 维度问题与缺口

### 1. DID 主体与绑定

| 项目 | DID 常见要求 | 当前实现 | 问题 |
|------|--------------|----------|------|
| 主体标识 | DID 应以「用户控制的标识」为主体（如链上地址） | 收集钱包地址，标注为「链上 DID」 | ✅ 概念正确 |
| 绑定关系 | 账号/身份与 DID（钱包）的绑定应可验证 | ✅ 后端 `postGuide` 已接收并存储 wallet_address、real_name、passport_number（哈希），实现账号↔向导 DID 绑定；链上 DID Document 仍待建设 | 基本符合 |
| 控制权 | 私钥/钱包由用户控制，平台不托管 | 仅收集地址，不触达私钥 | ✅ 符合 |

### 2. 身份声明 vs 可验证凭证（VC）

| 项目 | DID/VC 标准 | 当前实现 | 问题 |
|------|--------------|----------|------|
| 声明来源 | 真实世界 DID 通常依赖第三方签发之 VC（如 KYC） | 姓名、护照号、钱包均为用户自填，无签发方 | ❌ 属自声明，非「可验证凭证」，第三方无法验证 |
| 凭证存储 | VC 可存链上或可验证存储，供依赖方校验 | 无 VC 结构，无签发方签名 | ❌ 不符合 VC 模型 |
| 最小化披露 | 尽量不存明文证件号，用零知识证明或哈希 | 护照号后端仅存 Keccak256 哈希；姓名/钱包落库供审核与绑定；前端 session 预填后提交即清空 | 部分符合（护照号已哈希；姓名/钱包业务必需落库，合规待定稿） |

### 3. 链上与 DID Document

| 项目 | 说明 | 当前实现 |
|------|------|----------|
| DID 解析 | DID 对应 DID Document（含 verificationMethod 等） | 未实现 DID 解析或 DID Document 生成/更新 |
| 链上锚定 | 将 DID 或凭证哈希上链（如 Polygon） | 未实现；需合约或链上服务配合 |
| 钱包与 DID | 用钱包地址生成 did:polygon 或 did:eth 等 | ✅ 前端已展示等效 DID：`did:ethr:0x…`（EVM/Polygon 通用）；连接钱包可一键填入地址并校验一致 |

### 4. 小结：对 DID 来说的已闭合与剩余缺口

1. **DID 绑定** ✅：后端已接收并存储 wallet_address、real_name、passport_number（哈希），账号↔向导 DID 绑定已实现；链上 DID Document 仍待建设。
2. **纯自声明**：无 KYC/第三方签发，无法达到「可验证身份」的 DID/VC 标准（P1 改进）。
3. **敏感数据**：护照号仅存哈希；证件照与证明经 upload-doc 落库；访问控制与保留期限待合规定稿。
4. **链上未参与**：无 DID 注册、无 VC 上链、无 DID Document，与「链上 DID」目标尚有距离（P1）。

## 三、已做的前端改进（本轮）

- 钱包地址格式校验：0x + 40 位十六进制（EVM/Polygon）；**注册页与向导申请页（/guide/register）均校验**，提交前校验并提示格式错误。
- 申请向导提交前必须勾选「同意《服务条款》与《隐私政策》」，并说明 DID/护照信息用途；**注册页「申请向导」与向导申请页（/guide/register）均提供该勾选**，本页未勾选时禁用提交并提示。
- **向导申请页（/guide/register）**：已扩展 DID 字段与证件上传。本页**始终展示**真实姓名、护照号、钱包地址（**链上 DID 主标识**，区块内顺序为：钱包 → 真实姓名 → 护照号）；支持本页直接上传护照照片、语言能力证明（选填，&lt;800KB，先 `postGuideUploadDoc` 再随 `postGuide` 提交 URL）；若从注册页「申请向导」跳转而来，可预填 session 中的 DID 与已选证件。提交时发送 city、country_code、languages、service_types、bio、wallet_address、real_name、passport_number、id_photo_url、language_cert_url（与后端扩展一致）。
- **DID 逻辑与体验**：① 页顶**「关于链上 DID」**说明：链上 DID = 钱包地址，作为向导主标识，用于接单与托管签名。② **连接钱包**：集成 wagmi `useAccount`，已连接时显示「使用当前钱包」按钮一键填入地址；若填写地址与当前连接一致则显示「与当前连接的钱包一致」。③ **等效 DID 展示**：钱包格式有效时展示 `did:ethr:0x…`（EVM/Polygon 通用），并提供「复制地址」按钮。④ **同意文案**：勾选文案明确「钱包地址将作为链上 DID 与向导身份绑定（用于接单与托管签名），护照/姓名等将用于资质审核；平台不托管私钥」。

## 五、钱包与账号体系（多钱包 / 换绑 / 向导 vs 游客）

### 5.1 当前设计（写死）

| 概念 | 说明 |
|------|------|
| **账号** | 一个邮箱 = 一个账号；登录后同一套**个人中心**（`/me`），无「向导账户」与「游客账户」两套系统。 |
| **个人中心「绑定钱包」** | 账号级 **一个** 默认钱包（`users.default_wallet_address`），可在 `/me` 中**更换**；用于展示与（产品可约定）游客下单时默认使用的钱包。 |
| **向导链上 DID** | 申请向导时填写的**一个**钱包地址（`guides.wallet_address`），与向导身份绑定；**接单、托管签名、链上身份**均以此为准。可与账号「绑定钱包」不同。 |
| **多钱包** | 当前**不支持**一个账号绑定多个钱包或一个向导身份多个 DID；账号一个 default_wallet，向导一个 wallet_address。 |
| **换绑** | 账号可在个人中心换绑 default_wallet；**已支付订单的签名钱包不可变更**（01 12 缝 #11）。向导身份申请时填写的 DID 当前实现**不可在页面上换绑**（后端无更新向导钱包接口）；若需支持，须新增 API 并遵守「已支付订单归属不变」等约束。 |

### 5.2 向导 vs 游客

- **同一套账户**：向导与游客使用同一登录（邮箱）、同一 `/me` 个人中心。
- **角色**：通过「游客注册」或「申请向导」区分；个人中心按角色展示不同统计（游客：订单/消费/评价；向导：接待单数/完成单数/总收入/评分）。
- **向导登录后**：仍用同一账号；接单与托管签名使用**申请向导时填写的钱包地址**（向导 DID），非个人中心「绑定钱包」必填。

### 5.3 申请向导页说明

- 页上已说明：此处为**向导身份**的链上 DID，**仅一个钱包地址**；可与个人中心「绑定钱包」不同，接单与托管以本页填写的向导 DID 为准。
- 若用户已是向导再次提交：后端返回 `409 already_guide`，前端展示「您已是向导，无需重复申请」并引导至向导列表/个人中心。

## 六、结论

- **行业标准**：身份材料（护照、照片、语言证明）和隐私同意已基本对齐；证件照与证明已持久化；**向导证/资格证**可为可选 **`guide_license_url`**。**剩余缺口**：① 是否强制上传向导证（产品/合规）；② 敏感数据访问控制与保留期限等合规策略（待法务/合规定稿）；③ 防机器人（人机验证或风控接口，待接入）。  
- **DID**：前端已强化 DID 主标识（钱包首位）、「关于链上 DID」说明、连接钱包填入、等效 did:ethr 展示与复制、同意文案明确绑定与不托管私钥；后端已接收并绑定 wallet/real_name/passport。仍缺可验证凭证（KYC/VC）、链上锚定与 DID Document，需从链上与合规能力补齐。  
- **钱包与账号**：见 §五；账号一个默认钱包（可换绑）、向导一个 DID 钱包（申请时确定）；同一套账户服务向导与游客，无两套独立系统。

## 八、与 DApp 同步数据符合性检查

**标准依据**：[01-总库总览](01-总库总览.md) §9、[04-后端与API](04-后端与API.md) 开篇、[05-前端总览](05-前端总览.md) §二、[06-DApp架构总览](06-DApp架构总览.md) §二：**业务数据唯一数据源 = 后端 API**，Web 与 DApp **共用同一套 API**（同一 `lib/apiClient.ts` + `lib/api.ts`），不因是否连接钱包而分源或分缓存。

### 8.1 符合项

| 检查项 | 结论 | 说明 |
|--------|------|------|
| 注册/登录/向导/订单/me 数据来源 | ✅ 符合 | 前端统一经 `apiClient` 调 04 路由；注册 `postRegister`、向导 `postGuide`、订单 `getOrder`/`getOrders`、个人中心 `getMe`/`putMe` 均走 API，无单独 DApp 数据源 |
| Escrow 页业务数据 | ✅ 符合 | Escrow 详情页使用 `getOrder(escrowId)` 从 API 获取订单（id 为订单 UUID），行程/接待人/状态以 API 为准；链上负责支付/质押/**release**/openDispute 等签名；链下「确认行程完成」见 API（04 §3.4） |
| 游客注册与钱包 | ✅ 符合 | 游客注册仅提交 email/password/nickname（04 与 §五 一致）；`default_wallet_address` 在个人中心 `/me` 绑定与更新，DApp 连钱包后可与该字段一致 |
| 向导 DID 落库 | ✅ 符合 | 申请向导时 `wallet_address` 等经 `postGuide` 写入 API/DB，与 04、§五「向导链上 DID 以 guides.wallet_address 为准」一致 |

### 8.2 与 DApp 同步相关项（已闭合）

| 问题 | 状态 | 说明 |
|------|------|------|
| **向导接单及须钱包操作与 DID 一致** | ✅ 已实施 | GET /api/v1/me 返回当前用户 `guide.wallet_address`；订单详情页（EscrowDetail）接单及 **release / 意向签名等须链上钱包** 的操作前校验「当前连接钱包 === 向导 DID」，不一致时禁用按钮并提示（与前端 i18n `escrow_guideWalletRequired` 一致）。纯链下 API 路径以 04 §3.4 为准。 |
| **个人中心「绑定钱包」与当前连接钱包一键同步** | ✅ 已实施 | 个人中心增加「使用当前连接钱包」按钮（已连接钱包时显示），点击后 `putMe({ default_wallet_address })` 并刷新；编辑资料时提供「填入当前钱包」快捷填入。 |
| **注册时可选填 default_wallet** | ✅ 已实施 | 后端 `POST /auth/register` 支持可选 `default_wallet_address`（0x+40 位十六进制）；游客注册页增加「默认钱包（可选）」输入，提交时校验格式并写入账号。 |

### 8.3 小结

- **业务数据同源**：申请向导、注册游客、订单、向导、me 均以 API 为唯一数据源，Web 与 DApp 共用同一 API，**符合 01 §9、04/05/06 约定**。
- **与 DApp 钱包一致性**：§8.2 三项已全部落地；§七 身份/合规/DID/防机器人仍按原表执行。
