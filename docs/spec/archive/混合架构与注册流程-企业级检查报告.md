## 一、混合架构符合性

### 1.1 运行模式（链上 / 链下 / 混合）

| 项 | 04 §四 约定 | 当前实现 | 结论 |
|----|-------------|----------|------|
| 业务层（注册/登录/向导/订单/争议等） | **始终可用**，不依赖 P3_CHAIN_OFF | `ChainOffState` 始终创建；路由始终挂载；无 DB 时用内存 Store | ✅ 符合 |
| mock-pay | 仅 `P3_CHAIN_OFF=1` 时开放 | `order_mock_pay` 内检查 `P3_CHAIN_OFF==1`，否则 501 | ✅ 符合 |
| 用户等相关数据落库 | `DATABASE_URL` 设置时建池、迁移、双写 + 启动 hydrate | 已实现：users/sessions 迁移、db 模块、auth 双写、启动时 hydrate 到 chain_off | ✅ 符合 |
| 无 DB 时 | 沿用内存 Store，便于本地跑通 | 未设 `DATABASE_URL` 时 `db_pool=None`，不迁移、不 hydrate、不双写 | ✅ 符合 |

**结论**：混合架构实现与 04 §四 一致；业务接口不依赖 P3_CHAIN_OFF，仅 mock-pay 受控；用户/会话可落库并回填内存。

### 1.2 数据一致性风险（需关注）

| 风险 | 说明 | 建议 |
|------|------|------|
| 无 `DATABASE_URL` 时 | 业务数据主要在**内存** Store；重启后清空（除未接 DB 时的会话策略） | 生产/预发应配置 **DATABASE_URL**；见 04 §四、41、[55](../55-阶段-数据同步与数据库功能同步.md) |
| 有 `DATABASE_URL` 时 | **users/sessions/guides/orders/reviews/disputes** 等已按迁移 **双写 + 启动 hydrate**（与 04 附录 DDL、chain_off 一致） | 重启后数据保留；双写失败策略仍见下行与 Runbook §9 |
| 双写失败仅打日志 | auth_register/auth_login 写 DB 失败时 `eprintln!`，不改变 HTTP 响应；可能出现「内存有、DB 无」 | 可选：DB 写失败时返回 503 或写审计日志+告警；或保持现状并在 Runbook 中注明「双写失败需人工核对」 |
| 鉴权与会话（**2026-03 已演进**） | 有 DB：登录/注册签发不透明 **`tts_*`**；`extract_user_with_session_check` 在 DB 模式下 **仅**认 **sessions** 表，**带无效 Bearer 时不回退** `X-User-Id`；前端 **`traveltrust_session_token`** + Bearer。无 DB：内存 `sessions` + 仍可用 `X-User-Id` / `bearer_<user_id>` 联调。 | 权威口径：[65-企业级审计 §三·S1](../65-企业级审计-剩余问题与缺口-20250228.md)、`state.rs`、`.env.example`；生产建议 **`STRICT_SESSION_GATE=1`** |

## 二、注册旅行者（业务逻辑与正常使用）

### 2.1 流程梳理

- **前端**：`/auth/register` 选「旅行者注册」→ 填邮箱、密码、确认密码、昵称（可选）→ `postRegister({ email, password, nickname })` → 成功跳转 `/auth/login`。
- **后端**：`POST /auth/register` → `chain_off::auth_register`：邮箱唯一性（不区分大小写）、写入 user + session（内存 + 可选 DB），返回 `user_id`、`token`、`role`。
- **登录态**：前端注册后**不自动登录**，需到登录页再输入邮箱密码；登录成功后将 `user_id` 与 **`token`** 经 `applyClientSessionAfterAuth` 写入 **`traveltrust_user_id`** 与 **`traveltrust_session_token`**；`getAuthHeaders()` **优先** `Authorization: Bearer <token>`（有 DB 时须带 token；无 token 时仍可回退 `X-User-Id` 过渡）。见 `frontend/lib/apiClient/core.ts`、`auth.ts`。

**结论**：流程为「注册 → 登录 → 使用」，符合常规账号体系；与 04 §三 3.1 邮箱注册一致。

### 2.2 缺口与问题

| 编号 | 维度 | 发现 | 严重程度 | 建议 |
|------|------|------|----------|------|
| T1 | 安全 | **后端无邮箱格式校验**：任意字符串均可注册 | 中 | 后端对 email 做格式与长度校验（或与前端一致正则），非法返回 400 |
| T2 | 安全 | **后端无密码强度与长度校验**：当前为明文 `hash:${password}` 占位存储 | 中 | 至少长度≥8、禁止超长；上线前改为 bcrypt/argon2 等安全哈希 |
| T3 | 安全 | **注册接口无幂等键**：重复提交可造成多次注册尝试（邮箱唯一会 409，但消耗资源） | 低 | 若生产启用 `REQUIRE_IDEMPOTENCY_KEY`，前端 POST /auth/register 传 Idempotency-Key |
| T4 | 体验 | 前端有 `passwordStrength` 提示，但**未强制至少 8 位**即允许提交 | 低 | 前端提交前校验密码≥8 位（及与 04/产品约定一致），与后端规则同步 |

## 三、注册向导（业务逻辑、DID、正常使用）

### 3.1 流程梳理

- **路径一（推荐）**：用户先**旅行者注册** → **登录** → 进入 `/guide/register`（需登录）→ 填城市、DID/钱包、姓名、护照、证件等 → 上传证件 → `postGuide(...)` 带 `X-User-Id` → 成功即「已是向导」。
- **路径二**：在 `/auth/register` 选「申请向导」→ 填旅行者信息 + 向导必填项 → 提交后先 `postRegister`，再把 pending 数据存 sessionStorage → 跳转 `/auth/login?returnUrl=/guide/register` → 用户**登录后**进入 `/guide/register`，从 sessionStorage 恢复表单 → 再提交 `postGuide`。

**结论**：两条路径均满足「先有账号、再以该账号申请向导」；向导注册需登录，与 04 §三 POST /api/v1/guides 需登录一致。业务逻辑正确，可正常使用。

### 3.2 DID 与向导绑定

| 项 | 04 / 01 约定 | 当前实现 | 结论 |
|----|--------------|----------|------|
| 向导 DID（wallet_address） | 申请向导时可提交；与账号绑定 | 存于 `GuideRow.wallet_address`；`user_id` 绑定向导行 | ✅ 符合 |
| 格式 | 与 EVM/Polygon 一致 | 后端 `guide_create_impl` 校验 0x+40 位十六进制；非法返回 400 invalid_wallet_address | ✅ 已修复（审计 F1） |
| 必填 vs 可选 | 04 §二 为「可选提交」 | 后端、前端均为可选；若业务要求「向导必须有 DID」需产品定稿后改为必填并校验 | ⚠️ 待产品定稿 |
| 等效 DID 展示 | did:ethr 等 | 前端 `walletToDidEthr` 展示 `did:ethr:0x…` | ✅ 符合 |

### 4.2 正常使用场景

- **仅旅行者**：注册 → 登录 → 浏览向导、下单（需有向导数据；无链时可 mock-pay）、个人中心。✅ 可跑通（需至少一名向导或测试数据）。

## 八、旅行者注册后能否正常使用

**结论：可以。** 按下面流程即可正常使用旅行者能力。

### 8.1 推荐流程

1. **注册**：打开 `/auth/register` → 选「旅行者注册」→ 填邮箱、密码（至少 8 位）、确认密码、昵称（可选）→ 提交。
2. **登录**：注册成功会跳转到 `/auth/login`，用同一邮箱和密码登录 → 登录成功后会把 `user_id` 写入本地，并跳转到个人中心 `/me`（或 `returnUrl`）。
3. **之后**：个人中心、浏览向导、下单、我的订单等请求由 `getAuthHeaders()` 自动带 **`Authorization: Bearer`**（有 token 时）或 `X-User-Id`（过渡），可正常使用。

### 8.2 依赖环境

| 场景 | 说明 |
|------|------|
| **无 DB** | 不设 `DATABASE_URL` 时，用户/向导/订单都在内存。**重启后数据清空**，需重新注册；适合本地联调。 |
| **有 DB** | 设置 `DATABASE_URL` 后，用户、会话、向导、订单、reviews、disputes 等按实现落库并 hydrate。重启后仍可登录，**可长期正常使用**。 |
| **支付** | 旅行者下单后要进入「已托管」状态：本地无链时设 `P3_CHAIN_OFF=1` 用 mock-pay；有本地链则走真实链上支付。 |

### 8.3 已修复的体验

- 注册 409「邮箱已注册」：前端已映射为「该邮箱已注册，请直接登录」。
- 邮箱/密码格式错误：前端有长度与格式校验，后端返回明确错误码并已做中文提示映射。
