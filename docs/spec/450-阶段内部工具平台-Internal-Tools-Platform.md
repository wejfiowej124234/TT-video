## 一、文档定位

本文定义 TravelTrust 在 450 阶段的“内部工具平台”开发规范。

450 阶段用于集中承载运维、调试、修复、导出等内部能力，避免把大量临时工具堆进 Admin 主后台。

## 二、建设背景

后期必然出现大量内部工具需求：

- 修复订单
- 重跑任务
- 手动触发
- 导出数据
- 生成报表
- 调试接口
- 模拟用户

如果全部硬塞进 Admin，会导致权限混乱、流程污染和维护成本上升。

## 三、核心能力（必须具备）

必须具备：

- `internal tools`
- `ops tools`
- `debug tools`
- `scripts ui`

## 四、系统目标

1. 工具集中治理：内部工具统一入口与权限体系。
2. 高风险动作可审：所有修复与手工动作有审计证据。
3. 操作可回滚：关键工具动作可撤销或补偿。
4. 运维可提效：常见故障工具化、脚本化、界面化。

## 五、数据模型建议

建议最小实体：

- `internal_tools`
- `tool_actions`
- `tool_run_jobs`
- `tool_run_logs`
- `tool_permission_policies`
- `tool_audit_logs`

字段级要求：

- `internal_tools`：`tool_id`、`tool_name`、`tool_type`、`status`。
- `tool_actions`：`tool_id`、`action_code`、`risk_level`、`requires_approval`。
- `tool_run_jobs`：`job_id`、`tool_id`、`action_code`、`status`、`started_at`。
- `tool_audit_logs`：`actor_id`、`tool_id`、`action_code`、`input_digest`、`result_digest`。

## 六、后台模块要求

后台新增一级模块：`内部工具平台`

子模块（必须）：

- 工具目录
- 运行控制台
- 任务重跑
- 数据导出
- 调试面板
- 操作审计

## 七、实施计划（450 阶段）

### 7.1 P0（必须）

- 上线工具目录与统一执行入口。
- 覆盖订单修复、任务重跑、数据导出三类核心工具。
- 落地工具级 RBAC 与审计日志。

### 7.2 P1（增强）

- 脚本 UI 化与参数模板化。
- 高风险操作审批流接入。

### 7.3 P2（规模化）

- 工具插件化扩展。
- 运维自动化编排与 runbook 联动。

## 八、发布门禁

1. 核心内部操作不再依赖手工命令散落执行。
2. 高风险动作具备审批与审计链路。
3. 工具执行失败可追踪、可恢复、可复盘。

## 九、结论

内部工具平台是企业级运行效率与安全治理关键层。没有 450 阶段，运维能力会长期碎片化。
