### 2.6 深度多维度检查

对 §2.3 问题从**数据/API、前端展示、交互、视觉与规范、可访问性、后端逻辑、测试与回归、文档与契约**八维度做检查；**发布前必查以 §五 为准**，本节供迭代查漏。

#### 2.6.1 检查维度说明

| 维度 | 说明 | 检查要点示例 |
|------|------|----------------|
| **数据/API** | 接口契约、字段、去重、错误码 | 列表是否去重、GET order 是否含 images/attractions、删除接口是否存在 |
| **前端展示** | 渲染逻辑、空态、加载态 | 有数据时是否展示图、无数据时占位是否合理、列表是否重复渲染 |
| **交互与状态** | 按钮、表单、状态流转 | 删除后是否跳转/刷新、禁用态是否可见、输入是否可读 |

#### 2.6.3 跨问题共性结论

- **对比度与 a11y**：P54-001、003、004、006 均涉及「深底浅字、浅底深字」；整改时建议统一过一遍订单详情与列表内所有文本与输入，并做一次对比度与焦点检查。
- **删除/取消能力**：P54-005、008 依赖同一套 04 删除/取消 API 与 01/03 业务规则；建议后端先落契约与状态约束，前端再接详情+列表两处入口。
- **数据源与去重**：P54-009 需前后端同时约束：后端列表去重或发布唯一，前端禁止用首页同一 order_id 多卡充当市场列表。
- **TT 社区与权限**：P54-019 依赖反馈/提议 API 与官方账号权限；实现时需在 04 或新 API 中明确「仅官方可标记状态/置顶/关闭」，避免越权。
