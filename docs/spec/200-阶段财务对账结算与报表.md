## 一、文档定位

本文定义 TravelTrust 在 200 阶段的“财务、对账、结算与报表”开发规范。

Escrow 只解决托管与链上执行，不自动等于财务闭环。200 阶段要把“链为准、DB 为投影”落到可运行的财务系统，避免后台仅有看板而缺乏可核验账实一致能力。

## 二、系统目标

200 阶段目标是形成“链上资金真相 + 财务账本投影 + 结算执行 + 报表审计”的闭环：

1. 链上资金可对账：链上事件和财务账本持续一致。
2. 平台抽成可核验：费率、金额、时间点可追溯。
3. 向导收益可结算：应结、已结、待结、冻结状态清晰。
4. 退款账务可闭环：全额/部分退款在财务分录可复算。
5. 异常资金可处置：差异归因、修正、复算、审批全留痕。
6. 报表可审计导出：财务报表和审计证据一键导出。

## 三、范围定义（六大模块）

### 3.1 链上资金对账系统

核心能力：

- 以链上事件作为资金真相源，DB 为投影账本。
- 对账频率支持实时轻量与周期全量。
- 对账维度覆盖订单、Escrow、币种、金额、状态、时间窗口。
- 支持 reorg 与 finality 处理后的重放对账。

最小要求（P0）：

- 每个结算相关订单必须具备链上事件轨迹和账本轨迹。
- 对账任务失败必须告警并生成可追踪工单。

验收要求：

- 支持对账批次重算并输出差异清单。
- 差异处置后可二次复算并归档证据。

### 3.2 平台抽成与费率核算

核心能力：

- 平台费率配置版本化（含生效时间、环境、审批记录）。
- 抽成金额按订单与结算事件精确计算。
- 多币种最小单位精度一致，禁止浮点误差核算。
- 历史订单按确认时费率回放，避免追溯漂移。

最小要求（P0）：

- 每笔订单可追溯费率来源、计算公式、计算结果。
- 费率变更后必须触发回归核验任务。

验收要求：

- 平台抽成总账与订单明细可双向钻取。
- 支持按日/周/月、国家、币种、业务线统计。

### 3.3 向导收益结算系统

核心能力：

- 向导收益台账：应结金额、已结金额、冻结金额、扣减金额。
- 结算周期管理：T+N 周期、手动补结、异常挂起。
- 结算单状态机：待生成、待复核、待执行、已完成、已驳回。
- 与争议结果联动：仲裁后自动更新向导收益。

最小要求（P0）：

- 每笔向导收益必须绑定来源订单与链上事件。
- 结算执行必须满足审批与权限约束。

验收要求：

- 可按向导维度导出结算单与流水明细。
- 支持按结算批次回放与复核。

### 3.4 退款账务系统

核心能力：

- 支持全额退款、部分退款、争议裁决退款。
- 退款分录自动生成并与原订单分录关联。
- 退款状态与链上执行状态同步。
- 退款失败重试与人工介入流程清晰。

最小要求（P0）：

- 退款分录必须包含原始订单、退款原因、执行凭证。
- 退款不得造成双重结算或负向资损遗漏。

验收要求：

- 退款账务可按订单链路完整回放。
- 退款报表可按原因、国家、币种分组统计。

### 3.5 异常订单资金核对系统

核心能力：

- 异常分类：链有账无、账有链无、金额不一致、状态不一致、重复分录。
- 自动归因：索引延迟、重组回滚、执行失败、人工误操作、配置误发布。
- 处置流程：冻结、修正、复核、解冻、归档。
- 修正规则版本化并可审计。

最小要求（P0）：

- 每个异常单必须有 owner、SLA、处置路径与结果。
- 人工修正必须走审批，且不得覆盖原始记录。

验收要求：

- 异常关闭率、平均处置时长、重复异常率可观测。
- 关键异常具备事故复盘模板与结论留档。

### 3.6 财务报表与审计导出系统

核心能力：

- 财务主题报表：交易流水、平台抽成、向导结算、退款、异常处置。
- 审计导出：按时间段导出账本、批次、审批、操作日志、对账差异。
- 报表口径治理：指标定义、版本、发布记录可追溯。
- 导出文件可签名、防篡改校验。

最小要求（P0）：

- 报表与对账结果必须同口径。
- 审计导出支持 CSV/JSON，并带批次元数据。

验收要求：

- 监管/审计抽样订单可在限定时间内完成全链路举证。
- 报表与账本、链上事件可三方校验一致。

## 四、核心硬约束（必须写死）

1. Chain Is Source：资金终态以链上事件为唯一真相源。
2. DB Is Projection：财务 DB 仅为投影账本，必须可重建。
3. Reconciliation Is Mandatory：无对账通过不得进入财务结算确认。
4. No Silent Correction：任何修正不得静默覆盖，必须留痕与审批。
5. Fee and Settlement Versioning：费率与结算规则必须版本化可回放。
6. Audit Export Ready：关键报表与审计证据必须可导出可验签。

## 七、权限模型（最小角色）

建议最小角色集（与 `70` 对齐）：

- `FINANCE_VIEWER`
- `FINANCE_OPERATOR`
- `RECON_MANAGER`
- `FINANCE_AUDITOR`

200 扩展能力标签（不替代 70 主角色）：

- `FINANCE_SETTLEMENT_MANAGER`（结算域动作标签）

与 `70` 角色体系映射（统一口径，避免双轨 RBAC）：

| 财务治理角色 | 70 角色主映射 | 说明 |
|---|---|---|
| `FINANCE_VIEWER` | `Finance`（viewer）/`Auditor`（只读） | 仅读摘要、报表、差异列表 |
| `FINANCE_OPERATOR` | `Finance` | 可触发对账与修正草稿，不可直接生效 |
| `RECON_MANAGER` | `Finance`（受控） | 可发布对账域处置结果，需审批 |
| `FINANCE_SETTLEMENT_MANAGER` | `Finance`（受控） | 仅结算域动作标签，受 70 主角色约束 |
| `FINANCE_AUDITOR` | `Auditor` | 只读审计导出，不可写配置 |

冲突优先规则：若财务角色标签与 `70` 六角色授权冲突，以 `70` 主角色约束为准，财务标签仅作为财务域作用域权限。

权限约束：

- 结算执行与资金修正必须双人复核。
- `FINANCE_AUDITOR` 仅读，不得改动分录或规则。
- 高风险动作（批量修正、批量导出、费率发布）必须审批。

### 9.4 执行入口（工作流/命令/责任人）

- 代码与测试入口：`cargo test -p traveltrust-api`、`cd frontend && npm run test`。
- 当前 CI 入口：`.github/workflows/build.yml`（主流水线并轨） + `.github/workflows/indexer-reconcile-gate.yml`（索引器/对账基线） + `.github/workflows/finance-reconcile-gate.yml`（200 专项门禁）。
- 责任人：`api-backend`（路由与契约）、`admin-finance`（财务治理链路）、`ops-sre`（回放与对账演练证据）。
- 发布原则：200 门禁失败或证据缺失时，不得将财务链路标记为 `Implemented`。

### 9.5 证据字段规范（发布证据 JSON 最小字段）

财务治理相关证据最小字段必须包含：

- `workflow`
- `job`
- `check`
- `commit_sha`
- `ci_run_id`
- `env`
- `rule_id`
- `severity`
- `owner`
- `generated_at`（UTC）
- `passed`

字段缺失、时间戳非 UTC、`passed` 缺失视为门禁失败。

## 十、与既有阶段关系

- `110` 解决链上事件同步与基础对账能力。
- `120` 解决可观测、告警、审计链路。
- `130` 解决对账与结算相关测试门禁。
- `140` 解决生产发布、恢复、演练与交付门禁。
- `200` 将上述能力上收为“财务、对账、结算、报表”的独立经营与治理系统。

结论：Escrow 是托管基础，不是财务终局；200 阶段必须把资金真相、账本投影、结算执行和审计报表做成完整系统闭环。
