## 一、43 阶段目标与范围

| 维度 | 说明 |
|------|------|
| **阶段目标** | 前端 UI 的**最佳模块化拆解**：长文件按功能域/视图区/职责拆分，分类分区，达到企业级可维护性与可测试性。 |
| **范围** | 所有**过长**或**职责过多**的页面/组件（含弹窗、表单、列表、详情页）；优先处理单文件 > 500 行或圈复杂度/耦合度高的模块。 |
| **不涉及** | 后端 API、合约、数据库；仅限前端 `app/`、`components/`、`lib/` 的 UI 与展示逻辑。 |
| **交付物** | ① 拆分后的目录与文件结构；② 单文件行数/复杂度达标；③ 公共逻辑抽成 hooks/utils/components；④ 本文 §五 验收表全部勾选。 |

**判定「需拆分」的触发条件**（满足其一即进入 43 阶段拆解清单）：

- 单文件 **> 500 行**（不含空行与注释可放宽至 600，但建议 400 以内）。
- **单一组件/页面** 同时承担：路由数据、多 Tab/多步骤、多表单区块、弹窗、列表、详情、复杂状态机。
- **圈复杂度高**：单文件内分支/循环多，难以单测或难以一眼看懂主流程。
- **重复代码**：同一 UI 模式或逻辑在多处复制粘贴，未抽成组件或 hook。

## 二、拆分方法：分类与分区

### 2.1 拆分原则（三条）

1. **按职责拆**：一个文件/一个导出组件或 hook 只做一类事（如「仅展示列表」「仅处理表单提交」「仅弹窗容器」）。
2. **按视图/功能域拆**：同一业务块（如「行程按天编辑」「报价汇总」「向导选择」）放在同一目录或同一前缀下，便于定位。
3. **按可复用性拆**：可被多页或多弹窗复用的 UI 与逻辑，必须抽到 `components/` 或 `lib/`，不得留在页面内部。

### 2.2 分类分区方式

| 分类维度 | 做法 | 示例 |
|----------|------|------|
| **按功能域** | 同一业务域（如「行程编辑」「报价」「订单」）单独目录或子组件目录 | `CustomItineraryModal/` 下 `DayEditor/`、`QuoteSummary/`、`TransportSection/` |
| **按视图区块** | 页面/弹窗内「一块屏幕区域」一个组件（Header / Body / Footer / Sidebar） | `ModalHeader.tsx`、`ModalBody.tsx`、`QuoteTable.tsx` |
| **按状态与逻辑** | 表单状态、校验、提交、与 API 的交互抽成 custom hook | `useItineraryForm.ts`、`useQuoteCalculation.ts` |
| **按数据类型/展示** | 列表项、卡片、行内单元格等抽成纯展示组件 | `ItineraryDayCard.tsx`、`PriceRow.tsx` |
| **常量与配置** | 选项列表、枚举、校验规则、文案 key 集中到单独文件 | `constants.ts`、`validation.ts`、与 i18n key 表对应 |

### 2.3 推荐目录结构（以长弹窗为例）

以「自定义行程弹窗」类长模块为例，拆解后建议结构：

```
components/market/
  CustomItineraryModal/           # 弹窗根目录（或保留单文件入口再按需拆）
    index.tsx                     # 仅组合子组件 + 路由/模式切换，控制弹窗开闭
    constants.ts                  # 天数选项、价格常量、校验上限等
    types.ts                      # 表单类型、API 入参/出参类型
    useItineraryForm.ts           # 表单 state、校验、提交
    useQuoteCalculation.ts        # 报价计算（游客/向导共用逻辑）
    sections/                     # 按「区块」拆
      DayEditorSection.tsx        # 按天编辑（城市/景区/餐饮/酒店）
      TransportSection.tsx        # 城市交通 + 跨城交通
      QuoteSummarySection.tsx     # 报价汇总与明细
    shared/                       # 弹窗内复用
      PriceRow.tsx
      CitySelector.tsx
```

**页面级**（如 `app/community/page.tsx` 过长时）：

- 顶部「标题 + 操作栏」→ `CommunityFeedHeader.tsx`
- 筛选栏（推荐/关注、排序、类型）→ `FeedFilterBar.tsx` 或同目录下 `FeedFilters.tsx`
- 列表与骨架 → 已有 `CommunityFeedCard` 等；列表容器与 loading/error 态可再抽 `FeedList.tsx`
- 弹窗仍保持独立组件（如 `PublishDrawer`、`PostDetailDrawer`），不塞回页面文件

### 2.4 命名约定

| 类型 | 约定 | 示例 |
|------|------|------|
| **目录** | 与主功能一致，Pascal 或 kebab 皆可，同一模块内统一 | `CustomItineraryModal/` 或 `custom-itinerary-modal/` |
| **组件文件** | PascalCase，与默认导出组件名一致 | `DayEditorSection.tsx` |
| **Hook 文件** | `use` 前缀 + 功能名 | `useItineraryForm.ts` |
| **常量/类型** | `constants.ts`、`types.ts` 或按域 `itineraryConstants.ts` | 与 34、22 命名一致 |
| **区块组件** | 可带 Section/Block/Bar 后缀便于识别 | `QuoteSummarySection.tsx`、`FeedFilterBar.tsx` |

### 2.5 本仓库分层与顶级模块化方案

**统一分层（依赖自上而下，禁止反向或跨层循环）：**

```
┌─────────────────────────────────────────────────────────────────┐
│  App 层 (app/)                                                   │
│  路由、layout、page；仅负责取数(useSearchParams/useParams)、      │
│  组合 components + 可选 layout 级 Provider；单页建议 ≤400 行      │
└───────────────────────────┬─────────────────────────────────────┘
                            │ 仅引用
                            ▼
┌─────────────────────────────────────────────────────────────────┐
│  Components 层 (components/)                                     │
│  ├ 共享 (根目录): Header, Providers, LocaleProvider, ApiError…   │
│  └ 按域 (community/, market/, escrow/, trust/, did-rank/)        │
│     复杂模块可子目录: CustomItineraryModal/, EscrowDetail/ 等     │
│     单文件 ≤500 行；复杂弹窗/详情拆为 index + sections + hooks   │
└───────────────────────────┬─────────────────────────────────────┘
                            │ 可引用
                            ▼
┌─────────────────────────────────────────────────────────────────┐
│  Hooks 层 (hooks/ 或 components/<域>/hooks/)                     │
│  表单、报价计算、列表加载、弹窗开闭等逻辑；与 UI 解耦，可单测      │
│  本仓可选: frontend/hooks/ 公共 + components/market/hooks 等     │
└───────────────────────────┬─────────────────────────────────────┘
                            │ 可引用
                            ▼
┌─────────────────────────────────────────────────────────────────┐
│  Lib 层 (lib/)                                                   │
│  api, apiClient, i18n, constants；按需 lib/market/, lib/community/│
│  纯函数、类型、常量；禁止依赖 components 或 app                   │
└─────────────────────────────────────────────────────────────────┘
```

**最佳实践要点：**

| 层级 | 职责 | 本仓库落地建议 |
|------|------|----------------|
| **App** | 路由与页面组合，最小逻辑 | 长页（community、did-rank、me、market、page.tsx）拆出 Header/Filter/List 等区块组件到同域 components |
| **Components** | 可复用 UI + 组合子组件 | 超长组件（CustomItineraryModal、EscrowDetail）改为目录：index + constants + types + hooks + sections |
| **Hooks** | 状态、副作用、业务逻辑 | 新增 `frontend/hooks/` 放跨域 hook；`components/<域>/hooks/` 放域内专用（如 useItineraryForm） |
| **Lib** | API、类型、常量、纯工具 | 保持扁平或按域子目录（如 `lib/market/`）；cityDetails 等超大文件可拆为按国家/城市分文件 |

**依赖规则：** App → Components → Hooks → Lib；同层可互相引用（如 components 间）；禁止 Lib 引用 Components/App，禁止 Hooks 引用 Components 的具名 UI 组件（仅可引用类型）。

## 三、最终标准（验收线）

### 3.1 文件与行数

| 标准项 | 要求 | 说明 |
|--------|------|------|
| **单文件行数** | 建议 ≤ 400 行，硬性上限 500 行（不含空行与注释） | 超过则必须拆出子组件或 hook |
| **单组件职责** | 一个文件只导出一个主组件或一个 hook，或一组强相关的子组件（如 `sections/` 下各一个） | 禁止「一个文件里多个不相关组件」 |
| **单函数/单 hook 长度** | 单函数建议 ≤ 80 行；单 hook 内 effect/逻辑块建议 ≤ 50 行 | 过长则拆成子函数或子 hook |

### 3.2 复杂度与可测试性

| 标准项 | 要求 |
|--------|------|
| **圈复杂度** | 单文件/单函数圈复杂度建议 ≤ 15；关键分支可单独抽函数以降低复杂度 |
| **可单测** | 抽出的 hook、纯计算函数、校验函数必须可无 UI 单测（jest/vitest）；组件可测渲染与关键交互 |
| **依赖注入** | 与 API/路由耦合的逻辑通过 props 或 context 注入，便于 mock 与测试 |

### 3.3 复用与一致性

| 标准项 | 要求 |
|--------|------|
| **Design Tokens** | 样式仅用 22/28/30 规定 Token 与 Tailwind 扩展，禁止裸色、裸圆角（见 34 §二） |
| **i18n** | 所有文案走 `t(key)`，key 在 locales 中统一维护 |
| **无障碍** | 表单、按钮、列表、弹窗具备 aria-label/aria-describedby/role，焦点与键盘可操作（05 §9、37） |

### 3.4 目录与依赖方向

| 标准项 | 要求 |
|--------|------|
| **依赖方向** | 页面 → 组件 → hooks/utils；禁止组件反向依赖页面或跨域循环依赖 |
| **公共逻辑** | 两处及以上使用的逻辑/UI 必须落在 `components/` 或 `lib/`，不得重复实现 |
| **索引导出** | 同一功能域多文件时，可用 `index.ts` 统一导出，便于引用路径简洁 |

## 四、企业级最佳实践

### 4.1 可维护性

- **注释与文档**：每个目录可配 `README.md` 简述该模块职责与入口；复杂业务逻辑处保留必要注释（为何这样算、与哪条产品规则对应）。
- **类型**：表单、API 入参/出参、组件 props 全量 TypeScript 类型，禁止 `any`；公共类型放在 `types.ts` 或 `lib/` 下共享。
- **常量集中**： magic number、选项列表、校验上限等全部进 `constants.ts` 或等价文件，与 42-自定义行程弹窗文档中的常量表一致。

### 4.2 可测试性

- **纯逻辑与 hook**：报价计算、校验、状态转换等写成纯函数或 custom hook，单测覆盖核心分支与边界。
- **组件**：关键交互（提交、取消、必填校验）有测试；可配合 Testing Library 只测行为不测实现细节。
- **Mock**：API 与路由在测试中 mock，不依赖真实后端。

### 4.3 性能与体验

- **按需加载**：过重弹窗或复杂区块使用 `dynamic(..., { ssr: false })` 或 React.lazy，避免首屏阻塞。
- **状态粒度**：避免整页/整弹窗单一大 state；按区块或按步骤拆分 state，减少无关重渲染。
- **列表**：长列表考虑虚拟滚动或分页，见 31 清单与 38 性能预算。

### 4.4 安全与合规

- **输入校验**：用户输入做服务端与前端双重校验；前端校验与 04/08 业务规则一致。
- **敏感信息**：不把密钥、内部 ID 暴露到前端日志或未脱敏的 UI。

### 4.5 与现有规范对齐

- **22 Design Tokens**：颜色、圆角、阴影、字体仅用 22/28 规定（34 §二）。
- **13 / 13-1**：页面与权限、异常态、信息结构符合协议级 UI 宪法与 SSOT。
- **31 / 29 / 28**：社区、市场、Landing 各区域风格与组件按对应规范实现。

## 六、执行顺序与建议

1. **列清单**：按 §一「触发条件」扫描 `app/`、`components/`，列出所有 > 500 行或职责过多的文件，排优先级（如先弹窗、再长页）。
2. **拆解设计**：对每个文件按 §2 做拆分设计（目录、子组件、hook、常量），与 34 组件清单、33 页面验收对齐。

## 七、本仓库最佳实践总结（顶级优化要点）

基于当前仓库结构与企业级目标，43 阶段落地时遵循以下**顶级最佳实践**：

### 7.1 分层与依赖

- **严格分层**：App → Components → Hooks → Lib，禁止反向与跨层循环；同层可互引（如 components 间）。
- **入口单一**：复杂模块对外只暴露一个入口（如 `CustomItineraryModal/index.tsx`），内部再拆 sections/hooks/constants。
- **类型与常量下沉**：类型、常量、纯工具一律放在 Lib 或组件目录内的 `types.ts` / `constants.ts`，便于单测与复用。

### 7.2 代码拆分

- **单文件硬性上限 500 行**，建议 ≤400；超限必须拆为多文件（sections、hooks、utils）。
- **单职责**：一个文件只做一件事（一个主组件、或一个 hook、或一组强相关类型/常量）。
- **先抽逻辑再抽 UI**：先抽 hooks 与纯函数（可单测），再按视图区块抽 Section 组件，最后保留薄薄的 index 做组合。

### 7.3 可测试与可维护

- **Hook 与纯函数必可单测**：不依赖 DOM 与路由，通过参数入参、返回值断言；API 用 mock。
- **复杂逻辑与文档对应**：计费、校验、状态机与 [42-自定义行程弹窗](42-自定义行程弹窗-游客与向导UI设计与算法.md)、04/08 等文档一致，关键处注释引用文档章节。
- **命名与 34/22 一致**：组件名、Token、i18n key 符合 34 组件清单与 22 Design Tokens，便于后续替换与主题化。

### 7.4 性能与体验

- **重组件按需加载**：CustomItineraryModal、EscrowDetail、DidRank Modal 等可用 `dynamic(..., { ssr: false })` 或 lazy；**`Web3SciFiBackground`** 仅在仍挂载子树使用（**`/did-rank`/`/community` 壳层**见 **88**）。
- **状态粒度合理**：大表单按区块或按步骤拆 state，避免单一大对象导致全量重渲染；列表项用稳定 key。

### 7.5 本仓库优先顺序

1. **P0**：CustomItineraryModal 按 §2.6 表拆为目录 + constants/types/utils + useQuoteCalculation + useItineraryForm + sections（TouristForm、GuideForm、DetailOverlay、DayCard）+ index。
2. **P1～P3**：community/page、did-rank/page、EscrowDetail 按「Header/Filter/List 或 状态区块」拆出组件与可选 hooks。
3. **P4～P7**：cityDetails、page.tsx（Landing）、me/page、market/page 按需拆为多文件或子目录。
4. **Hooks 与 Lib**：新增 `frontend/hooks/` 或 `components/<域>/hooks/`；lib 保持或按域分子目录（如 `lib/market/`），避免单文件过大。

按上述执行并勾选 §五 验收表，即达到**本仓库 43 阶段顶级模块化与最佳实践**要求。
