## 一、文档定位

本文定义 TravelTrust 在 380 阶段的“灾难恢复与回放系统”开发规范。

380 阶段确保在数据库损坏、事件错位、缓存丢失后，系统可以重建投影并恢复业务状态。

## 二、必须具备的恢复能力

企业级必须支持：

- 重建 DB 投影
- 重放链事件
- 重跑任务
- 重建缓存
- 恢复订单状态

## 三、必备组件

- `event log`
- `replay tool`
- `rebuild script`
- `snapshot`

## 四、系统目标

1. 可重建：主库损坏后可重建关键业务投影。
2. 可回放：链上与任务事件可按序重放。
3. 可验证：恢复后状态可校验一致。
4. 可演练：灾备流程可定期演练并留痕。

## 五、恢复分层策略

### 5.1 数据层恢复

- 基于事件日志重建投影。
- 基于快照 + 增量回放加速恢复。

### 5.2 任务层恢复

- 未完成任务重跑。
- 死信任务人工筛选回放。

### 5.3 缓存层恢复

- 缓存失效后按主库重建。
- 关键热点可优先回暖。

### 5.4 业务状态恢复

- 订单、争议、结算等关键状态一致性校验。
- 链上状态优先，DB 状态按规则修复。

## 六、数据模型建议

建议最小实体：

- `replay_events`
- `replay_runs`
- `rebuild_snapshots`
- `recovery_tasks`
- `recovery_audits`

字段级要求：

- `replay_events`：`event_id`、`source`、`sequence_no`、`payload_digest`。
- `replay_runs`：`run_id`、`scope`、`started_at`、`ended_at`、`result`。
- `rebuild_snapshots`：`snapshot_id`、`captured_at`、`checkpoint`、`storage_ref`。
- `recovery_tasks`：`task_id`、`task_type`、`status`、`retry_count`。
- `recovery_audits`：`run_id`、`validator`、`diff_count`、`approved_by`。

## 七、核心硬约束

1. Replayable By Design：关键域数据必须可由事件重建。
2. Snapshot Controlled：快照生成、保留、恢复必须受控。
3. Recovery Tested：恢复方案必须定期演练。
4. Chain Priority：资金相关状态恢复以链上事件为准。
5. Audit Ready：每次恢复必须可审计。

## 八、后台模块要求

后台新增一级模块：`灾难恢复中心`

子模块（必须）：

- 回放任务
- 重建任务
- 快照管理
- 恢复结果校验
- 灾备演练记录

## 九、实施计划（380 阶段）

### 9.1 P0（必须）

- 建立事件日志与回放工具。
- 建立重建脚本与快照机制。
- 建立恢复校验与审计流程。

### 9.2 P1（增强）

- 自动化灾备演练。
- 分域并行恢复编排。

### 9.3 P2（规模化）

- 多区域容灾回放联动。
- 恢复时间目标（RTO/RPO）持续优化。

## 十、发布门禁

1. DB 投影重建演练通过。
2. 链事件回放一致性校验通过。
3. 任务与缓存恢复流程可执行。
4. 灾备报告可导出可审计。

## 十一、结论

灾难恢复与回放系统是平台韧性的底线。没有 380 阶段，数据库级事故会直接演化为全站停摆。
