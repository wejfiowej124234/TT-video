## 一、文档定位

本文定义 TravelTrust 在 110 阶段的“链上索引器与事件同步器”开发规范。

本系统是混合架构的基础设施层，不是可选组件。

若缺失 indexer / event consumer / finality / reorg / 对账闭环，则后台管理、订单页、财务页都不具备可靠性。

根据正式架构约束（Indexer -> RPC -> Polygon），110 阶段必须作为主线工程能力落地。

## 二、系统目标

110 阶段目标是建立“链上事件到业务投影”的可验证同步闭环：

1. 事件可完整消费：链上关键事件不丢失、不重复、不乱序落库。
2. 终局可确认：finality 达标前不进入资金终态投影。
3. 重组可恢复：reorg 发生后可回滚并重放到正确状态。
4. 投影可对账：链上到账状态与 DB 投影持续对账。
5. 运行可审计：索引、重放、修复动作全量留痕。

## 三、范围定义（六大模块）

### 3.1 Indexer 事件抓取层

核心能力：

- 从 RPC 节点拉取事件（按 block range、topic、address）。
- 支持多合约与多事件类型订阅。
- 支持断点续抓与批量抓取。
- 支持冷启动全量回放与增量追块。

最小事件集（P0）：

- `EscrowCreated`
- `Paid`（若合约事件名为 `Deposited`，在消费层统一映射为 `Paid`）
- `DisputeOpened`
- `ResolutionExecuted`
- **`PlatformFeeRouted`**（**FeeRouter**；与订单状态机**独立**；投影表 **`fee_router_routed_events`**，见 **§3.1.1**）

事件命名规范（避免口径漂移）：

- 链上原始事件名允许存在别名，但平台投影与对账口径统一使用 `EscrowCreated/Paid/DisputeOpened/ResolutionExecuted`。
- 若合约保留 `Released/Refunded` 等细分事件，消费层必须映射到资金终态字段，不新增平行主状态机。

验收要求：

- 事件主键去重（chain_id + block_number + tx_hash + log_index）。
- 断点恢复后不漏事件、不重复写入。

#### 3.1.3.1 复合门闸 **`indexer_reconcile_compound_gate`（B-101 / TT-121）** · Implemented-Minimal

**目的**：在保留 **`orders_projection_reconcile_gate`**（**`110-ORDERS-PROJECTION-RECONCILE-GATE`**）为 **DB 主对账** 子门禁的前提下，为 **`POST …/internal/indexer-reconcile`** **`200`** 提供**单一根级布尔** **`reconcile_compound_pass`**（与对象 **`indexer_reconcile_compound_gate.pass`** 同源），便于探针 **`jq`** 一次判定「本请求启用的对账信号是否**全部**通过」。

|--------|------------------------------|----------------|
| **`orders_projection`** | **恒真** | 与 **`orders_projection_reconcile_gate.pass`** / **`projection_reconcile_clean`** 同源 |
| **`rpc_escrow_samples`** | body **`rpc_escrow_samples>0`** 且**未**走 **`rpc_escrow_samples_skipped`**（即已实际拉样） | 每个样本 **`coarse_terminal_aligned`** 均为 **`true`**；**`samples` 为空**时 **vacuous**（**`pass: true`**） |
| **`event_log_escrow_coverage`** | body **`include_event_log_escrow_coverage:true`** 且 **`200`** 体已含 **`event_log_escrow_coverage`** | **观测计数**，当前**不设阈值**：**`pass` 恒 `true`**（**`rule`=`B101_EVENT_LOG_COVERAGE_NO_THRESHOLD`**）；若未来引入不变量须与本节同批 bump 文档锚点 |

### 3.2 Event Consumer 投影层

核心能力：

- 将链上事件标准化为内部事件模型。
- 执行业务投影写入（orders_projection 等）。
- 保持状态机合法迁移，拒绝非法跳转。
- 维护 checkpoint（block_number + log_index）。

投影原则：

- 链上是资金状态真源，DB 是业务投影。
- 投影表可删除并由事件重建。
- 非 finality 事件不得写入“终态字段”。

验收要求：

- 同一事件消费幂等。
- checkpoint 单调前进且可审计。

### 3.3 Finality 确认层

核心能力：

- finality 参数配置化（如 `FINALITY_N`）。
- 区分 pending / confirmed 事件视图。
- 记录每条事件使用的 `finality_n_used`。
- finality 变更触发回放计划。

硬约束：

- 未确认事件可用于提示，不可用于资金终态落库。
- finality 参数变更必须有回放与审计记录。

验收要求：

- 运行时可查询 finality 生效值。
- finality 变更后有 replay 证据链。

**启动闸（Partial，与 tick 上界互补）**：当 **`CHAIN_RPC_URL`** 已配置且 **`ESCROW_FACTORY_ADDRESS`** 非空（将跑 **`indexer-tick`**）时，可选 **`INDEXER_MIN_FINALITY_N`** 强制 **`FINALITY_N` ≥ 该值；或 **`STRICT_INDEXER_FINALITY=1`** 且未设前者时要求 **`FINALITY_N` ≥ 12**（与默认 **`FINALITY_N`** 一致）。不满足则 API 拒绝启动。实现：**`crates/api/src/startup/mod.rs`** **`enforce_indexer_finality_floor`**；见 **`.env.example`**、**04 §四**、**Runbook §11**。

### 3.4 Reorg 检测与恢复层

核心能力：

- 识别链重组（区块哈希分叉）。
- 回滚受影响的投影区间。
- 从安全高度重放事件。
- 在恢复期对外标记降级状态。

恢复策略：

- `detect -> freeze-sensitive-write -> rollback -> replay -> verify -> unfreeze`。
- 对账失败时进入人工介入流程。

验收要求：

- 模拟 reorg 场景可恢复到一致状态。
- reorg 期间关键业务动作被正确降级或阻断。

### 3.5 链上到账与 DB 投影对账层

核心能力：

- 对账对象：链上 escrow 状态、金额、参与方、终态。
- 对账频率：实时轻量 + 周期全量。
- 差异分类：可自动修复 / 需人工复核 / 严重告警。
- 对账报告归档与审计导出。

对账最小维度：

- 订单资金状态一致性
- 金额与币种一致性
- 关键时间点一致性
- 裁决执行结果一致性

验收要求：

- 能输出标准化对账报告。
- 差异处理动作可追溯且具备 owner。

### 3.6 运行可观测与故障处置层

核心能力：

- 核心指标：indexer lag、consumer throughput、reorg count、replay duration、reconcile mismatch rate。
- 告警策略：阈值告警、持续告警、升级告警。
- 健康探针：indexer 健康、RPC 健康、队列积压健康。
- Runbook 联动：故障处置步骤与责任人明确。

验收要求：

- 关键指标可视化可检索。
- 至少覆盖 5 类典型故障场景演练。

## 四、核心可靠性约束（必须写死）

1. Chain Truth First：资金终态以链事件确认结果为准。
2. Event Idempotency：同一事件多次消费不得改变最终结果。
3. Checkpoint Monotonicity：正常增量消费下 checkpoint 单调前进；当发生 reorg/replay 时可按已审批回放计划受控回退到安全高度并重放，且全量留痕。
4. Finality Discipline：未 finality 的事件不得写入资金终态。
5. Reorg Recoverability：重组后必须可回滚与重放到一致状态。
6. Reconcile Closure：链上与 DB 差异必须闭环，不得长期漂移。
