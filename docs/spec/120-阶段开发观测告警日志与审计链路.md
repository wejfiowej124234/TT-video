## 一、文档定位

本文定义 TravelTrust 在 120 阶段的“观测、告警、日志、审计链路”开发规范。

120 阶段的核心目标是把“能跑的系统”升级为“能运维、能排障、能审计、能追责的系统”。

若缺失 metrics / tracing / structured logs / alerting / 审计与安全操作留痕，系统在生产环境将不可控：

- 事故发生时无法快速定位根因。
- 资金与状态异常无法及时发现。
- 敏感操作无法追责与复盘。
- 合规审计无法提供完整证据链。

## 二、系统目标

120 阶段目标是建立“从用户请求到链上执行再到审计导出”的全链路可观测与可审计闭环：

1. 指标可量化：关键业务与系统健康可实时量化。
2. 链路可追踪：一次请求可贯通 API、任务队列、执行器、链上交易。
3. 日志可检索：结构化日志可按 order_id / trace_id / tx_hash 快速查询。
4. 告警可处置：告警具备明确阈值、升级策略与 runbook 动作。
5. 审计可导出：关键行为与安全操作可形成不可抵赖证据链。

## 三、范围定义（六大模块）

### 3.1 Metrics 指标体系

核心能力：

- 统一指标分层：业务指标、平台指标、基础设施指标。
- 指标命名规范化（service, endpoint, action, status, chain_id, env 标签）。
- 指标采集与持久化（Prometheus 拉取，Grafana 展示）。
- 指标基线与 SLO 绑定（错误率、延迟、可用性、一致性）。

最小指标集（P0）：

- API：QPS、P95/P99 延迟、4xx/5xx 比例。
- DB：连接池利用率、慢查询计数、事务失败率。
- Queue：队列积压、消费速率、重试次数、死信数。
- Indexer：lag blocks、reorg count、replay duration。
- 业务：下单成功率、支付成功率、争议率、仲裁执行成功率。

验收要求：

- 每个关键链路至少有 1 个成功指标 + 1 个失败指标。
- 指标可按环境、链 ID、版本号切片分析。

### 3.2 Tracing 链路追踪体系

核心能力：

- 统一 trace_id / span_id 生成与透传。
- 跨组件追踪：Frontend -> API -> Queue -> Worker -> RPC -> Chain。
- 关键字段关联：request_id、message_id、order_id、resolution_id、tx_hash、log_index。
- 异常 span 标记：超时、重试、回滚、降级、人工接管。

追踪原则：

- 没有 trace_id 的关键请求视为观测缺口。
- 关键异步任务必须保留父子 span 关系。

验收要求：

- 可通过 trace_id 一键定位到对应日志与审计记录。
- 可通过 order_id 反查完整链路时序。

当前差距说明：现阶段以请求标识与业务主键关联为主，完整跨组件 span 树、统一采样/导出与可视化链路仍在后续阶段收口。

### 3.3 Structured Logs 结构化日志体系

核心能力：

- 日志统一 JSON 格式，不允许关键路径纯文本日志。
- 字段标准化：ts、level、service、env、trace_id、request_id、actor、action、resource、result、error_code。
- 日志分级：debug/info/warn/error/fatal。
- 日志脱敏：PII、凭据、密钥、token 严禁明文输出。

日志分类：

- 访问日志：请求路径、耗时、状态码。
- 业务日志：订单、争议、裁决、执行器关键动作。
- 系统日志：DB、缓存、队列、RPC、重试与故障。
- 安全日志：登录失败、权限拒绝、敏感接口访问。

验收要求：

- 关键动作日志包含 trace_id 与业务主键（order_id 或 resolution_id）。
- 可在日志平台按 5 分钟窗口完成事故定位查询。

当前差距说明：代码中仍存在非 JSON 的 `println!/eprintln!` 路径；上线前必须完成关键链路结构化改造与脱敏回归。

### 3.4 Alerting 告警体系

核心能力：

- 告警分级：P1（资损/不可用）、P2（高风险）、P3（一般异常）。
- 告警触发：阈值告警、持续告警、异常波动告警。
- 告警降噪：去重、抑制、聚合，避免告警风暴。
- 告警升级：超时未响应自动升级到下一值班层级。

最小告警集（P0）：

- API 5xx 比例超阈值。
- 订单关键写路径失败率超阈值。
- Indexer lag 持续扩大。
- 对账差异超过金额或笔数阈值。
- 执行器死信队列非零且持续增长。
- 安全告警：internal 接口异常访问、权限暴力尝试。

验收要求：

- 每个 P1/P2 告警必须绑定 runbook 链接与值班责任组。
- 告警触发到确认、处置、恢复全过程可追踪。

当前差距说明：`internal/alerts/test-fire` 与 `internal/incident/open` 当前用于演练与接口锚点，不等于告警编排、升级、抑制、值班平台能力已全部落地。

### 3.5 审计日志与安全操作留痕体系

核心能力：

- 审计对象标准化：Who / When / Where / What / Why / Result。
- 高风险操作强制审计：配置变更、权限变更、仲裁执行、手工修复、重放回滚。
- 审计记录防篡改：append-only、哈希指纹、导出签名。
- 操作票据关联：工单号、审批号、变更单号。

必须留痕的安全操作：

- RBAC 角色授权与回收。
- `internal/*` 运维接口调用。
- 关键参数修改（如 FINALITY_N、STRICT_SSOT、风控阈值）。
- 手工触发 replay / reconcile / correction。
- 执行器人工重试、死信处理、强制终止。

验收要求：

- 任一敏感动作均可追溯到发起人、审批人、执行结果。
- 审计导出可满足合规检查与事故复盘。

当前差距说明：现有审计能力已覆盖部分管理员动作留痕与查询，但 append-only 防篡改与签名导出闭环仍按目标态推进。

### 3.6 运行看板、SLO 与值班处置体系

核心能力：

- 看板分层：业务看板、平台看板、安全审计看板。
- SLO 固化：可用性、延迟、错误预算、数据一致性预算。
- 值班流程：告警接收、确认、止损、恢复、复盘闭环。
- 事故分级：SEV1/SEV2/SEV3 对应不同升级与沟通机制。

最小看板集（P0）：

- API 与核心业务指标看板。
- Indexer + 对账 + 执行器健康看板。
- 安全事件与审计操作看板。

验收要求：

- 发生 P1 事故可在 15 分钟内定位主要故障域。
- 每次事故有标准复盘记录与改进动作 owner。

## 四、核心硬约束（必须写死）

1. No Blind Path：订单、支付、争议、裁决、执行器路径不得存在无指标、无日志、无追踪盲区。
2. Trace Consistency：trace_id 在同步与异步链路中必须可持续关联。
3. Structured First：关键路径必须输出结构化日志，禁止仅凭自由文本日志排障。
4. Alert Actionability：所有 P1/P2 告警必须可执行，不得出现“响了但没人知道怎么处理”。
5. Audit Immutability：审计日志 append-only，禁止覆盖式更新。
6. Security Accountability：所有敏感操作必须留痕并可追责。

## 七、阶段实施计划（120 阶段）

### 7.1 P0（必须）

- 指标体系最小集落地（API/DB/Queue/Indexer/业务）。
- 全链路 trace_id 贯通与日志字段统一。
- 结构化日志标准落地与脱敏基线。
- P1/P2/P3 告警规则最小集上线。
- 审计日志与安全操作留痕最小闭环。

### 7.2 P1（增强）

- 告警去重、抑制、升级策略完善。
- 事故管理（incident）与复盘模板平台化。
- 审计日志哈希签名与导出校验。
- 跨系统链路追踪（前端性能、后端、执行器）统一视图。

### 7.3 P2（规模化）

- 多区域观测聚合与跨区域告警联动。
- SLO/错误预算驱动发布门禁。
- 智能异常检测（基线漂移、异常模式识别）。
- 合规审计自动出具周期报告。

## 八、发布门禁（分层：P0 必须全过）

### 8.1 P0（最小可发布门禁，必须全过）

1. 核心业务链路具备 metrics + trace + structured logs 三件套。
2. 至少 10 条关键告警规则上线并完成演练。
3. P1/P2 告警均绑定 runbook 与责任人。
4. 审计日志可导出并通过抽样追责演练。
5. 安全敏感操作 100% 留痕，且可按 trace_id 关联。
6. 至少完成 3 个事故场景演练：API 异常、Indexer 滞后、执行器死信。

关键告警规则最小覆盖矩阵（10 条不得“凑数”）：

| 域 | 最小条数 | 规则示例 |
|---|---|---|
| API 可用性 | >= 2 | 5xx 比例、P95 延迟超阈值 |
| Indexer/对账 | >= 2 | lag 持续扩大、reconcile diff 超阈值 |
| 执行器/任务 | >= 2 | 死信队列增长、重试耗尽 |
| 安全边界 | >= 2 | internal 异常访问、权限暴力尝试 |
| 审计完整性 | >= 2 | 高危操作缺审计、导出失败 |

单条规则验收模板（每条规则都必须具备）：`rule_id`、`severity`、`scope`、`threshold`、`suppress/dedupe`、`escalation_policy`、`runbook_link`、`last_drill_at`、`owner`。

量化判定基线（P0 建议阈值，缺证据按未通过）：

- 关键写链路结构化日志覆盖率 >= 95%（按抽样/日志规则统计）。
- 关键写链路 trace_id 贯通率 >= 95%，关键异步链路父子关联率 >= 90%。
- 关键写链路 request_id 贯通率 >= 99%，message_id 覆盖率 >= 95%。
- `internal` 演练链路处置闭环证据完整率 = 100%（触发、确认、恢复、复盘四段齐全）。
- 审计抽样可回放成功率 = 100%（至少 10 条高风险操作样本）。
