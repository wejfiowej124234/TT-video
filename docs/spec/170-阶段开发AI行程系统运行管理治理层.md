## 二、系统目标

170 阶段目标是建立 AI 行程系统的运行治理闭环：

1. 可控：模型、Prompt、规则、灰度、配额均可配置和发布。
2. 可审：每次生成都可追溯到版本、参数、责任人和时间。
3. 可回滚：模板、参数、策略异常时可快速回滚。
4. 可运营：支持审核、预算、SLA、故障处理和跨区域策略。
5. 可合规：输出内容可治理、可过滤、可审计、可复盘。

## 三、系统分层（必须写死）

### 3.1 前台 Web / DApp

只负责：

- 用户输入需求。
- 展示 AI 生成结果。
- 提交确认与查看历史版本。

硬约束：

- 前端不得持有 AI Provider 密钥。
- 前端不得直接调用外部模型 API。

### 3.2 Rust 后端（AI 执行层）

负责：

- 模型调用编排与失败重试。
- Prompt 组装、参数校验、JSON Schema 验证。
- 输出结构化、版本冻结、snapshot 绑定。
- 成本统计、限流、审计留痕。

硬约束：

- AI 执行必须经后端统一网关，不得绕过。
- 所有生成任务必须产生任务号与审计记录。

### 3.3 管理员后台（AI 治理层）

负责：

- 配置 AI 规则、模板、灰度、开关、配额。
- 人工审核与修正、上线发布与回滚。
- 运行监控、告警处理、审计追溯。

硬约束：

- AI 治理能力作为后台一级模块存在。
- 发布、回滚、审计权限必须独立于普通管理员权限。

## 四、后台一级模块清单（A-G）

### 4.1 A. AI 配置中心

管理范围：

- 模型提供商与模型版本。
- `temperature`、`max_tokens`、`timeout_ms`、`retry_policy`。
- fallback 模型路由。
- 国家/城市级功能开关。

最小要求（P0）：

- 配置项版本化，支持定时生效。
- 变更记录必须包含变更人、变更原因、审批单号。

### 4.2 B. Prompt 模板中心

管理范围：

- 系统 Prompt。
- 国家 Prompt、城市 Prompt。
- 向导侧 Prompt、游客侧 Prompt。
- 多语言模板。

最小要求（P0）：

- 模板支持版本号、发布人、生效时间、回滚。
- 不允许直接覆盖线上模板，必须走新版本发布。

### 4.3 C. 行程生成规则中心

管理范围：

- 行程天数约束、每日结构模板。
- 必填字段与字段合法范围。
- 输出 JSON Schema。
- 价格展示字段允许策略（仅展示/解释，不改变订单结算与报价定价权）。
- 景点来源规则与禁止项。

最小要求（P0）：

- 规则变更后必须跑回归校验样本。
- JSON Schema 不通过的输出不得入库。
- 涉及价格字段的 AI 输出只允许写入“展示层分项/说明字段”；订单可执行金额与结算口径仍以 `44+42+53` 与 `04` 契约为准，不允许 AI 治理层越权改价。

### 4.4 D. 审核与人工修正台

管理范围：

- AI 生成结果预览。
- 人工编辑、审核通过/驳回。
- 不合规内容标记与处置。
- 生成后发布控制。

最小要求（P0）：

- 涉及资金与协议摘要的关键内容支持人工复核。
- 人工修正痕迹不可覆盖原始输出，必须双轨留存。

### 4.5 E. 成本与配额中心

管理范围：

- 每用户每日调用次数。
- 每国家预算、每向导预算。
- token 消耗统计。
- 失败率、平均响应时长、可用性指标。

最小要求（P0）：

- 达到预算阈值时自动告警与限流。
- 费用归因可按国家、城市、用户类型拆分。

### 4.6 F. 灰度与实验中心

管理范围：

- 国家灰度、城市灰度、用户群灰度。
- Prompt A/B 实验。
- 新模型小流量验证。

最小要求（P0）：

- 灰度计划可配置开始/结束时间。
- 实验结果可回放，可一键回滚到稳定版本。

### 4.7 G. 审计与追溯中心

必须记录：

- 谁修改了 Prompt、谁发布了模板、谁触发了回滚。
- 哪个订单使用了哪版模型与模板。
- 输入摘要 hash、输出 snapshot hash。
- 模型版本、时间戳、是否人工修正。

最小要求（P0）：

- 任意订单可回放当时 AI 配置快照。
- 审计日志不可篡改、可导出、可检索。

## 六、密钥与安全边界（必须写死）

1. AI Key 不得存储在普通业务配置表明文。
2. 真实密钥必须由 Secret Manager/Vault/KMS 托管。
3. 后台页面只展示 Provider 与环境绑定状态，不显示完整密钥。
4. 管理员只可替换密钥引用或重新绑定，不可读取明文。
5. 密钥轮换、撤销、失效必须有审计记录与告警。

## 八、权限模型（必须独立拆分）

建议最小角色集：

- `AI_VIEWER`
- `AI_EDITOR`
- `AI_REVIEWER`
- `AI_RELEASE_MANAGER`
- `AI_AUDITOR`

与 `70` 角色体系映射（统一口径，避免双轨 RBAC）：

| AI 治理角色 | 70 角色主映射 | 说明 |
|---|---|---|
| `AI_VIEWER` | `Ops` / `CS` / `Auditor`（只读范围） | 仅查看治理看板与任务状态 |
| `AI_EDITOR` | `Ops` | 可编辑模板/规则，不可发布 |
| `AI_REVIEWER` | `Risk` / `Ops` | 负责审核与复核，不可越权发布 |
| `AI_RELEASE_MANAGER` | `SuperAdmin`（或经授权 `Ops`） | 可执行发布/回滚，必须双人复核 |
| `AI_AUDITOR` | `Auditor` | 只读审计导出，不可写配置 |

冲突优先规则：若 `AI_*` 与 `70` 六角色授权冲突，以 `70` 主角色约束为准，`AI_*` 仅作为治理域作用域权限标签。

权限约束：

- `AI_EDITOR` 可编辑模板与规则，但不可直接发布。
- `AI_RELEASE_MANAGER` 才能发布/回滚线上版本。
- `AI_AUDITOR` 只读审计，不可修改任何配置。
- 关键动作（发布、回滚、阈值调整）要求双人复核。

## 十、发布门禁（分层：P0 必须全过）

### 10.1 P0（最小可发布门禁，必须全过）

1. 前端无直连模型调用，AI 生成入口统一经 `POST /api/v1/itineraries`、`POST /api/v1/itineraries/custom`。
2. 生成入口契约回归通过（请求体校验、失败路径、证据留痕）。
3. 关键生成任务具备“结果可追溯”能力（至少含请求摘要、输出快照、时间戳）。
4. 运行态可观测基线可用（`GET /api/v1/admin/observability/overview` 可读且有证据）。

### 10.1.1 量化门禁基线（P0，必须写入 CI 并按 fail-closed 执行）

- 生成入口可用性：`/api/v1/itineraries*` 关键用例通过率 = 100%。
- 输出结构合规：`output_schema_version` 校验通过率 = 100%，Schema 失败样本禁止入库。
- 可追溯完整性（Current 可执行口径）：抽样 20 条任务，`content_hash + snapshot_hash + prompt_version + schema_version + created_at` 完整率 = 100%。
- 可追溯完整性（Target 升级口径）：`ai_generation_jobs/results` 落地后，升级为 `request_hash + output_snapshot_hash + prompt_version + model_version + generated_at` 完整率 = 100%。
- 治理动作审计完整性：模板发布/回滚/阈值调整抽样 10 条，审计字段完整率 = 100%。
- 运行态门禁：`admin/observability/overview` 可读且返回非空关键指标快照，失败即阻断发布。

证据文件绑定（最小集合）：

- 生成链路回归：`evidence/GO_YYYYMMDD/ai_generation_contract_report.json`
- 输出结构校验：`evidence/GO_YYYYMMDD/ai_schema_validation_report.json`
- 任务追溯抽样：`evidence/GO_YYYYMMDD/ai_traceability_sampling_report.json`
- 治理动作审计：`evidence/GO_YYYYMMDD/ai_governance_audit_report.json`
- 门禁汇总：`evidence/GO_YYYYMMDD/ai_governance_gate_summary.json`

当前状态说明：170 专项 gate 已接入独立工作流 `.github/workflows/ai-governance-gate.yml`；并入 `build.yml` 前，仍按“独立 gate + 证据强制校验”执行，不得跳过证据校验。

### 10.2 P1/P2（增强门禁，按阶段收口）

1. Prompt/模型/规则的版本化发布与回滚能力完成后，再执行治理发布门禁。
2. `admin/flags`、`admin/secrets/metadata`、`admin/internal-tools/audits` 从 `Target` 升级到可验收状态后，再作为强制门禁。
3. 成本、配额、SLA 的告警、演练和审计导出闭环完成后，进入规模化门禁。
