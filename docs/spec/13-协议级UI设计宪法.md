# 一、协议级 UI 设计宪法（7 条，任何 UI 讨论前必须锁死）

## 1️⃣ 资金区必须像银行

- **不允许**：渐变按钮、炫光、跳动数字、3D 元素侵入**资金区**（定义见下款）。
- **资金区设计关键词**：严肃、留白、信息优先、状态清晰、风险提示可见。

**补充（与 [86 §0.4](86-UI-双系统未来风-风格与动效技术规格.md) 一致 · 评审闭环）**  

- **资金区 / 资金决策 UI**（**始终**适用上条「不允许」）：**Escrow** 详情与操作、**支付/充值/提现**流、**争议**中与金额/证据/裁决相关的表单与主操作、**订单**状态下触发链上资金变动的确认与签名区。  
- **体验层例外（非资金决策）**：在 **`/`**、**`/traveltrust`** 的 **Hero、叙事、融资进度展示、教育切片** 等处，允许 **渐变主 CTA、glow、数字滚动**，**不得**伪装为托管/签名/支付界面。  
- **Business（`/market`）**：仅允许 **86 降级** 的 hover/卡片动效与 **克制** 装饰；**不得** 使用 Experience 级粒子/Hero 强特效。  
- **渐变 / glow / 数字动画** 的允许范围以 **86 §0.4 规则 1** 为操作定义；**冲突时以本文 P0 条款为准**。

## 2️⃣ 3D 只能存在于「情绪层」

- **3D 仅允许存在于**：Landing Hero、品牌演绎、资金流抽象可视化。
- **绝不进入**：EscrowDetail、Dispute、Governance。否则可信度崩塌。
- 与 [09 §2.5](09-技术架构总览-v1.0.md)、[05 §九](05-前端总览.md) 一致：3D 不用于订单操作页。

## 3️⃣ 旅游与 Web3 的融合逻辑

- **旅游** = 情绪 + 图片 + 目的地；**Web3** = 状态 + 余额 + 交易 + 签名。
- **正确融合方式**：旅游内容在「上层」，金融交互在「下层」。
- **视觉上**：上半屏可以温和；下半屏必须克制。
- **定稿落点**：情绪层（Travel）不变、可信层（Web3）内嵌、资金层（Console）隔离；**叙事结构、微徽章逻辑、折叠条款、银行级 Console** 见 [28-Cinematic-Glassmorphism-Web3融合规范](28-Cinematic-Glassmorphism-Web3融合规范.md)；**Experience 外观（色、动效、粒子、桥接渐变）** 见 **[86](86-UI-双系统未来风-风格与动效技术规格.md)**（须符合 **§一 1️⃣** 补充款）。

## 4️⃣ 角色必须空间隔离

- 五类角色：旅行者、向导、仲裁员、治理者、观察者。
- **与 87 分工**：**[87-TravelTrust-角色体系技术文档-融合架构版](87-TravelTrust-角色体系技术文档-融合架构版.md)** 定义**协议产品侧**四类（Traveler / Guide / Shop·`provider` / Region Steward）及 **UI·API·合约**命名；本条「五类」是**页面与工作空间 / RBAC 体验切分**（含**仲裁员**、**治理者**、**观察者**），**不**互相替代。**Region Steward** **不**作为订单内 Escrow 操作者叙事，见 **87 §5**；**仲裁员**为争议**裁决执行**，与 **87 §6**「仲裁执行者 vs 争议当事人」及 **[100](100-阶段开发风控与仲裁执行系统.md)** 同读。
- **UI 要求**：不是 Tab 切换，而是「进入不同工作空间」；否则会混乱。

## 5️⃣ 风格优先级排序（必须锁死）

**可信度 > 清晰度 > 一致性 > 美感 > 动效**  
不得颠倒。

## 6️⃣ AI 输出控制规则

与 AI 协作 UI 时：**不要先输出代码**。先输出：**视觉哲学 → 信息层级 → 页面结构 → 风格控制表**。否则易产出 neon dashboard 类结果。

## 7️⃣ 可感知响应时间（≤200ms）

**所有 UI/UX 的响应与切换必须在 200ms 内完成可感知的展示**，尤其是：路由/页面切换、Tab 切换、抽屉/弹窗的打开与关闭、视图切换（如市场订单/向导切换）等。  
- **达标方式**：用户操作（点击/触摸）后，**200ms 内**必须出现可见反馈（如进度条、激活态、骨架、占位内容）；数据加载可滞后，但「系统已响应」的视觉确认不可延迟。  
- **实现要点**：主导航等可用 **pointerdown 即显**反馈（首帧约 16ms）；Tab/抽屉等用同步 setState 或首帧占位，避免在事件处理中做耗时请求再更新 UI。  
- 与 [22-Design-Tokens](22-Design-Tokens-旅游Web3融合体系-v1.0.md) 响应时间数值、[52-阶段开发技术文档](52-阶段开发技术文档.md) §7.5 一致。

# 二、统一视觉哲学（高级原则）

- **易犯错误**：旅游区做得太感性、金融区做得太冷，导致割裂。
- **正确做法**：整个系统统一为 **温和的科技感**（gentle tech feel）。
- **不是**：旅游风 + Web3 风拼接。**是**：单一、温和的科技感贯穿全站。

# 三、必须准备的 5 项（正式版）

## 1️⃣ 项目定位声明（最终版示例）

TravelTrust 是一个基于 EVM 的去中心化旅游托管协议。所有资金状态以链上事件为真相。前端仅用于签名与状态展示。视觉语言必须表达：**可信、克制、未来科技感与旅行体验的平衡**。

## 2️⃣ 目标用户画像（2 类核心）

| 类型 | 特征 |
|------|------|
| **A. 高净值旅行者（核心用户）** | 注重安全、注重体验、对链理解有限；希望「安全但不复杂」。 |
| **B. 专业向导 / 服务商** | 关注托管安全、结算透明、争议流程公平。 |

仲裁员与治理者属于功能角色，不属于体验主角。

## 3️⃣ 页面列表（协议级产品结构）

| 页面 | 说明 |
|------|------|
| Landing | 落地页 |
| Discover | 发现/向导列表 |
| Booking | 预订/下单 |
| EscrowDetail | 托管详情（资金区，须遵守 1️⃣） |
| DisputeCenter | 争议中心（资金/证据区，须遵守 1️⃣，无 3D） |
| Governance | 治理（须遵守 1️⃣，无 3D） |
| Profile | 个人中心 |
| Admin | 内部管理 |

## 4️⃣ 视觉关键词（必须锁死 5 个）

**克制 · 信任 · 科技 · 空间感 · 温和旅行**

## 5️⃣ 不允许出现的风格（必须写死）

- Neon Cyberpunk  
- 极重玻璃态叠加  
- 交易区强动效
