## 一、文档定位

本文定义 TravelTrust 在 `340` 阶段的 API 版本治理规范，目标是支撑多客户端长期并行演进，避免“客户端升级引发全量兼容事故”。

权威对齐关系：

- 业务与链上事实边界：以 `01/03` 为准（链上事实优先，DB 为投影）。
- 分层架构：以 `02` 九层模型（`0~8`）为准，本文归属 API 治理与管理后台治理层。
- 路由与状态口径：以 `04 §3.4` 为准；Admin 只读台账以 `04 §3.5` 为准。
- 合约/API/前后端对齐：以 `14` 为准。
- 后台治理能力承接：以 `70`（含 `C-013`）为准。

## 二、版本演进背景

API 从单版本演进到并行版本，以路径版本化作为唯一正式策略：

- `/api/v1/orders`
- `/api/v2/orders`
- `/api/v3/orders`

必须同时满足：

- 旧客户端在兼容窗口内持续可用。
- 新客户端可消费新增字段与能力。
- 后端可在双版本/多版本并行期间稳定提供契约。

## 三、系统目标

1. 兼容可控：旧版本在生命周期内稳定可用。
2. 演进可控：新版本可独立发布、灰度和回滚。
3. 退役可控：`deprecated -> sunset` 有明确窗口、公告和审计。
4. 变更可见：版本差异、字段差异、错误码差异可追溯。

## 五、版本策略

### 5.1 路径版本策略

- 正式 API 必须使用 `/api/v{n}/*`。
- 禁止新增长期无版本正式接口。
- 仅允许在兼容窗口内并行维护多主版本。

### 5.2 兼容策略

- 增量字段默认向后兼容。
- 破坏性变更必须升主版本。
- 关键字段移除必须声明兼容窗口并给出替代字段。

### 5.3 生命周期策略

- `active`：正式支持。
- `deprecated`：进入退役窗口，仍可用。
- `sunset`：窗口结束后下线。

### 5.4 观测与告警策略

- 记录客户端版本与 API 版本使用量。
- 为高风险版本迁移设置告警阈值。
- 对 `deprecated` 版本保留趋势统计，作为 sunset 决策依据。

### 5.5 生命周期状态跃迁治理

| 跃迁 | 触发角色 | 前置条件 | 回退条件 | 审计要求 |
|------|----------|----------|----------|----------|
| `active -> deprecated` | Admin-Backend + Reviewer | 兼容窗口已登记（`compat_window_days`）、迁移公告已发布、回归通过 | 客户端迁移失败率超阈值 | 记录 `actor_id/reviewer_id/reason/before/after/trace_id` |
| `deprecated -> sunset` | Admin-Backend + Reviewer | 活跃客户端占比达阈值、回退预案完成演练、错误码矩阵稳定 | 活跃客户端占比反弹或关键回归失败 | 同上，且附 sunset 公告证据路径 |
| `sunset -> deprecated`（紧急回滚） | Ops + SuperAdmin + Admin-Backend | 事故等级达到回滚触发线、回滚窗口可用 | 事故解除且验证通过后再进入 sunset | 必须关联 incident_id、审批记录与恢复报告 |

## 六、数据模型建议

最小实体：

- `api_versions`
- `api_version_routes`
- `api_version_policies`
- `api_client_usage`
- `api_version_change_logs`

字段级要求：

- `api_versions`：`api_version`、`status`、`released_at`、`sunset_at`。
- `api_version_routes`：`api_version`、`route`、`handler_ref`。
- `api_version_policies`：`breaking_change_rule`、`compat_window_days`。
- `api_client_usage`：`client_id`、`api_version`、`request_count`、`last_seen_at`。
- `api_version_change_logs`：`actor_id`、`change_type`、`before`、`after`。

### 6.1 `/api/v1/admin/api-versions` 最小契约（Implemented（基线））

最小响应字段（`200 ok`）：

- `items[]`：`api_version`、`status`、`released_at`、`deprecated_at`、`sunset_at`
- `items[]`：`compat_window_days`、`active_client_ratio_7d`、`request_count_7d`
- `items[]`：`last_change_at`、`last_change_by`
- `meta`：`generated_at`、`source`（代码当前为 `db`）、`note`、**`build`**（与 **`GET /meta.build`** 同源）

错误码矩阵：

- `401 login_required`
- `403 admin_required`
- `400 invalid_admin_api_version_status_filter`（**可无 DB**）
- `200 ok`
- `503 admin_db_required`

说明：本接口已在 `04 §3.5`/`14` 标注 **Implemented（基线）**；`active_client_ratio_7d` / `request_count_7d` 等观测聚合仍按本文 §五 与 `api_client_usage` 后续阶段补齐。

## 七、核心硬约束

1. Versioned Endpoint Only：新增正式 API 必须带版本。
2. Compatibility Window Required：破坏性升级必须有兼容窗口。
3. Sunset With Notice：下线前必须公告并可观测。
4. Contract Tested：各版本契约必须独立测试。
5. Double-Version Support：关键路径需具备双版本并行期。

## 八、后台模块要求

后台新增一级模块：`API 版本中心`。

子模块（必须）：

- 版本目录
- 路由映射
- 兼容策略
- 废弃与下线计划
- 客户端使用分析
- 变更审计

## 十、发布门禁（可执行）

上线前必须同时满足：

1. 接口契约门禁：新版本接口文档、请求/响应样例、错误码矩阵齐全。
2. 兼容门禁：老版本可用性验证通过，且兼容窗口参数已登记（含 `compat_window_days`）。
3. 迁移门禁：版本切换演练通过并有回退预案。
4. 退役门禁：sunset 计划包含公告窗口、目标客户端覆盖率、回退条件。
5. 审计门禁：版本变更至少有一条成功与一条失败审计样例。

量化阈值（默认门槛，可在 `220` 参数化但不得低于基线）：

- `compat_window_days >= 14`（破坏性变更）。
- `deprecated` 版本活跃客户端占比 `<= 5%` 且连续 `14` 天稳定后，方可进入 sunset 审批。
- 版本回归通过率 `= 100%`（active + deprecated 版本契约测试）。
- 版本切换回滚演练 `RTO <= 30` 分钟，且有可复现演练记录。

建议证据路径模板：

- `evidence/GO_YYYYMMDD/api-versioning/contracts/`
- `evidence/GO_YYYYMMDD/api-versioning/compat/`
- `evidence/GO_YYYYMMDD/api-versioning/sunset/`
- `evidence/GO_YYYYMMDD/api-versioning/audit/`

## 十一、结论

API 版本管理系统是多端长期演进底座。`340` 的价值不在于“单次升级”，而在于建立持续、可观测、可审计的版本治理机制。
