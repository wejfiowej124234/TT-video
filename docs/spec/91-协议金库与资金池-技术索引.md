## 二、结论摘要（必读）

### 2.1 治理金库 vs 「USDT 协议金库」是不是两个东西？

- **`GovernanceTreasury`（治理金库）**：链上单合约；**主要叙事**是 **治理代币（TTG）** 的归集与 **`spend`**（经 **Timelock**）。合约实现为 **通用 ERC20 金库**，**可以**接收 **USDT/USDC**，但 **这不等于**「所有 USDT 只进这一处」。
- **「协议金库」在 84 分轨 B 中的含义**：用户以 **稳定币认购 / 换 TTG / 融资进账** 的资金路径，**会计上**进入 **协议金库及其子科目**（可为 **`GovernanceTreasury` 地址** 或 **披露的多签/托管地址**），详见 **[84 §1.2.1](84-第一阶段10国Country-Pool发行参数总表.md)** 第 2～3 点、**[governance-token/02 §4.7](governance-token/02-对内技术规格-草案.md)**。
- **订单可分配手续费（USDT/USDC 等）**：走 **分轨 A** → **`FeeRouter`** → **国家桶 / Global 三方收款**，**不**与 **分轨 B** 自动混账。

**因此**：**没有**一个独立必部署合约名叫「USDT 专用协议金库」。**USDT 出现在哪**，取决于 **费用**、**认购/换币**、**订单托管**、**质押** 等不同路径；**语义与对账科目不同**。

### 2.2 「一共有多少个金库和池子？」怎么数？

| 数法 | 说明 |
|------|------|
| **严格「金库」合约名** | 本仓库与治理强相关的 **金库型**合约主要是 **`GovernanceTreasury`**（**1** 个部署实例为一组治理栈）；另有 **`ReserveVault`**（罚没准备金托管，**与 FeeRouter 正交**，见下表）。 |
| **费用侧「池」** | **`FeeRouter`** 将单笔费用拆向 **4 个收款地址**：**`countryBucket`**、**`globalStakers`**、**`globalReserve`**、**`globalOps`** —— **4 个资金去向**（实现上可能是 **合约池** 或 **EOA/多签**，以部署为准）。其中 **国家桶** 常见落地为 **`RegionVault`**（**MVP 单实例**）。 |
| **身份质押「池」** | **`GuideIdentityStakingPool`** 与 **`ProviderIdentityStakingPool`** 各 **1** 合约实例 = **2** 个质押池（**81 v2.1**；质押品多为 **USDC** 等，**≠** 治理 TTG）。 |
| **订单托管** | **`Escrow`**：每单独立合约实例（由 **`EscrowFactory`** 部署），**用户本金**，**不是**协议收入金库。 |

**不要**把 **Escrow 余额**、**FeeRouter 暂存余额**、**GovernanceTreasury 余额** 在同一句话里称为「协议金库总池」—— **对账与合规上会错**。

## 四、资金安全硬约束（协议级 · 文档与运维必须一致）

本节解决 **「认知正确 ≠ 系统强制正确」**：链上合约**不会**阻止一笔 USDT 转错地址；**错误不会自动报错**，但会导致 **账错、审计失败、经济模型失真**。下列 **§4.1～§4.6** 为 **硬约束**（会计科目 + 工程意图 + **执行层 UB**）；违反须在 **Runbook / 台账 / PR** 中显式记录并纠偏，**不得**长期「口头对、系统错」。

### 4.1 分轨唯一映射（禁止双计）

- **任何资金路径**（含链下记账、API 归因、报表行）**必须唯一映射**到上文 **§三** 之 **分轨 A** 或 **分轨 B**（或正交路径：**Escrow 用户本金**、**身份质押**、**ReserveVault 罚没准备金** 等 —— 各自独立科目）。
- **禁止**同一笔资金在 **会计或链上意图** 上同时归属 **多个池、多个金库或多个分轨**（例如既当「手续费收入」又当「融资进账」，或同一笔 USDT 同时记入 **FeeRouter 归因** 与 **GovernanceTreasury 募资** 而无调账分录）。
- **工程推论**：后端 **不得**默认「打进 `GovernanceTreasury` 即等于分轨 B」**而不**核对产品定义；**不得**绕过 **`FeeRouter`** 却仍将金额记入 **§1.1 可分配费用** 口径。

### 4.2 FeeRouter 四收款地址（部署与 `/meta` 红线）

**`countryBucket`、`globalStakers`、`globalReserve`、`globalOps`** 在实现上可能是 **合约、多签或 EOA**，且 **可能升级** —— **类型不明 = 资金安全风险**（黑洞地址、权限错误、运维换地址未同步文档等）。

- **生产环境（及对外对账口径）**：上述 **每一地址** 须在 **部署台账** 与 **`GET /api/v1/meta`**（或 **[14](14-合约-API-ABI-前后端对齐.md)** 登记的等价机读字段）中标注：**地址类型**（合约 / 多签 / EOA）、**用途**（国家桶 / TTG 质押激励侧 / 储备侧 / 运营侧等，与 **83/84** 叙事一致）。
- **未同时标注类型与用途的**，**不得**作为 **生产分配** 的终态收款配置对外承诺；须先补齐标注并完成 **Explorer 与 /meta 对键**（见 **[82 §10](82-治理币-文档总览.md)**）。
- **不可变性策略（防「黑箱改址」）**：**`FeeRouter`** 的 **`countryBucket` / `globalStakers` / `globalReserve` / `globalOps`** 一经用于 **生产费用分配**，**不得**由运维以「直接改配置、换私钥、热更新 `.env`」等方式**单独**变更而不留痕。**若须变更**收款配置，**必须**走 **`Governor → Timelock` `execute`**（对 **`setRoutingConfig`** 或等价函数的受控调用）或 **经披露的等价多签 + 链上交易**，并同步 **台账、/meta、84/91、Runbook** 与 **`evidence/.../run_<UTC>/`**。**禁止**资金流已改而系统文档仍显示旧地址 —— 否则 **FeeRouter** 退化为 **可随意改向的黑箱**。

### 4.3 `GovernanceTreasury` 用途边界（防「万能金库」）

- 合约层 **`GovernanceTreasury`** 为 **通用 ERC20** 金库，**技术上可接收任意代币**。
- **在本协议经济语义中**：**仅作为治理支出金库**（**TTG** 为主、经 **Timelock** **`spend`**；分轨 B 稳定币进账须在披露与台账中可审计）。**不得**作为 **订单可分配手续费** 或 **用户托管资金** 的 **默认归集地址**；**不得**因「能收款」即等同于「应进 Treasury」—— **否则分轨 A/B 被打穿**，审计无法区分 **收入 vs 融资**。

**新增硬约束（P0）— 分轨 B 入账入口白名单（唯一入口策略）**：

- **分轨 B（稳定币认购 / 换 TTG / 融资）** 的**入账入口地址**必须属于以下集合之一：  
  - **`GovernanceTreasury` 合约地址**；  
  - **已披露的多签 / 托管地址**（必须在 **`GET /api/v1/meta`** 或部署台账中可机读检索与对键）；  
  - **经治理批准并披露的新入口地址**（`Governor → Timelock` 执行或等价披露流程，且与台账/证据同步）。
- **禁止**：未披露地址作为募资/换币入口；临时地址收款后仅以「口头归类」为金库子账；入口地址漂移而不留痕。
- **一致性要求（强制）**：任何分轨 B 入口地址集合的变更，必须在 **`/meta`**、**`evidence/.../run_<UTC>/`** 与**部署台账**三处可追溯且一致；三者任一缺失或不一致，视为 **未定义行为（UB）**（对账与审计不得依赖其可解释性）。

**新增硬约束（P0）— 治理支出资产分类与 fail-closed**（与 **[governance-token/02 §4.4～§4.6](governance-token/02-对内技术规格-草案.md)** 同源）：

- `GovernanceTreasury` 内资产按**对外解释与风控**至少分为：  
  - **A 类**：治理代币（TTG）；  
  - **B 类**：分轨 B 稳定币（募资 / 换币）；  
  - **C 类**：储备映射资产（Reserve 子账映射或等价披露口径）；  
  - **D 类**：其他 ERC20（必须披露其来源与用途边界）。
- **默认规则（fail-closed）**：任何未被明确分类并披露的资产，**不得**作为治理提案的支出对象（工程上应表现为：治理执行链路拒绝、或 UI/运维 gate 阻断进入可执行队列）；不得以「能 `spend`」推导「应允许支出」。
- **绝对禁止**：任何属于 **Escrow 用户托管资产**（含订单本金）或其等价映射资产，**不得**被治理直接动用（见 **§4.4**）。

### 4.4 `Escrow` 与协议收入隔离（强化）

- **`Escrow` 合约内资产**在任何情况下 **均不属于协议收入**，**不是**资金池、**不是** Revenue 科目。
- **禁止**将 Escrow 余额 **计入** **FeeRouter** 拆分口径、**`GovernanceTreasury`** 收益、**84 §1.1** 可分配费用、或 **任何**「收益分配 / 股东或持有人分配」报表行；**禁止**将 Escrow 当作 **协议自有流动性** 做运营决策而未区分用户债权。

### 4.5 行为强约束（工程执行层 · 受控入口）

**§4.1～§4.4** 多为 **文档与运维纪律**；**链上与后端仍可能「做错但不 revert」**。本小节规定 **业务语义** 上的 **允许路径** —— 违反视为 **未定义行为（Undefined Behavior）**：**不得**依赖其在报表、审计或对外披露中的可解释性。

- **资金进入或协议侧分配**（含稳定币/TTG 的**业务入账与对外划出**）**必须**通过 **受控入口** 完成，例如：**`FeeRouter.distribute`**（分轨 A）、**`GovernanceTreasury.spend`**（经 **Timelock**）、**`EscrowFactory` + `Escrow` 状态机**（用户托管）、**身份质押池** 的 **`stake`/`withdraw`**、**`ReserveVault.withdraw`**（经 Timelock）、**`RegionVault.forward`**（国家桶转出）等 —— **以 Runbook / 14 / 产品定义为准**。
- **禁止**将裸 `ERC20.transfer` / `transferFrom` 作为**常规业务路径**（例如运维脚本直接把 USDT 打进 **`GovernanceTreasury`** 却宣称「手续费」或「融资」）。**例外**：**[82](82-治理币-文档总览.md)**、**contracts/README**、Runbook 已 **逐笔披露** 的 **部署期一次性步骤**（如创始 TTG **`transfer`**）**可**为受控例外，**须** tx 可复核、台账科目已标 **分轨 B** 或 **非分轨 A**。
- **后端与索引器**对链上事件的 **分轨标签**（A/B/Escrow/slash 等）**错误归因**，与 **裸转账** 同属 **高风险 UB**：须按 **§八** 收敛为可校验实现。
- **分轨 B 入口机读对齐**：**`GET /meta` → `governance.treasury_track_b_entrances`**（**`schema=treasury_track_b_entrances_v1`**，含 **`chain_id`** 与 **`entries[]`**）须与 **部署台账**、**`evidence/.../meta.json`** 及 **[04 §3.4](04-后端与API.md)** 对读；**不**写入 **`chain.contracts`** 七键。

### 4.6 资金守恒原则（Accounting Invariant · 审计必问）

**目的**：在 **分轨 A / B、Escrow、质押、Reserve** 并存时，仍能给审计/投资人一句 **「钱可对上」** 的总账骨架（非替代精算或法务收入确认）。

- 在任一 **约定对账窗口**（日 / 轮次 / 审计期；口径由 **Runbook + 产品** 定），**进入协议相关地址体系** 的代币流，**在会计上**应能与下列 **科目桶** **闭合**（与链上余额 + 台账一致，允许已定义 **流出**）：**`Escrow` 托管**、**`FeeRouter` 及四向拆分后子余额**、**`GovernanceTreasury`（及披露之托管/多签）**、**`ReserveVault`**、**身份质押池**、**`RegionVault`** 等 —— **外加** **手续费、退款、冲销、跨期、gas、rounding** 等 **已解释偏差**。
- **任一闭合偏差**须能在 **链上 tx / 事件** 或 **台账分录** 中指到 **唯一解释**；**禁止**「收入算多/算少」长期无说明。**本公式为协议级检查清单**，具体 **资产范围与窗口边界** 以 **84 §1.2.1**、**Runbook §7.1**、法务口径为准。

| **投资者分配（如部署）** | `InvestorDistributionClaim.sol` 等 | 认领/分配叙事 | 与 **84/83** 披露一致时单独对账 |

## 六、冲突时信谁（与 82 §10 一致）

当 **`.env`、`/meta`、Explorer、证据目录** 不一致时：**以链上已确认交易与合约状态（Explorer 可复核）为最终真值**；其余为派生态，须回填修复。详见 **[82-治理币-文档总览 · §10](82-治理币-文档总览.md)**「最终一致性原则（SSOT 优先级）」。

### 6.1 跨网络一致性原则（Multi-Chain Consistency）

上文 **单链 / 单环境 SSOT** 在 **多网络** 场景下必须 **显式拆分**，否则审计与运维会把 **testnet 地址**、**mainnet 分轨**、**indexer 重跑后的投影** 混为同一叙事。

- **不同链**（local Anvil / testnet / mainnet / 未来多 region 部署）上的 **合约地址、FeeRouter 配置、`chain.contracts` 分轨语义** **不得混用**；**禁止**用 **A 链** 的 `/meta` 或台账去解释 **B 链** 的 Explorer 状态作为「同一真值」。
- **`GET /api/v1/meta`**、**台账、 indexer 游标、`evidence/.../run_<UTC>/`** 均须带 **`chainId`（及网络标签，如 sepolia / mainnet）**；**fork / replay / 索引重建** 后若与历史 run 对照，**须**在证据或 Runbook 中说明 **重建范围**，**禁止**默认同名目录跨链混指。
- **跨链桥 / 多链产品**（若未来纳入）须 **单独** SSOT，**不得**并入本节默认单链公式而不加 **per-chain** 附件。

### 七点五、线 A 验收 PASS 判据（可粘贴为验收结论）

**线 A** = **`FeeRouter` + `GET /meta` + 分轨 A/B** 专项验收（与 **Governor/Timelock 执行链** **正交**）。**全文展开、FAIL 句与演练上下文**见 **[Runbook §7.1 · 线 A · 验收结论模板](../../ops/RUNBOOK.md#line-a-feerouter-pass)**。

**PASS（线 A）**（**须全部满足**）：

1. **`chain_id`** 全链路一致  
2. **`/meta` 七键**与部署台账一致  
3. **Track B** 入口机读存在且与披露一致  
4. **FeeRouter** 四向地址链上可读且用途一致  
5. **分轨 A/B** 在 **`event_log`** 与 **API** 中一致表达  
6. **projection** 数据未被误用为链上 **SSOT**

### 8.1 不可降级保证（防「文档强于实现」倒挂）

上表所列 **仍为 Target 或未写「已落地」之条目** 为 **未来实现的最低标准**；**已落地** 行 **不得在无迁移/评审下回退**。**实际交付的校验与对账能力不得弱于上表约束**（例如「简化版」跳过 **分轨标签**、**FeeRouter 对键** 或 **证据分类**）。若工程上确需减弱自动化或缩小范围，**必须** **同步修订本文 §四～§八 与 84/02/Runbook**、**bump 版本** 并 **重新走审计/披露闭环** —— **禁止**在弱实现下长期宣称 **91** 与 **84 §1.2.1** 已等价满足。

### 8.2 证据不可抵赖（防封口后篡改）

**`run_<UTC>/` 目录 + 封口脚本** 解决「**有据**」；**「不可抵赖」** 由 **工程落地**：**[`evidence_run_sha256_manifest.py`](../../scripts/ops/evidence_run_sha256_manifest.py)** 生成 **`evidence_sha256_manifest.json`**（`schema`: **`traveltrust.evidence_sha256_manifest.v1`**）及侧车 **`evidence_sha256_manifest.sha256`**（**JSON 文件本身** 的哈希，防改 manifest）。**`python3 … verify <dir>`** 重算各文件与侧车。**[`tt-testnet-fullstack-seal.sh`](../../scripts/ops/tt-testnet-fullstack-seal.sh)** 封口末段 **默认** 调用 **generate**（无 Python 时 **WARN** 跳过）。**链上锚定** manifest 哈希仍为 **可选增强**（未在仓库强制）。**禁止**在声称「已封口」后 **无记录地替换** `run_<UTC>/` 内文件；任何补正须 **新 run** 或 **显式勘误段落** 可追溯。

**边界**：本节 **不**替代法务对 **收入确认、托管、证券** 的结论；**链上不可逆** 见 **[82 §10](82-治理币-文档总览.md)**「链上不可逆声明」。

### 8.3 后续增强（非当前阻塞）

- **同 tx「多轨合规」**：若未来允许 **单笔交易** 同时产生 **Escrow 类** 与 **FeeRouter 类**（或其它组合）日志，须在 **放开写入** 之前单独立项：**允许的组合**、**冲销 / 双分录规则**、**报表与对账拆分口径**；在此之前 **`event_log` 同 tx 单轨 / 禁混轨** 的 **严格失败** 为 **正确默认**。
- **侧带事件表**：**`investor_share_transfer_events` / `investor_stake_state_events` 等** 当前 **不经** **`event_log`** 主合并流；若纳入 **核心对账**，再评估 **`track_type`、统一校验框架、reconcile 二次校验**。
