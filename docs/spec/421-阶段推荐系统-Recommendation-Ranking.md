## 一、文档定位

本文定义 TravelTrust 在 421 阶段的“推荐与排序系统”开发规范。

421 阶段用于建立从“按时间排序”升级到“按价值与个性化排序”的平台能力。

## 二、建设背景

平台后期必须具备推荐能力：

- 推荐向导
- 推荐城市
- 推荐路线
- 推荐热门行程
- 推荐评价高的向导
- 推荐相似订单

如果没有独立推荐层，系统会长期停留在时间排序，难以支撑增长和转化。

## 三、系统目标

1. 排序可计算：统一 ranking/scoring 管线。
2. 规则可配置：weight、feature、热度策略可迭代。
3. 结果可解释：可追溯推荐结果主要得分来源。
4. 人群可细分：支持个性化和分层推荐策略。

## 四、核心能力（必须具备）

必须具备：

- `ranking`
- `scoring`
- `weight`
- `feature`
- `热度`
- `个性化`

## 五、系统架构建议

### 5.1 Candidate Recall

候选召回层：

- 城市候选集
- 向导候选集
- 行程候选集
- 相似订单候选集

### 5.2 Ranking Layer

排序层：

- 统一评分函数
- 特征加权
- 分桶与重排
- 去重与多样性约束

### 5.3 Serving Layer

推荐服务层：

- 实时推荐 API
- 缓存与降级策略
- 实验版本切换

## 六、数据模型建议

建议最小实体：

- `rec_models`
- `rec_features`
- `rec_weights`
- `rec_rank_runs`
- `rec_results`
- `rec_feedback_events`

字段级要求：

- `rec_models`：`model_id`、`model_name`、`version`、`status`。
- `rec_features`：`feature_id`、`feature_name`、`feature_type`、`source`。
- `rec_weights`：`model_id`、`feature_id`、`weight`、`effective_from`。
- `rec_rank_runs`：`run_id`、`scene`、`model_version`、`latency_ms`。
- `rec_results`：`request_id`、`entity_id`、`score`、`rank`、`reason_tags`。
- `rec_feedback_events`：`user_id`、`scene`、`entity_id`、`action_type`、`occurred_at`。

## 七、评分框架建议

### 7.1 基础分

- 实体质量分（评分、投诉率、履约率）
- 内容质量分（完成度、互动质量）

### 7.2 热度分

- 近期浏览/点击/收藏/下单趋势
- 时间衰减处理

### 7.3 个性化分

- 用户历史偏好（国家/城市/预算/风格）
- 相似用户偏好
- 行为反馈闭环

### 7.4 业务约束分

- 风险惩罚（高风险账户降权）
- 合规约束（地区限制）
- 多样性约束（避免单一来源垄断）

## 八、后台模块要求

后台新增一级模块：`推荐系统中心`

子模块（必须）：

- 模型与版本
- 特征管理
- 权重管理
- 推荐场景配置
- 结果分析
- 实验与回滚

## 九、实施计划（421 阶段）

### 9.1 P0（必须）

- 建立候选召回 + 排序 + 服务三层架构。
- 覆盖向导、城市、路线、热门行程四大推荐场景。
- 落地基础 scoring + weight 配置。

### 9.2 P1（增强）

- 个性化特征接入与分层推荐。
- 多场景 AB 实验与自动评估。

### 9.3 P2（规模化）

- 多目标排序（转化、满意度、风控约束）联合优化。
- 在线学习或准实时权重更新。

## 十、发布门禁

1. 核心场景推荐结果可用，不再仅按时间排序。
2. 排序得分可回放、可解释。
3. 权重变更支持灰度和回滚。
4. 推荐性能和稳定性达到门槛。

## 十一、结论

推荐系统是平台增长与用户体验提升的关键引擎。没有 421 阶段，平台将停留在低效排序模式。
