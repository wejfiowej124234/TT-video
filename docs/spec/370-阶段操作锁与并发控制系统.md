## 一、文档定位

本文定义 TravelTrust 在 370 阶段的“操作锁与并发控制系统”开发规范。

370 阶段用于解决多角色并发写冲突，防止资金错账、状态乱跳与重复执行。

## 二、并发参与方

系统并发写入主体包括：

- 游客
- 向导
- 客服
- 仲裁
- 管理员
- 后端任务
- indexer

高风险并发场景：

- 同时改订单
- 同时改状态
- 同时执行结算
- 同时仲裁

## 三、必备能力（必须具备）

- `row lock`
- `optimistic lock`
- `version check`
- `distributed lock`

## 四、系统目标

1. 并发可控：同一对象写操作有序化。
2. 冲突可见：冲突即时识别与反馈。
3. 执行可幂等：重复请求不重复生效。
4. 资金可保护：结算与仲裁操作避免双执行。

## 五、控制策略

### 5.1 行级锁

用于短事务关键写保护，防止并发覆盖。

### 5.2 乐观锁 + 版本检查

- 实体维护 `version` 字段。
- 更新时校验 `expected_version`。
- 冲突返回显式错误并触发重读。

### 5.3 分布式锁

- 对跨服务关键操作加分布式锁。
- 需含超时、续约、释放与死锁检测。

### 5.4 幂等与去重

- 关键写动作强制 idempotency key。
- 关键资金动作必须去重检查。

## 六、数据模型建议

建议最小实体：

- `entity_versions`
- `concurrency_locks`
- `operation_idempotency`
- `concurrency_conflicts`

字段级要求：

- `entity_versions`：`entity_type`、`entity_id`、`version`、`updated_at`。
- `concurrency_locks`：`lock_key`、`owner`、`expires_at`、`status`。
- `operation_idempotency`：`idempotency_key`、`operation_type`、`result_digest`。
- `concurrency_conflicts`：`entity_id`、`actor_a`、`actor_b`、`detected_at`。

## 七、核心硬约束

1. Version Required：关键实体写入必须带版本校验。
2. Lock Before Critical Write：高风险写操作先取锁再执行。
3. No Double Settlement：结算/仲裁执行必须防双触发。
4. Conflict Observable：并发冲突必须记录并告警。

## 八、后台模块要求

后台新增一级模块：`并发控制中心`

子模块（必须）：

- 锁状态总览
- 冲突事件
- 幂等记录
- 异常修复

## 九、实施计划（370 阶段）

### 9.1 P0（必须）

- 引入版本检查与行级锁。
- 引入关键操作分布式锁。
- 引入幂等与冲突审计。

### 9.2 P1（增强）

- 自动冲突恢复策略。
- 锁竞争可视化与优化。

### 9.3 P2（规模化）

- 跨区域并发控制统一策略。
- 锁服务高可用治理。

## 十、发布门禁

1. 关键对象更新必须版本校验。
2. 资金类操作并发冲突测试通过。
3. 锁异常可发现可恢复。

## 十一、结论

并发控制系统是资金与状态一致性的保险丝。没有 370 阶段，资金错账与卡单会长期存在。
