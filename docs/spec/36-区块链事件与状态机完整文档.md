## 1. 订单状态机 (Order State Machine)

### 1.1 核心状态图

```
┌─────────┐
│  Draft  │  P15/17 ① 行程生成层
└────┬────┘
     │ (游客确认行程，生成订单)
     ↓
┌─────────┐
│ Created │  Orders.status='created', escrow=null
└────┬────┘
     │ (向导接单)
     ↓
┌─────────┐
│Accepted │  Orders.status='accepted', escrow=null, guide_id 已绑定
└────┬────┘
     │ (游客支付进escrow)
     ↓
┌──────────┐
│ Escrowed │  Escrow.status=Funded, orders_projection.status='escrowed'
└─────┬────┘  [单位：Wei, chain=Escrow.sol状态]
      │
      ├─→ (向导完成, 游客确认) ─────┐
      │                         ↓
      │                    ┌───────────┐
      │                    │Completed  │  Escrow.status=Completed
      │                    │           │  orders_projection.status='completed'
      │                    │ [资金终态]│
      │                    └───────────┘
      │
      └─→ (游客发起退款) ───────┬─────┐
          (向导同意) ──────┐   │     │
                          ↓   ↓     ↓
                    ┌──────────────────────┐
                    │    Disputed          │  Escrow.status=Disputed
                    │                      │  orders_projection.status='disputed'
                    └────────┬─────────────┘
                             │
                    ┌────────┴─────────┐
                    │                  │
                    ↓                  ↓
            ┌──────────────┐   ┌─────────┐
            │Refunded /    │   │Slashed  │
            │PartiallyRef  │   │         │
            │ [资金终态]   │   │[资金终态]│
            └──────────────┘   └─────────┘
```

### 1.2 状态转移表 (Legal Transitions)

| 当前状态 | 允许的下一状态 | 触发事件 | 规范来源 |
|---------|--------|---------|---------|
| Draft | Created, Cancelled | 订单确认/超时取消 | P15/17① |
| Created | Accepted, Cancelled | 向导接单/超时取消 | 01§1 |
| Accepted | Escrowed, Cancelled | 游客支付/取消 | 01§1 |
| Escrowed | Completed, Disputed | order.release() / order.openDispute() | 01§5-7 |
| Disputed | Completed, Refunded, PartiallyRefunded, Slashed | executeResolution() | 01§7.3 |
| Completed | (terminal) | — | 01§5.2 |
| Refunded | (terminal) | — | 01§5.3 |
| PartiallyRefunded | (terminal) | — | 01§5.3 |
| Slashed | (terminal) | — | 01§7.3 |
| Cancelled | (terminal) | — | 01§5 |

### 1.3 资金流向 (Fund Flow per State)

```
Draft → Created → Accepted → Escrowed → [Completed / Refunded / PartiallyRefunded / Slashed]
         (¥0)     (¥0)      (¥X in escrow)   (release / refund / slash)
                                              
资金位置: 
  Draft/Created/Accepted: 【游客钱包】
  Escrowed: 【Escrow合约】
  Completed: 【向导钱包】+ 【平台费钱包】
  Refunded: 【游客钱包】
  Slashed: 【待执行队列】(executor 从 escrow 扣罚)
```

## 2. 链事件与Escrow.sol状态机

### 2.1 Escrow.sol 状态枚举

```solidity
enum Status {
    None,      // 0: 未初始化
    Created,   // 1: init() 后
    Funded,    // 2: deposit() 后
    Completed, // 3: release() 后 → terminal
    Refunded,  // 4: refund() 后 → terminal
    Disputed,  // 5: openDispute() 后
    Resolved   // 6: executeResolution() 后 → terminal
}
```

### 2.2 Escrow.sol 事件清单

| 事件 | 触发函数 | 参数 | 映射到 Order状态 | 规范 |
|------|---------|------|-----------------|------|
| **EscrowCreated** | init() | orderId, escrow, traveler, guide, token, amount, fee%, snapshotHash, schemaVersion | Created | 01§4.1 |
| **Deposited** | deposit() | orderId, escrow, from=traveler, amount | Escrowed | 01§5.1 |
| **Released** | release() | orderId, escrow, guideAmount, platformFee | Completed | 01§5.2 |
| **Refunded** | refund() | orderId, escrow, travelerAmount | Refunded | 01§5.3 |
| **DisputeOpened** | openDispute() | orderId, escrow, opener, reasonHash | Disputed | 01§7.1 |
| **ResolutionExecuted** | executeResolution() | orderId, escrow, resolutionId, decisionHash | Completed\|Refunded\|PartiallyRefunded\|Slashed | 01§7.3 |

### 2.3 事件 → DB 投影 (Indexer Handler)

```
Escrow.sol Event (on-chain)
    ↓ (Indexer 扫描 event_log)
event_log 表 (append-only)
    ↓ (Handler 消费 event_log)
orders_projection 表 (链上订单快照)
    ↓ (API 读取投影)
前端 / 仲裁系统 / 执行器
```

**例**:
```python
# Indexer 拉取链事件
event = chain.get_event(tx_hash, log_index)  # Deposited(orderId=0xabc..., amount=100e6)

# 入库 event_log
event_log.insert(
    event_type="Escrow.Deposited",
    payload={"orderId": "0xabc...", "amount": "100000000"},
    block_number=12345,
    log_index=0,
    finality_n_used=12  # 确认深度
)

# Handler 消费，更新投影
orders_projection.update(
    order_id=0xabc,
    status="escrowed",
    paid_at_block=12345,
    paid_at_log_index=0,
    updated_at=now()
)
```

## 3. Chain vs Chain_off 模式

### 3.1 架构对比矩阵

| 维度 | Chain 模式 | Chain_off 模式 (MVP) |
|------|----------|------------------|
| **Escrow部署** | 每订单 new Escrow() 合约实例 | 无合约，DB + 签名验证 |
| **资金托管** | 链上 ERC20 transfer 到 Escrow 合约 | DB 记录，模拟转账 |
| **状态来源** | Escrow.status（合约状态） | DB orders.status（链下） |
| **终态确认** | N-finality 区块确认 + ReadOnly quorum | 数据库事务 ACID |
| **费用支付** | on-chain transfer + gas fee | 模拟，无实际支付 |
| **DID/Registry** | 链上 Registry.approve() | DB guides.status + 签名 |
| **争议仲裁** | 链上 executeResolution() | DB disputes.resolution + executor.sign() |
| **数据恢复** | Event replay from event_log | DB transaction log |

### 3.2 代码中的 Chain_off 条件分支

```rust
// crates/api/src/routes/orders/mod.rs（及 mutations.rs / reviews.rs）
pub async fn order_confirm_completion(
    State(state): State<ApiMetaState>,
    ...
) -> impl IntoResponse {
    if let Some(ref co) = state.chain_off {
        // === Chain_off 模式 ===
        let uid = extract_user_with_session_check(&state, &headers).await?;
        let order = db::get_order(&co.db_pool, order_id).await?;
        
        // 直接在 DB 中模拟状态转移
        db::update_order_status(&co.db_pool, order_id, "completed").await?;
        
        return json_response(OrderResponse { status: "completed" });
    }
    
    // === Chain 模式（生产） ===
    // 调用 chain::escrow::confirm_release(&state.chain_config, order_id)
    // 生成链上交易，等待 indexer 投影
}
```

**关键观察**:
- 所有 route handler 都有该分支
- Chain_off 路径: 直接 DB 操作 + 模拟响应
- Chain 路径: 构造合约调用 + 等待事件投影

### 3.3 配置切换


## 4. Indexer 与事件处理流程 (spec 48 §12)

### 4.1 Indexer 架构

```
RPC Node (Ethereum/Polygon/...)
    ↓ (JSON-RPC eth_getLogs)
Indexer (crates/api/src/chain/indexer.rs)
    ↓ getLatestBlock(), get_events_range(from_block, to_block)
    ↓ (批量拉取 logs)
    ↓
event_log 表
    ↓ (按消费者分片进度)
checkpoints_sharded 表 (consumer_id → last_block)
```

### 4.2 Indexer 迭代过程 (POST /api/v1/internal/indexer-tick)

```
Iteration N:
┌─────────────────────────────────────────┐
│ 1. 读 checkpoints_sharded 获取上次进度  │
│    (consumer_id="handler_escrow", block=9000)
└────────────┬────────────────────────────┘
             ↓
┌─────────────────────────────────────────┐
│ 2. 调用 RPC get_latest_block()          │
│    latest_block = 9012
└────────────┬────────────────────────────┘
             ↓
┌─────────────────────────────────────────┐
│ 3. 范围查询 (from_block=9001, to_block=9012)
│    拉取所有 EscrowFactory.EscrowCreated  │
│           + Escrow*.Deposited/Released  │
│           + Registry.Approved           │
└────────────┬────────────────────────────┘
             ↓
┌─────────────────────────────────────────┐
│ 4. 插入 event_log (append-only)         │
│    每条事件一行                          │
└────────────┬────────────────────────────┘
             ↓
┌─────────────────────────────────────────┐
│ 5. 遍历 event_log，更新投影表           │
│    switch(event_type) {                 │
│    EscrowCreated → orders_projection... │
│    Deposited → orders_projection.status │
│    DisputeOpened → orders_projection... │
│    ExecutionResolved → ...              │
│    }                                     │
└────────────┬────────────────────────────┘
             ↓
┌─────────────────────────────────────────┐
│ 6. 更新 checkpoints_sharded             │
│    (consumer_id, block=9012)            │
└─────────────────────────────────────────┘

Result: Indexer 追进（同步延迟 < 1分钟）
```

### 4.3 N-Finality 确认机制 (spec 48 §12.3)

```
Event 在 Block 12345 产生
    ↓
Block 12345 + 11 = Block 12356 时
    ↓ (N-finality, N=12)
视为 "确认" (finality_n_used=12)
    ↓
orders_projection.status 才能用于
  - 订单完成判定
  - 用户资金查询
  - 仲裁决策

早于 Block 12356 的查询：
  - orders_projection.status = "pending"（保守估计）
  - orders.status 作为备用源（链下快照）
```

**代码**:
```rust
// crates/api/src/chain/indexer.rs
async fn handle_deposited_event(&event: &Event) {
    if event.block.number + FINALITY_N > current_block {
        // 未确认，放入 pending 队列
        return;
    }
    // 已确认，更新投影
    orders_projection.update(...);
}
```

## 5. 执行器 (Executor) 与上链流程 (spec P5-4)

### 5.1 裁决循环

```
仲裁员在 Web UI 提交裁决
    ↓ (POST /api/v1/disputes/:id/resolve)
    ↓
disputes 表 update (status=resolved, refund_ratio=0.5)
    ↓
后端生成 "意图"
    ├─ resolutionId = hash(chainId, orderId, resolutionSeq, decisionHash)
    ├─ guideAmount, travelerRefund, platformFee (按 refund_ratio 计算)
    └─ store in executor_executions (status='pending')
    ↓
Executor 定期轮询 (POST /api/v1/internal/process-resolution-outbox)
    ↓
┌──────────────────────────────────────────┐
│ 1. 读 executor_executions 查找 pending   │
│    resolutionId=0x1234..., status=pending│
└─────────────┬──────────────────────────┘
              ↓
┌──────────────────────────────────────────┐
│ 2. 构造链上交易                          │
│    escrow.executeResolution(             │
│      resolutionId,                       │
│      decisionHash,                       │
│      guideAmount=50e6,                   │
│      travelerRefund=50e6,                │
│      platformFee=0                       │
│    )                                     │
└─────────────┬──────────────────────────┘
              ↓
┌──────────────────────────────────────────┐
│ 3. 签名 + 广播交易                       │
│    tx_hash = send_to_rpc(tx)             │
└─────────────┬──────────────────────────┘
              ↓
┌──────────────────────────────────────────┐
│ 4. 更新 executor_executions              │
│    executor_executions.tx_hash = 0x...   │
│    executor_executions.status = 'executed'
└──────────────────────────────────────────┘
              ↓
Indexer 拉取链事件
    ↓
event_log 插入 ResolutionExecuted
    ↓
orders_projection 更新 (status=resolved)
    ↓
前端轮询，显示 "仲裁已执行"
```

### 5.2 执行器错误恢复

```
Executor 失败场景（network error / account insufficient balance）:
    ↓
executor_executions.status = 'failed'
    ↓
后续 Executor 轮次重试（最大 X 次）
    ↓ (若 X 次失败后仍 pending)
alert_admin() → 人工审查完成
```

## 7. 争议仲裁流程 (spec 01 §7)

### 7.1 仲裁状态机

```
客户端提供证据（hash）
  ↓
disputes 表 INSERT (status='open')
  ↓
后端分配仲裁员 (arbitrator_id)
  ↓
disputes 表 UPDATE (status='assigned')
  ↓
仲裁员审核证据 + 链下订单快照（orders_projection）
  ↓
仲裁员做出决策（refund_ratio, slash_guide）
  ↓
disputes 表 UPDATE (status='resolved', refund_ratio, slash_guide)
  ↓
Executor 自动上链执行 (executeResolution)
  ↓
Indexer 投影 ResolutionExecuted 事件
  ↓
orders.status ← Completed | Refunded | PartiallyRefunded | Slashed
```

### 7.2 证据哈希验证 (proof-of-existence)

```solidity
// Escrow.sol openDispute()
function openDispute(bytes32 reasonHash) external {
    // reasonHash = keccak256(证据打包体)
    // 证据本身不上链（gas 成本），仅记录哈希
    status = Status.Disputed;
    emit DisputeOpened(orderId, msg.sender, reasonHash);
}

// 仲裁员可通过 keccak256(链下证据) 与 reasonHash 对比验证
```

## 9. 链重组 (Reorg) 场景

### 9.1 区块重组处理

```
正常场景：
  Block 12345: Deposited Event
  Block 12346, 12347, ..., 12356 (N=12)
  → finality_n_used=12 ✓

重组场景：
  Block 12345: Deposited Event
  [网络分叉]
  Chain A: Block 12346, 12347, ..., 12356 (长链)
  Chain B: Block 12346', 12347' (短链，被淘汰)
  → Nodes 切回 Chain A
  → Indexer 检测到 reorg
  ↓
Correction Log:
  - correction_type='reorg'
  - payload={from_block: 12346, to_block: 12356}
  ↓
重新拉取 [12346, latest] 之间的所有事件
  ↓
orders_projection 修正（覆盖写）
```

**检测机制**:
```rust
// crates/api/src/chain/indexer.rs
if current_block < last_checkpoint_block {
    // Reorg detected
    log_correction(ReorgReason { from: current_block, to: last_checkpoint_block });
    resync_from_block(current_block);
}
```

## 10. 完整端到端示例

### 10.1 订单完成：Chain 模式

```
T0: 游客创建订单
    Order{id=O1, status='created', tourist_id=U1, guide_id=G1}

T1: 向导接单
    Order{status='accepted', accepted_at=T1}

T2: 游客点击"支付"
    ↓ POST /api/v1/orders/O1/pay
    ↓ (Chain 模式)
    ↓ Backend 组装交易，调用 escrow.deposit(amount)
    ↓ 前端显示钱包确认弹窗
    ↓ 游客批准交易
    ↓ Tx Hash = 0xabc...

T3: Indexer 轮询检测到事件
    event_log.insert({
        event_type='Escrow.Deposited',
        tx_hash=0xabc,
        block_number=12345,
        payload={orderId, amount, block_timestamp}
    })

T4: Handler 投影
    orders_projection.update({
        order_id=O1,
        status='escrowed',
        paid_at_block=12345,
        escrow_address=0x1234...
    })

T5: 链下确认行程完成（**非**链上放款）
    参与方触发 `POST /api/v1/orders/O1/confirm-completion`
    ↓ 仅更新链下业务进度（如 completed_at / sub_status；**不**在本步调用 `escrow.release`，见 [04](04-后端与API.md) §3.4、[53](53-阶段开发技术文档.md)）

T6: 行后评分（53 Happy 路径，若适用）
    `POST /api/v1/orders/O1/reviews`（及可选 `confirm-rating`）
    ↓ 业务侧满足「评分与双方确认」等释放前置后，才进入 T7

T7: 链上释放
    用户钱包签 `Escrow.release()`（或执行器/超时路径，01/03）
    ↓ Tx Hash = 0xdef...

T8: Indexer 检测
    event_log.insert({
        event_type='Escrow.Released',
        tx_hash=0xdef,
        block_number=12350
    })

T9: Handler 投影
    orders_projection.update({
        status='completed',
        completed_at_block=12350
    })

T10: 用户查询状态
    GET /api/v1/orders/O1
    ↓ Backend 读 orders_projection
    ↓ status='completed' ✓
    ↓ 前端展示与 04 状态枚举一致

T11: 评价与信誉
    评价提交时点与终态校验以 [04](04-后端与API.md) §3.4、[53](53-阶段开发技术文档.md) 为准；`reviews.insert`、信誉汇总等与实现一致
```

### 10.2 订单纠纷：Chain 模式

```
T<n>: 游客发起争议（在 dispute_deadline 前）
    POST /api/v1/orders/O1/dispute
    ↓
    disputes.insert({
        order_id=O1,
        status='open',
        evidence_hashes=['0xhash1', '0xhash2']
    })
    ↓
    后端生成离链签名证明（intent）
    ↓
    orderentIntentQueue.push({
        type='open_dispute_intent',
        order_id=O1,
        signature=...
    })

T<n+1>: 仲裁员分配（自动 or 手动）
    disputes.update({arbitrator_id=A1, status='assigned'})

T<n+2>: 仲裁员审核 & 做决定
    仲裁员进入后台，查看：
    - orders 详情
    - 争议原因（evidence_hashes 对应的证据）
    - 游客/向导的聊天记录
    ↓
    做出决策：refund_ratio=0.5, slash_guide=true
    ↓ PATCH /api/v1/disputes/D1/resolve
    ↓
    disputes.update({
        status='resolved',
        refund_ratio=0.5,
        slash_guide=true,
        resolved_at=now()
    })

T<n+3>: Executor 周期巡检
    POST /api/v1/internal/process-resolution-outbox
    ↓ 读 disputes 表
    ↓ 构造链上交易：
       escrow.executeResolution(
         resolutionId=hash(chainId=1, orderId=O1, resolutionSeq=1, decisionHash=hash(O1,0.5)),
         decisionHash=...,
         guideAmount=50e6,
         travelerRefund=50e6,
         platformFee=0
       )
    ↓ executor_executions.insert({tx_hash=0xghi...})

T<n+4>: Indexer 投影
    event_log.insert({
        event_type='Escrow.ResolutionExecuted',
        block_number=12360,
        payload={orderId=O1, decisionHash, guideAmount, ...}
    })
    ↓
    orders_projection.update({
        status='partially_refunded',  // 因为 refund_ratio=0.5
        resolution_type='mediated'
    })

T<n+5>: 用户查询状态
    GET /api/v1/orders/O1
    ↓ status='partially_refunded' ✓
    ↓ 前端显示 "仲裁已完成，已退款 50%"
```

## 11. 监控 & 告警

### 11.1 关键指标

```
Indexer 健康度:
  - last_indexed_block vs current_block (延迟 < 1分钟 正常)
  - event_log.insert_rate (预期 100-1000 events/min)
  - finality_n_stuck_events (预期 < 10)

Orders 健康度:
  - orders.status='escrowed' 数量 (快速增长 = 活跃)
  - orders_projection vs orders 状态一致性 (偏差 < 1% 正常)
  - disputes.status='pending' 数量 (< 100 正常)

Executor 健康度:
  - executor_executions.status='pending' 数量 (< 50 正常)
  - failed_executions_7d 数量 (0 最佳)
  - resolution_execution_latency (P95 < 5分钟 目标)
```
