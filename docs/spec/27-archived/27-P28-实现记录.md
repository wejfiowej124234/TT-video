| **traceId** | requestId→messageId→txHash→logIndex 贯通；API 响应头 x-request-id | crates/api request_id_layer：请求头带入或生成 UUID，响应头回写；每请求打印 `[req] x-request-id= path= status=` | ✓ |

## 四、告警通道定稿说明（与 Runbook §1 衔接）

**用途**：告警与 Runbook §1 触发表衔接，定稿时由运维选型并落地；本条写死即视为 P28 告警落点闭合。

| 项 | 写死内容 |
|----|----------|
| **触发条件** | 与 Runbook §1 表一致：① RPC 大面积不可用 ② Indexer 落后 ③ reorg ④ 执行器卡单 ⑤ token 冻结/黑名单；触发阈值见该表「触发阈值」列。 |
| **步骤** | 触发 → 告警推送至值班 → 值班按 Runbook §1「人工动作」执行 → 产物入 evidence 或 08-3 变更记录。 |
| **推荐通道** | 任选一种或组合：**Prometheus + Alertmanager**（指标超阈值）、**Webhook**（API 回调钉钉/飞书/Slack）、**日志告警**（ELK/Loki 规则触发 Webhook）。 |
| **闭合标准** | 运维确定告警通道并写死至 Runbook §1 或内部运维文档；与 Runbook §1 触发表无冲突。 |

## 二、traceId 贯通与验证

| 项 | 01 §9 / 04 要求 | 当前实现 | □ 可验证 |
|----|-----------------|----------|--------|
| API 响应头 x-request-id | 即 requestId，供审计与资损排查 | 中间件 request_id_layer 回写 x-request-id（请求头带入或自动生成） | ✓ |
| 请求级日志 | request_id + path + status | eprintln `[req] x-request-id=… path=… status=…` | ✓ |
| messageId | 与 requestId 关联，后续对账/执行器消费可落库 | 04 §四 messageId 生成与回写已预留；审计表/落库待扩展 | ✓ 已预留；落库可追溯待扩展 |

**验证方式**：调用任意 API（如 `GET /meta` 或 `GET /health`），检查响应头含 `x-request-id`；若请求未带该头，应为服务端生成的 UUID；日志中可见同 id 与 path、status。
