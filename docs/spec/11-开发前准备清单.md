## 五、项目宪法（一句话）

在开始任何 UI/前端设计前，须锁死**项目定位**与**设计优先级**：

- **定位**：TravelTrust 是基于 EVM 的去中心化旅游托管协议；资金状态以链上事件为真相；前端仅用于签名与状态展示。
- **设计优先级**：可信度 > 清晰度 > 一致性 > 美感 > 动效。
- **资金区**：必须严肃、留白、信息优先；禁止渐变/炫光/跳动数字/3D 侵入。
- **3D**：仅用于 Landing Hero、品牌演绎、资金流抽象可视化；不进入 EscrowDetail、Dispute、Governance。

详见 [08-4](08-4-对外口径包.md)、[05](05-前端总览.md) §九、[13](13-协议级UI设计宪法.md)。对应 §一 项 1、11。

## 六、SSOT 与事件契约（必含四块）

单源真相（SSOT）建议包含且不少于：

1. **State Machine**：订单与争议状态、合法迁移、非法转移禁止（§一 项 3）。
2. **Invariants**：资金、权限、幂等、审计（[10](10-系统级不变量白皮书-v1.0.md)；§一 项 2）。
3. **Events**：字段、indexed、**schemaVersion**（§一 项 4）。
4. **Reorg & Replay Rules**：finalityN、回退窗口、投影重建、幂等与重复消费（10 §7；§一 项 8、10）。

## 九、开发前清单「可以开工」标准与两项风险提醒

### 9.1 何时达到「可以开工」

当 §一 A～F 中下列项已定稿或就绪时，可认定开发前清单达到**可以开工**标准（按工程总设计施工，而非边写边想）：

- 项目定位声明、不变量白皮书、状态机 SSOT、事件契约  
- 合约接口规范、升级策略、安全模型  
- 索引器设计、DDL 草案、投影与对账策略  
- UI 宪法（协议级 UI 设计宪法）、Release Gate、提交规范（见 [12-应提交与不应提交清单](12-应提交与不应提交清单.md)）

从工程标准看，此时已具备：**架构完整性、治理闭环、参数可控性、不变量约束、CI 阻断机制、UI 宪法、发布门禁思维**。所缺的是**第一版最小闭环代码**，不是「标准」本身。

### 9.2 ⚠ 风险一：复杂度压垮开发节奏

当前文档体系已接近**企业级 1.5 期**。若尚未跑通最小资金闭环：

**createOrder → fund → complete → dispute → resolve**

则文档复杂度会**反向压垮**开发节奏。

**建议**：立刻按 [07-开发流程与顺序](07-开发流程与顺序.md) 先做**合约最小闭环**；在此闭环跑通前，**不要再堆文档**。

### 9.3 ⚠ 风险二：Reorg 与 Finality 的实现难度

Reorg/Finality 在设计文档里已写清楚，但**真正难的是实现**：

- checkpoint 回退  
- logIndex 严格比较  
- 幂等去重  
- 副作用隔离  

这是系统最核心的工程难点，不是「写完了设计就结束」。

**建议**：**第一个 sprint 就实现可 replay 的 indexer**（从 event_log 可重建 orders_projection）；把 Reorg 回退与幂等去重做实，再扩展业务。
