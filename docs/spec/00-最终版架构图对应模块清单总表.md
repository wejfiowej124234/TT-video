## 一、文档定位

本文给出《**最终版架构图对应的模块清单总表**》，按**主序列文档**口径约定：

- **优先级**与**落地顺序**（1～48）
- **是否 P0**
- **是否已有**（见下文判定口径，**不**等同于「代码已 100% 实现」）

### 1.1 先说明两点（判定口径）

1. **「是否已有」**不按「代码里是否百分百已实现」判断，而按**文档体系能否证明「已定义 / 已成体系」**判断。因此使用三种状态：**已定稿**、**有方案未落地**、**待补齐**。这比假装掌握代码现状更准确。
2. **主序列与分层文档的对应关系**（与排期、阅读串联配合使用）：
   - **L1**：`01` / `03` — 业务与资金硬约束  
   - **L2**：`04` / `13-1` / `14` — 接口与页面 SSOT、合约对齐  
   - **架构分层与云部署（主文档）**：`17` / `18` / **[18-补充](18-补充-TravelTrust-全系统架构层级图-最终版.md)** / `19` / `20` — MVP 模块区、全系统架构、层级 ASCII 补充、Escrow 参数、企业级云部署  
   - **UI 初稿后实现闭环**：`32`～`41`  
   - **行程报价与订单执行主线**：`80`（AI/Draft/snapshot、**自定义行程 API** 门禁，与 [18](18-TravelTrust-全系统架构图.md) **§七** 口语链一致）→ `42` → `44` → `52` → `53`  
   - **主链「大图」速览（与 53 对齐）**：[18-TravelTrust-全系统架构图](18-TravelTrust-全系统架构图.md) **§二、§七**（模块交互 + 口语闭环）、[18-补充-TravelTrust-全系统架构层级图-最终版](18-补充-TravelTrust-全系统架构层级图-最终版.md) **§二**（主链路 ASCII）；**状态机、API、验收**仍以 **53、04、13-1** 为 SSOT，避免「只读图不读 53」。
   - **企业级防呆（真实落地）**：**Happy 路径**须统一理解为 **「链下确认行程完成（`confirm-completion`，非放款）→ 行后评分（若适用）与双方确认 → 再智能合约 `release`」**，与 **53**、**04 §3.4**、**14**、**01 §〇 E2E**、**03 §一**、**02 §14.3**、**18/18-补充** 一致；争议/退款/处罚分支仍以 **01/03** 为准。**本表「是否已有」**表示**文档体系是否成体系**，**不**等于产线已 `Implemented`；代码与运行态以 **CI 证据、迁移、53/55 收口清单、Wave Done Definition**（见 [07-开发流程与顺序](07-开发流程与顺序.md) **§零 0.4.1**）为准，避免「文档已定稿但无证据即宣称上线就绪」。

### 1.2 与「07 §零」中 L1/L2/L3 的关系

[07-开发流程与顺序](07-开发流程与顺序.md) **§零 0.1** 中的 **L1 / L2 / L3** 表示**权威冲突时的层级**（硬约束 > 契约 > 执行主链），其中 **L3 执行主链** 对应 `42/44/52/53`。[00-文档体系与阅读串联](00-文档体系与阅读串联.md) 为兼容壳，正文在 **07**。

**可视化对照**：八层纵向栈见 [18-补充-TravelTrust-全系统架构层级图-最终版](18-补充-TravelTrust-全系统架构层级图-最终版.md)。

## 四、优先落地 12 项（执行摘要）

若不看整表，按项目**实际闭环**，建议优先推进以下 **12** 项（顺序与文档串联一致，非随意排序）：

| 顺位 | 子系统 | 原因 |
|------|--------|------|
| 1 | 业务硬约束 + 系统不变量 | 不先钉死，后面全返工 |
| 2 | API 单源 + UI SSOT + ABI 对齐 | 不统一，前后端和合约会漂 |
| 3 | 订单与撮合 | 主业务主链 |
| 4 | 行程与报价 | 订单前置依赖 |
| 5 | Escrow 协议编排 | 资金托管核心 |
| 6 | Escrow 合约体系 | 链上执行核心 |
| 7 | DApp / 钱包交互 | 没有它无法真正支付托管 |
| 8 | 身份与账户 | 向导/旅行者无法进入可信交易 |
| 9 | 争议与仲裁 | 旅游场景必有纠纷 |
| 10 | Indexer / Event Projection | 不然 DB 与链状态会脱节 |
| 11 | Admin 后台 + 财务/对账 | 没后台无法运营、仲裁、审计 |
| 12 | 测试 + 数据接库 + 发布验收 | 没有上线闭环 |

**文档串联关系（与上表一致）**：

- 订单线：`01` → `03` → `04` → `13-1` → `53`（**大图对照**：[18](18-TravelTrust-全系统架构图.md) §二/§七、[18-补充](18-补充-TravelTrust-全系统架构层级图-最终版.md) §二）  
- 行程报价线：`80` → `42` → `44` → `52` → `53`  
- UI 初稿后落地闭环：`32`～`41`  
- 云部署：`20`（并与 `140`、`08` 系列、`ops/RUNBOOK` 等联动）  
- 架构主文档：`17`、`18`、[18-补充](18-补充-TravelTrust-全系统架构层级图-最终版.md)、`19`、`20`  
- 治理代币（可选专题）：`82`、[governance-token/](governance-token/README.md)（与 `49` §G、`81` 衔接；非 MVP 主链必做）

## 五、按文档成熟度理解的「已有度」

从**文档体系**看，项目已具备下列「**架构已成型**」特征（不等于每一行都已编码完成）：

1. **MVP 六大区域**在 [17-TravelTrust-MVP-产品与模块清单](17-TravelTrust-MVP-产品与模块清单.md) 等文中已有明确定义：AI 行程、撮合、协议控制台、Escrow、风控仲裁、身份。  
2. **全系统架构、Escrow 参数结构、企业级云部署**均已独立成篇（`18`、`19`、`20`），并配有 [18-补充](18-补充-TravelTrust-全系统架构层级图-最终版.md) 层级总览，而非零散笔记。  
3. **32～41** 已将 UI 初稿后的实现、测试、i18n、性能、验收、运营内容、接库列为连续阶段清单，说明整体处于**系统落地编排**阶段，而非「只缺一个页面」。

**结论**：客观上讲，工作重心已从「补单页设计」转向**按模块清单与阶段文档编排落地与证据闭环**。
