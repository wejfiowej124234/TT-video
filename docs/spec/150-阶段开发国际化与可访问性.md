## 一、文档定位

本文定义 TravelTrust 在 150 阶段的“国际化（i18n）与可访问性（a11y）”开发规范。

TravelTrust 是跨区域旅游平台，国际化与可访问性不是后补能力，而是正式交付项。

150 阶段解决的问题是：

- 不同语言、时区、币种用户是否都能正确使用系统。
- 不同国家/城市规则差异是否可配置且可验证。
- 残障用户是否可独立完成关键交易路径。

## 二、系统目标

150 阶段目标是建立“多区域一致体验 + 本地化差异能力 + 无障碍合规”闭环：

1. 多语言可覆盖：关键业务链路支持多语言可切换。
2. 多币种/多时区可正确：金额、汇率、时间展示与计算正确。
3. 日期格式可本地化：按地区展示和输入，避免歧义。
4. 无障碍可达标：关键交易路径满足 a11y 标准。
5. 区域差异可配置：国家/城市级策略可配置、可审计、可测试。

## 三、范围定义（六大模块）

### 3.1 多语言体系（i18n）

核心能力：

- 多语言资源管理（至少 `zh`、`en`，可扩展）。
- 统一翻译键命名规范与命名空间。
- 运行时语言切换与回退机制。
- 文案版本化与审校流程。

最小要求（P0）：

- 关键路径页面（登录、下单、支付、争议、订单详情）100% 文案国际化。
- 错误提示、空态、加载态、确认弹窗全部国际化。

验收要求：

- 不允许关键页面存在硬编码文案漏网。
- 新增文案必须带翻译键和默认语言回退。

### 3.2 多币种与多时区

核心能力：

- 金额显示层支持多币种符号、精度、分组格式。
- 汇率来源与更新时间可追踪。
- 系统内时间采用统一基准（UTC）存储，展示按用户时区转换。
- 截止时间、争议窗口、超时规则按统一时钟计算。

结算币边界（与 01 对齐，P0）：

- 多币种能力仅用于展示层、报价换算与本地化阅读体验。
- Escrow 结算路径在 MVP 阶段仍以 `01` 写死规则为准：仅 USDC；不得因为多币种展示能力改变链上结算币。

最小要求（P0）：

- 前端展示支持至少 2 种货币格式。
- 用户可选择或自动识别时区，关键时间字段按本地化展示。

验收要求：

- 金额计算使用统一精度策略，避免前端浮点误差。
- 超时与窗口计算不受时区显示影响。

### 3.3 日期与时间格式本地化

核心能力：

- 支持地区化日期格式（如 `YYYY-MM-DD`、`MM/DD/YYYY`、`DD/MM/YYYY`）。
- 日期输入组件本地化（周起始日、月份语言、24h/12h）。
- 关键业务时间文案标准化（下单时间、支付截止、争议截止）。

最小要求（P0）：

- 所有日期显示通过统一格式化层输出，不允许散落拼接。
- 所有用户输入日期均做格式解析与歧义校验。

验收要求：

- 任一地区格式切换后不改变真实业务时间语义。
- 日期解析错误可被明确提示并记录。

### 3.4 可访问性（a11y）

核心能力：

- 键盘可达：Tab 顺序、焦点可见、Esc/Enter 行为一致。
- 语义可读：ARIA 标签、role、heading 层级正确。
- 视觉可读：对比度满足标准，文字缩放不破版。
- 辅助技术兼容：屏幕阅读器关键路径可操作。

最小要求（P0）：

- 关键路径满足 WCAG 2.1 AA 基线。
- 核心表单组件（输入、选择、弹窗、按钮）均有 a11y 约束。

验收要求：

- 自动化审计 + 人工审计双通过。
- a11y 缺陷分级与修复 SLA 明确。

### 3.5 国家/城市级配置差异

核心能力：

- 国家级配置：币种、语言优先级、日期格式、税费规则、支付方式。
- 城市级配置：时区、本地服务条款、价格参数、业务限制。
- 配置版本化、灰度生效、可回滚。

最小要求（P0）：

- 国家与城市配置具备独立数据结构与读取接口。
- 配置变更具备审计记录与生效范围。

验收要求：

- 同一订单在不同地区策略下行为可解释。
- 配置回滚不会破坏历史订单一致性。

### 3.6 本地化质量与合规验收

核心能力：

- 语言质量：术语表一致、关键法律文案准确。
- 格式质量：金额/时间/日期展示一致。
- 可访问性质量：自动化工具与手工测试闭环。
- 区域策略质量：国家/城市配置回归验证。

最小要求（P0）：

- 每次发布前有 i18n + a11y + 地区配置三类验收报告。
- 关键缺陷（阻断级）未清零不得发布。

验收要求：

- 验收报告可追溯到版本、环境、责任人。
- 与 130 测试门禁联动执行。

## 四、核心硬约束（必须写死）

1. Locale by Design：所有用户可见文本必须可本地化，不得硬编码关键文案。
2. UTC for Logic：业务计算统一 UTC，展示再本地化。
3. Currency Precision Safety：金额计算使用统一精度模型，不得前端自由计算。
4. A11y is Release Gate：关键路径 a11y 不达标不得上线。
5. Region Config as Product Asset：国家/城市配置必须版本化、可审计、可回滚。
6. No Silent Fallback：语言/币种/时区回退必须可见且可记录。
7. Settlement Boundary Safety：多币种不等于多结算币；资金结算规则仅可由 `01/04/14` 定义与变更。

建议新增或确认以下实体：

- `timezone_profiles`

- `city_policies`
- `i18n_coverage_reports`
- `a11y_audit_reports`

字段级要求：

- 文案包必须含 `locale`、`namespace`、`key`、`value`、`review_status`。
- a11y 报告必须含 `page`、`rule_id`、`severity`、`status`、`owner`。

## 六、实施计划（150 阶段）

### 6.1 P0（必须）

- 多语言关键链路全覆盖。
- 多币种/多时区/日期本地化基础能力上线。
- 国家/城市配置模型与读取链路上线。
- 关键路径 a11y 基线达标并接入门禁。

### 6.2 P1（增强）

- 术语表治理与翻译审校流程平台化。
- 多地区法律文案与条款差异化支持。
- a11y 自动化测试覆盖扩展到全站。

### 6.3 P2（规模化）

- 更多语言与地区扩展。
- 智能本地化推荐（语言/时区/币种默认策略优化）。
- 区域策略灰度发布与风险监控联动。

## 七、发布门禁（分层：P0 必须全过）

### 7.1 P0（最小可发布门禁，必须全过）

1. 多语言关键链路覆盖率达标。
2. 多币种/多时区/日期本地化测试通过。
3. 国家/城市配置差异回归测试通过。
4. a11y 关键路径满足 WCAG 2.1 AA。
5. i18n + a11y + 区域策略验收报告齐全。

### 7.1.1 量化门禁基线（P0，必须写入 CI 并按 fail-closed 执行）

- i18n 覆盖率：关键链路页面（登录/下单/支付/争议/订单详情）国际化覆盖率必须为 100%。
- a11y 阻断阈值：关键链路页面存在 `critical`/`serious` 级问题时不得发布。
- 区域策略回归：最小矩阵 `country x city x locale x timezone` 通过率必须为 100%。
- 证据完整性：`i18n`、`a11y`、区域策略三类主证据任一缺失即阻断发布。

门禁责任与执行入口（必须绑定）：

- 门禁 Owner：`Frontend Lead`（主责） + `QA Oncall`（备份）。
- 执行入口：`Build/frontend`（i18n 回归）、`Build/a11y`（a11y 主门禁）。
- 执行策略：任一必过门禁失败即阻断发布（fail-closed），不得人工绕过。

### 7.2 P1/P2（增强门禁，按阶段收口）

1. 全站 a11y 自动化覆盖与多地区法律文案验收闭环完成后，再执行规模化门禁。

统一证据字段要求（主证据必须具备）：

- `commit_sha`、`env`、`locale`、`rule_id`、`severity`、`owner`、`generated_at`。

## 八、与 37 的关系（正式交付项，不是附属项）
