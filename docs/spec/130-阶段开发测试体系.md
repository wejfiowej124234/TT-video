## 一、文档定位

本文定义 TravelTrust 在 130 阶段的“测试体系”开发规范。

130 阶段的核心目标是把“页面能跑”升级为“系统可验证、可回归、可发布”。

测试体系在本项目中是独立板块，不是附属项：

- 已有前端测试门禁：`docs/spec/36-前端测试与质量门禁.md`

130 阶段负责将上述能力扩展为覆盖后端、合约、钱包、索引器、风控与争议异常流的全栈测试体系。

## 二、系统目标

130 阶段目标是建立“分层测试 + 异常流测试 + 发布门禁”闭环：

1. 关键模块可单测：业务规则、状态机、风控规则可独立验证。
2. 契约可集成：API、DB、队列、索引器、执行器联动可验证。
3. 链路可端到端：从前端操作到链上结果可回归验证。
4. 异常可演练：钱包、断链、争议、退款、重试、reorg 均有用例。
5. 发布可门禁：测试结果可量化，不达标不得进入发布阶段。

架构锚点（强制）：130 阶段测试分层与证据归档口径统一对齐 `02 §十四`（`0~8` 九层 + 主链路 + 五中心）。

- `1~3` 层（接入/控制/API）：以前后端联调、API 集成、鉴权与错误码契约测试为主。
- `4~6` 层（业务/平台/链上接入）：以状态机、风控、合约、索引器、对账与执行器测试为主。
- `7~8` 层（数据与运行层）：以数据一致性、可观测、审计留痕、发布门禁与恢复演练为主。

## 三、范围定义（八大测试模块）

### 3.1 单元测试（Unit Tests）

覆盖对象：

- Core 领域模型与状态机迁移。
- 风控规则函数、评分函数、超时计算函数。
- 前端关键组件逻辑与 hooks（含 tx 状态机）。
- 索引器事件解析与去重逻辑。

最小要求（P0）：

- 订单状态机合法/非法迁移全覆盖。
- 争议终态分支（Refunded/PartiallyRefunded/Slashed/Completed）全覆盖。
- 超时规则（接单、支付、完成）边界值覆盖。

验收要求：

- 关键模块行覆盖率 >= 70%，分支覆盖率 >= 60%（P0）；核心状态机与资金终态相关模块建议分支覆盖率 >= 80%。
- 单测失败不得进入主干分支。

### 3.2 API 集成测试（API Integration Tests）

覆盖对象：

- 对外业务接口：Auth/me/guides/orders/disputes/itineraries/did-rank。
- 内网运维接口：internal/indexer 与 internal/incident/alerts（仅内网演练与运维回归）。
- 鉴权、幂等、限流、参数校验、错误码一致性。
- DB 写入与查询一致性。

边界说明（强制）：`/api/v1/internal/*` 不纳入公网业务兼容性断言；该类接口仅用于内网运维验证，必须同时提供“网关/网络隔离证据 + 调用审计证据”。

最小要求（P0）：

- 关键写接口均有“成功 + 失败 + 幂等重试”三类用例。
- 核心错误码（401/403/409/422/429/500）有契约断言。

验收要求：

- API 契约与 04/14 文档一致。
- 集成测试报告可追溯到接口版本与提交版本。

### 3.3 合约测试（Contract Tests）

覆盖对象：

- Escrow / EscrowFactory 核心状态迁移。
- deposit/release/openDispute/executeResolution 关键路径。
- 权限边界、重复执行、非法参数、金额守恒。

最小要求（P0）：

- 正常支付与放款路径可重复通过。
- 争议与裁决路径覆盖至少三种终态。
- 重放/重复执行幂等验证。

验收要求：

- Foundry 测试通过且可复现。
- ABI 与前端调用函数签名一致。

### 3.4 前后端联调测试（FE-BE Integration）

覆盖对象：

- 前端页面真实调用后端接口流程。
- 表单校验、错误态展示、权限态展示。
- x-request-id / trace_id 贯通验证。

最小要求（P0）：

- 登录、下单、接单、确认、评价、争议流程联调通过。
- 前端不使用 mock 时主流程可闭环。

验收要求：

- 联调环境报告可复核。
- 前后端字段映射无关键偏差。

### 3.5 E2E 测试（End-to-End）

覆盖对象：

- 从用户操作到后端状态变更再到链上/投影结果的完整链路。
- 核心角色（旅行者、向导、仲裁/运维）视角流程。

最小要求（P0）：

- 正常交易链路 E2E。
- 争议仲裁链路 E2E。
- 超时自动推进链路 E2E。

验收要求：

- E2E 在目标环境连续 20 次执行通过率 >= 95%，并记录失败归因。
- 每次发布前至少执行一次完整 E2E 回归，且发布候选构建的核心链路通过率必须为 100%。

### 3.6 钱包连接/签名/断链异常测试

覆盖对象：

- 钱包连接成功、拒签、断开、切链错误。
- 签名超时、签名 payload 变更、重复签名。
- RPC 不可用或高延迟下的交互表现。

最小要求（P0）：

- connect/reconnect/disconnect 全流程。
- 用户拒签、链 ID 不匹配、RPC 超时三类异常流。
- 前端提示、后端日志、审计记录三侧一致。

验收要求：

- 钱包异常不导致状态污染或误判成功。
- 异常流具备可回放证据。

### 3.7 争议与退款异常流测试

覆盖对象：

- 争议窗口边界、重复开争议、超时争议。
- 裁决执行失败、重试、死信、人工介入。
- 退款比例边界、非法退款参数、重复退款请求。

最小要求（P0）：

- 至少覆盖 10 个争议/退款异常场景。
- 场景分布必须覆盖 5 类：争议窗口边界、执行失败重试/死信、退款比例边界、重复请求幂等、权限越权防护；每类 >= 2 个场景。
- 每个场景验证状态机、资金守恒、审计链路三项。

验收要求：

- 异常场景下不会出现越权退款或双重结算。
- 执行失败场景有自动/人工恢复路径。

### 3.8 索引器与数据一致性测试

覆盖对象：

- indexer 断点恢复、去重、reorg 回滚、finality 门控。
- 链上事件与 DB 投影对账。
- replay/reconcile 工具链正确性。

最小要求（P0）：

- 模拟 reorg 场景可恢复。
- 模拟 lag 场景可告警并恢复。
- 对账差异可被检测并归类。

验收要求：

- 投影结果可通过回放重建验证。
- 数据一致性报告可归档到审计链路。

## 四、测试分层与执行策略

### 4.1 测试金字塔（建议基线）

- 单元测试：60%
- API/服务集成测试：25%
- E2E/UI 回归测试：15%

原则：

- 低层测试优先保证快速反馈。
- 高层测试重点覆盖关键用户路径与异常流。

### 4.2 环境分层

- Local：开发快速反馈（单测、部分集成）。
- CI：合并前质量门禁（当前已接入 `Build/build`、`Build/frontend`、`Build/e2e`；合约/索引/内网演练门禁按 8.4 缺口补齐前，不得宣称“已 CI 全量覆盖”）。
- Staging：联调与 E2E 回归。
- Pre-Prod：发布前最终验收与演练。

### 4.3 测试数据与夹具

- 固定测试账号、角色、订单模板、争议模板。
- 独立测试链与可重放数据集。
- 测试数据生成器与清理机制。

## 五、质量门禁（必须写死）

1. PR 门禁：单测与 API 集成测试必须通过。
2. 合约门禁：合约测试与 ABI 对齐检查必须通过。
3. 联调门禁：关键页面联调失败不得进入发布候选。
4. E2E 门禁：核心三条链路（正常/争议/超时）必须通过。
5. 异常门禁：钱包异常与争议退款异常流必须通过。
6. 一致性门禁：索引器与对账异常测试必须通过。

### 5.1 量化门禁基线（P0）

- 覆盖率门禁：行覆盖率 >= 70%，分支覆盖率 >= 60%；核心状态机与资金终态模块分支覆盖率 >= 80%。
- E2E 稳定性门禁：近 20 次执行通过率 >= 95%；发布候选构建核心链路（正常/争议/超时）必须 100% 通过。
- 异常流门禁：争议/退款异常场景 >= 10，且满足五类分布约束（每类 >= 2）。
- 可追溯门禁：失败用例必须具备 `request_id`、`trace_id`、日志与证据链接，任一缺失按门禁失败处理。

### 6.1 数据迁移与发布批次门禁（强制）

| 批次 | 范围 | 通过条件（Fail-Closed） |
|---|---|---|
| M1 | 新增测试域基础表（`test_cases`、`test_runs`、`test_run_artifacts`） | 迁移成功 + 回滚脚本可执行 + 样例写读验证通过 |
| M2 | 覆盖率/报告与门禁表（`test_coverage_snapshots`、`contract_test_reports`、`e2e_run_reports`、`release_quality_gates`） | 迁移成功 + 历史数据兼容检查通过 + 门禁查询链路通过 |
| M3 | 扩展演练与异常报告（`chaos_test_reports`）及索引优化 | 迁移成功 + 回放/对账与报表验证通过 + 证据归档完成 |

批次规则：任一批次若缺少“迁移结果 + 回滚结果 + 校验证据”三联证据，禁止进入下一批次与发布候选（Fail-Closed）。

## 七、阶段实施计划（130 阶段）

- 测试报告与证据归档机制上线。

### 7.2 P1（增强）

- 异常流测试矩阵扩充（钱包、争议、执行器、reorg）。
- 契约测试与文档对齐自动校验。

- 混沌测试（网络抖动、节点故障、队列阻塞）。

- 测试平台化看板（趋势、失败归因、回归风险）。

## 八、发布门禁（分层：P0 必须全过）

### 8.1 P0（最小可发布门禁：全量 CI 主证据 + 运行态深度证据）

CI 主证据门禁（必须全过）：

1. `Build/build`：后端构建与测试通过（含不变量检查）。
2. `Build/frontend`：前端 lint/tsc/unit 全部通过。
3. `Build/e2e`：核心 E2E 回归通过。
4. `Contract ABI Gate/contract-abi`：合约测试与 ABI 对齐证据通过。
5. `Indexer Reconcile Gate/indexer-reconcile`：索引/对账 CI 锚点核验通过。
6. `Internal Drill Gate/internal-drill`：internal 边界 CI 锚点核验通过。

运行态深度证据（预发/演练必须全过）：

1. 索引器回放与对账深度报告通过（含差异归零或可解释闭环）。
2. `/api/v1/internal/*` 网关隔离实测通过（含策略导出、探测日志、审计样本）。
3. 前后端联调关键路径、钱包异常、争议/退款异常流通过并归档证据。
4. 测试报告、覆盖率与证据链接齐全可审计。

### 8.2 P1/P2（增强门禁，按阶段收口）

1. 混沌、压测、容量基线和趋势化测试看板闭环后，再执行规模化门禁。

### 8.3 门禁执行锚点（仓库现有入口）

| 门禁类别 | 执行入口 | 证据落点 |
