## 一、文档定位

本文定义 TravelTrust 在 MVP 与后续阶段的“身份与信任系统”开发规范。

本系统不是“注册/登录”子功能，而是平台交易真实性与资金安全的基础设施：

- TravelTrust 是真人服务交易平台，不是纯 DeFi 协议。
- 若无身份与信任层，订单真实性、履约可信度、争议仲裁与资金托管都会失真。
- 因此“身份与信任”与风控仲裁同级，是 MVP 六大区域之一。

与现有体系关系：

- 业务与风控：`docs/spec/03-业务流程与风控.md`
- 后端与 API：`docs/spec/04-后端与API.md`
- 状态机与不变量：`docs/spec/01-总库总览.md`、`docs/spec/10-系统级不变量白皮书-v1.0.md`
- 文档串联：**[07-开发流程与顺序.md](07-开发流程与顺序.md) §零、§五**（[00-文档体系与阅读串联.md](00-文档体系与阅读串联.md) 兼容壳）
- 协议级四类角色 SSOT：**[87-TravelTrust-角色体系技术文档-融合架构版](87-TravelTrust-角色体系技术文档-融合架构版.md)**（与 **13-1** 表 2、**04** `users.role` 真值交叉核对）

## 二、系统目标（不是“账号系统”）

身份与信任系统的目标是形成“可验证的交易主体 + 可演化的信任分层”：

1. 交易主体可验证：确认“谁在下单、谁在接单、谁有资格提供服务”。
2. 服务能力可验证：向导身份、资质、历史履约可检查。
3. 风险画像可计算：把 KYC、设备行为、争议记录、违规历史汇总为风险标签。
4. 信任分可演化：信誉分与评价体系能抗刷、抗串谋、抗短期操纵。
5. 资金动作可解释：每次托管与释放都能回溯到身份、行为、风控决策与证据。

## 三、范围定义（五大模块）

### 3.1 用户身份体系

核心能力：

- 多角色身份模型：Tourist / Guide / Arbiter / Ops / Auditor。
- 账号身份与链上地址绑定（一主多辅策略可扩展）。
- 会话可信度分层（设备、IP、异常地理、历史登录行为）。
- 身份状态机（active / restricted / suspended / pending-review）。

最小数据对象：

- identity_profile
- wallet_binding
- session_risk_snapshot
- identity_status_history

验收要求：

- 任一用户在订单链路中可定位唯一主体身份。
- 关键身份变更（角色、状态、绑定地址）全量审计留痕。

### 3.2 向导入驻审核

核心能力：

- 入驻申请受理与材料完整性校验。
- 审核工作流（提交 -> 初审 -> 复审 -> 通过/驳回）。
- 审核结果与接单权限联动。
- 与订单状态机联动的强约束：向导接单权限以 `01` 的可接单条件为准（`registry.approved && now<expiry && staking>=minStake(tier) && !suspended`），并叠加档期冲突拦截；已占用档期时间窗内不得并发接冲突新单。

审核维度：

- 身份真实性
- 资质有效性
- 历史行为风险
- 区域执业匹配

验收要求：

- 审核结论必须有理由、证据指针、审核人、时间戳。
- 被驳回/封禁向导不得绕过权限接单。

### 3.3 KYC / DID / 资质认证

定位：三层信任，不互相替代。

- KYC：现实世界身份核验与合规校验。
- DID：去中心化身份标识与可验证声明容器。
- 资质认证：行业资质、服务能力证明、有效期管理。

核心能力：

- KYC 等级分层（L0/L1/L2...），按风险策略控制可用功能。
- DID 绑定与声明校验（签发方、有效期、撤销状态）。
- 资质证书生命周期管理（上传、审核、续期、失效）。

验收要求：

- 订单/争议场景可读取身份层级与资质状态。
- 任何证书状态变更（生效/过期/撤销）可追溯。

### 3.4 风险标签

定位：把离散风险信号标准化为可执行策略输入。

标签来源：

- 身份层：KYC 等级、证件异常、DID 声明异常。
- 行为层：频繁取消、异常接单速度、跨地域异常登录。
- 交易层：争议率、退款率、超时率、仲裁不利历史。
- 设备层：设备指纹重叠、批量账号关联。

标签输出：

- risk_level（low/medium/high/critical）
- risk_reason_codes
- recommended_actions（限单/限聊/限提现/人工复核）

验收要求：

- 标签变更有版本号与命中证据。
- 风险处置动作必须回写审计链路。

### 3.5 信誉分与评价防刷

目标：评价体系“可用”而不是“可刷”。

核心能力：

- 信誉分由多因子计算，不等于星级平均值。
- 评价权重按交易完成质量、金额区间、账户可信度加权。
- 防刷机制：反自评、反互刷、反短期异常爆发、反羊群行为。
- 处罚联动：对刷评行为降权、冻结、人工复核。

最小防刷规则集：

- 同设备/同关系网短期互评上限。
- 低质量交易评价权重衰减。
- 异常时间窗评分突增触发风控。
- 争议败诉记录对信誉分产生惩罚。

验收要求：

- 信誉分计算可解释（输入因子、权重版本、输出结果）。
- 评价被降权或剔除必须可审计、可复核。

## 四、与订单与托管系统的耦合要求

身份与信任层必须贯穿订单全链路：

1. 下单前 / mock 付款前：**链下规则版（与 `GET /me.trust` 同源）**：`POST /api/v1/orders`、`POST /api/v1/orders/:id/mock-pay`（旅行者）在身份 **`pending_review`**（**403** **`trust_verification_pending`**，与接单侧 **`trust_guide_pending_review`** 区分）、**`restricted`**、或 **`risk_level=high`** 时 **403**（见 **04 §3.4**）。
2. 接单前：校验向导审核状态、资质有效性、风险等级。**链下规则版（与 `GET /me.trust` 同源）**：`POST /api/v1/orders/:id/accept` 在 **`guides.status=pending`**、身份 **`restricted`**、或 **`risk_level=high`**（未决争议计数）时 **403**（**`trust_*`** 键，见 **04 §3.4**）。
3. **参与方其它写路径（链下规则版）**：`cancel`、`confirm-completion`、`confirm-final-plan`、`set-escrow-address`、`PATCH …/itinerary`、`dispute`、`confirm-bilateral`、`confirm-rating`、`reviews`、订单 **POST messages**、**POST evidence** 等 — 旅行者侧同 **1** 的 **`trust_verification_pending` / `trust_identity_restricted` / `trust_risk_too_high`**，向导侧同 **2** 的 **`trust_guide_pending_review`** 等；**参与方判定**：**`orders.guide_id`** 为 **guides 行 id**，向导账户以 **`guides.user_id`** 对齐（与 **`GET /api/v1/orders`**、**`GET /api/v1/orders/:id`** 详情 **403** 一致；自由市场列表数据源为 **`GET /api/v1/discover/orders`**，主 UI **`/market`**，见 **04 §3.4**）。
4. 托管前：若风险超阈值，触发人工复核或限制交易。
5. 争议时：仲裁面板读取身份证据、信誉历史、风险标签版本。
6. 结算后：履约结果反哺信誉分与风险模型。

硬约束：

- 不允许绕过身份与风险门禁直接进入资金关键动作。
- 风险策略变更不得影响历史审计可解释性（需版本化）。

## 五、数据模型建议（最小集合）

建议新增或扩展数据实体：

- `identity_profiles`
- `identity_verifications`
- `did_bindings`
- `guide_certifications`
- `guide_review_workflows`
- `risk_tags`
- `risk_tag_events`
- `reputation_scores`
- `reputation_events`
- `review_anti_fraud_cases`

字段级要求：

- 所有状态类字段必须带 `updated_at` 与 `updated_by`。
- 所有策略类字段必须带 `version`。
- 所有审计关键动作必须带 `x_request_id` 与 `evidence_hash`（可空但要有字段）。

## 六、API 与权限建议（最小接口面）

接口分层：

- Identity API：身份查询、状态变更、地址绑定。
- Verification API：KYC/DID/资质审核与回执。
- Risk API：标签查询、标签处置、策略命中解释。
- Reputation API：信誉分查询、评分解释、反刷处置。

概念 API 与权威路由映射（对齐 `04 §3.4`、`14`）：

| 概念 API | 当前路由锚点（已登记） | 当前状态 |
|---|---|---|
| Identity API | `GET/PUT /api/v1/me`、`GET /api/v1/me/stats` | Implemented（基础档案；**GET /me** **`trust`**：**`kyc_status`**、**`wallet_linked`**、**`guide_registration_status`**、**`identity_status`**、**`risk_level`**、**`risk_basis`**、**`risk_reason_codes`**、**`recommended_actions`**（**90 §3.4** 规则版）、**`rule`**，见 **04 §3.4**；**`risk_*`** 为规则版，**100** 深度联动仍为 Partial） |
| Verification API | `POST /api/v1/guides`、`POST /api/v1/guides/upload-doc`、`GET /api/v1/uploads/guides/:name` | Implemented（最小注册与材料上传） |
| Risk API | `POST /api/v1/orders/:id/dispute`、`GET/POST /api/v1/orders/:id/evidence` | Partial（与 100 风控引擎深度联动待补） |
| Reputation API | `GET/POST /api/v1/orders/:id/reviews`、`GET /api/v1/did-rank/travelers`、`GET /api/v1/did-rank/guides`、`GET /api/v1/did-rank/itineraries` | Partial（**已实现**：评价 **`weight`/`weight_breakdown`** 与列表 **`meta.review_weight_rule_*`**；**`GET /me` → `trust.reputation`**：**`me_reputation_summary_v2`** 含全角色 **`as_reviewer`**（已提交评价条数与权重合计）与向导 **`as_guide`** 加权均分；反刷处置与客服解释面板仍待补） |

口径说明：本节“概念 API”仅用于阶段能力分层，不替代 `04/14` 的路由清单；若两者冲突，以 `04/14` 为准。

RBAC 原则：

- CS：可读身份摘要，不可改 KYC 与资质结论。
- Risk：可写风险标签与处置动作。
- Ops：可发起向导审核，不可越权修改风控策略。
- Auditor：全只读，可导出审计链路。

## 七、阶段实施计划（90 阶段）

### 7.1 P0（必须先落地）

- 用户身份状态机与账号-地址绑定。
- 向导审核流（提交/审核/通过/驳回）。
- KYC 与资质最小字段和状态落库。
- 风险标签最小模型（规则版）。
- 信誉分 v1 与基础防刷规则。

### 7.2 P1（增强）

- DID 声明校验与撤销检查。
- 风险标签实时更新与策略联动。
- 信誉分解释面板（给客服/审计）。
- 审核与风控操作审批流。

### 7.3 P2（规模化）

- 风险模型策略版本治理。
- 信誉体系跨区域差异化权重。
- 反刷模型从规则走向混合模型（规则 + 统计）。

## 八、验收门禁（发布前）

必须全部满足：

- 身份状态、向导审核、KYC/资质、风险标签、信誉分五模块均可查询。
- 至少一条完整链路可演示：向导申请 -> 审核 -> 接单资格生效。
- 风险标签能阻断至少一类高风险交易动作。
- 信誉分能解释输入因子与权重版本。
- 评价防刷至少覆盖互刷与异常时间窗两类场景。
- 全部关键操作具备审计字段与证据指针。
