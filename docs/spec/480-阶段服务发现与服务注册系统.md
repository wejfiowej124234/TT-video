## 一、文档定位

本文定义 TravelTrust 在 480 阶段的“服务发现与服务注册系统”开发规范。

480 阶段用于治理多服务环境下的服务地址管理与路由发现，避免静态配置持续膨胀。

## 二、建设背景

服务增多后，静态配置会快速失控：

- api
- worker
- indexer
- chat
- ai
- search
- notify

必须具备：

- `service registry`
- `service discovery`
- `health check`
- `routing`

## 三、系统目标

1. 服务可注册：实例上线/下线自动登记。
2. 服务可发现：调用方通过发现机制获取健康实例。
3. 健康可感知：实例健康状态可实时更新。
4. 路由可治理：流量路由策略可配置、可灰度、可回滚。

## 四、数据模型建议

建议最小实体：

- `service_registry`
- `service_instances`
- `service_health_checks`
- `service_routing_policies`
- `service_discovery_logs`

字段级要求：

- `service_registry`：`service_name`、`service_type`、`owner`、`status`。
- `service_instances`：`instance_id`、`service_name`、`endpoint`、`zone`、`status`。
- `service_health_checks`：`instance_id`、`check_type`、`result`、`checked_at`。
- `service_routing_policies`：`service_name`、`route_rule`、`weight`、`effective_from`。

## 五、后台模块要求

后台新增一级模块：`服务治理中心`

子模块（必须）：

- 服务注册表
- 实例状态
- 健康检查
- 路由策略
- 发现日志

## 六、实施计划（480 阶段）

### 6.1 P0（必须）

- 建立服务注册与发现最小闭环。
- 建立健康检查与实例摘除机制。
- 覆盖 api/worker/indexer/search/notify 核心服务。

### 6.2 P1（增强）

- 分区/可用区路由策略。
- 服务级熔断与降级联动。

### 6.3 P2（规模化）

- 多集群服务发现。
- 服务拓扑可视化与自动依赖分析。

## 七、发布门禁

1. 核心服务实例可自动注册与发现。
2. 健康异常实例可自动隔离。
3. 路由策略切换通过灰度演练。

## 八、结论

服务发现与注册系统是多服务架构治理底层能力。没有 480 阶段，服务配置复杂度会持续失控。
