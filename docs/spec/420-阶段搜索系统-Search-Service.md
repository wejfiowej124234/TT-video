## 一、文档定位

本文定义 TravelTrust 在 420 阶段的“搜索系统”开发规范。

420 阶段用于构建独立搜索能力，避免仅靠 SQL 查询导致后期性能和体验崩溃。

## 二、建设背景

旅游平台必须支持高维检索：

- 搜城市
- 搜向导
- 搜行程
- 搜景点
- 搜评论
- 搜订单（后台）
- 搜举报
- 搜日志

只依赖数据库 `LIKE`/`ILIKE` 无法长期支撑复杂检索、排序与召回。

## 三、系统目标

1. 检索可扩展：支持跨实体检索与聚合查询。
2. 排序可配置：多字段排序、权重、相关性评分。
3. 体验可用：拼写纠错、模糊匹配、多语言检索。
4. 性能可控：索引与主库解耦，查询延迟可预测。

## 四、核心能力（必须具备）

必须具备：

- 全文搜索
- 模糊匹配
- 多字段排序
- 权重
- 拼写纠错
- 多语言

通常独立建设：

- `search index`
- `search sync`
- `search query api`

## 五、系统架构建议

### 5.1 Search Index

独立索引层承载高频检索：

- 城市索引
- 向导索引
- 行程索引
- 内容索引（评论/帖子）
- 运营索引（订单/举报/日志）

### 5.2 Search Sync

索引同步层负责数据一致性：

- 全量构建
- 增量同步
- 重试与死信
- 版本切换与回滚

### 5.3 Search Query API

统一查询网关：

- 实体查询接口
- 混合检索接口
- 高级过滤（国家/城市/价格/评分/状态）
- 权重与排序策略配置

## 六、数据模型建议

建议最小实体：

- `search_index_defs`
- `search_sync_jobs`
- `search_sync_offsets`
- `search_query_logs`
- `search_spell_dicts`
- `search_language_profiles`

字段级要求：

- `search_index_defs`：`index_name`、`entity_type`、`schema_version`、`status`。
- `search_sync_jobs`：`job_id`、`index_name`、`sync_mode`、`status`、`started_at`、`ended_at`。
- `search_sync_offsets`：`index_name`、`source_cursor`、`updated_at`。
- `search_query_logs`：`query_id`、`keyword`、`filters`、`latency_ms`、`hit_count`。
- `search_spell_dicts`：`locale`、`term`、`correction`、`weight`。
- `search_language_profiles`：`locale`、`tokenizer`、`normalizer`。

## 七、检索与排序策略

### 7.1 召回策略

- 精确匹配
- 前缀匹配
- 模糊匹配
- 同义词召回
- 拼写纠错召回

### 7.2 排序策略

综合排序建议：

- 文本相关性分
- 实体质量分（如向导评分、行程质量）
- 时效分
- 运营权重分

### 7.3 多语言策略

- 按 locale 选择分词器。
- 跨语言别名与译名映射。
- 多语言字段分别建索引或联合索引。

## 八、后台模块要求

后台新增一级模块：`搜索系统中心`

子模块（必须）：

- 索引管理
- 同步任务
- 查询分析
- 词典与纠错
- 排序权重管理
- 性能监控

## 九、实施计划（420 阶段）

### 9.1 P0（必须）

- 建立 search index/search sync/search query api 三层架构。
- 打通城市、向导、行程、订单四类核心检索。
- 落地查询日志与延迟监控。

### 9.2 P1（增强）

- 拼写纠错、多语言分词、同义词扩展。
- 评论、举报、日志检索与后台高级筛选。

### 9.3 P2（规模化）

- 个性化检索排序。
- 搜索意图识别与查询改写。

## 十、发布门禁

1. 核心检索场景脱离纯 SQL 方案运行。
2. 索引同步稳定，支持全量与增量恢复。
3. 查询 API 支持权重、排序、过滤组合。
4. 多语言和纠错能力通过抽样验证。

## 十一、结论

搜索系统是平台中后期性能与体验的基础设施。没有 420 阶段，查询性能和检索质量会成为增长瓶颈。
