**全系统架构大图**（前端在用户层/市场/Escrow 中的位置，与 **53** 主链叙事对齐）：[18-TravelTrust-全系统架构图](18-TravelTrust-全系统架构图.md)、[18-补充-TravelTrust-全系统架构层级图-最终版](18-补充-TravelTrust-全系统架构层级图-最终版.md)；串联入口 **[07-开发流程与顺序](07-开发流程与顺序.md) §五 5.1**、[00-最终版架构图对应模块清单总表](00-最终版架构图对应模块清单总表.md)。

## 二、业务流程在前端的体现（预约 → 确认 → 上链 → 钱包付代币）

```
游客端:
  浏览向导(API) → 选择向导、填行程、下单(API) → 确认订单
    → 上链：为该笔旅行创建/分配 Escrow 合约（含旅行费用、质押规则）
    → 钱包：用户用钱包支付「这笔旅行的费用」（代币打入该合约）
    → 行程中/完成后：**确认行程完成（链下 API）** → **行后评分与双方确认（若适用，见 53）** → **智能合约 release** → 评价/信誉归档（禁止口语「先放款再评价」）

向导端:
  注册/质押(API + 钱包代币质押) → 接单(API) → **确认行程完成(API，链下)**
    → **评分路径闭环后**由钱包签 **Escrow.release**，收入至向导钱包（与 01/03/53、OrderFlow 步骤条一致）

仲裁端:
  查看争议(API) → 裁决(API) → 执行由合约完成（退款/扣罚）
```

| 数据与操作 | 前端落点 |
|------------|----------|
| 订单、向导、预约、争议内容 | 通过 **api** 模块与后端通信。 |
| 上链、支付旅行费用、质押 | 通过 **dapp** 模块连接钱包，前端发起签名。 |

**DApp 与 Web 业务数据同步（P0 口径）**：

| 维度 | 约定 |
|------|------|
| **业务数据** | 旅行行程、接待人员/向导信息、订单详情、档期、争议与证据 **唯一数据源 = 后端 API/DB**；Web 页与 DApp 页**共用同一套 API**（同一 `api/` 模块），不因是否连接钱包而分源或分缓存。 |
| **链上仅负责** | 支付、质押、**Escrow.release**、openDispute 等由钱包签名完成；**链下**「确认行程完成」见 API（04 §3.4），**不得**与 release 混谈；业务展示以 API 为准，与 01/02「链为准、DB 为缓存与检索」一致。 |
| **实现要求** | 同一订单在 Web 与 DApp 页上的行程、接待人、订单状态须一致；DApp 路径不单独维护业务数据、不用本地状态覆盖 API 结果。 |
| **超时与争议窗口** | 接单/支付/完成超时、争议窗口（如 disputeDeadline≥autoCompleteAt）等时间节点以 01、[03-业务流程与风控](03-业务流程与风控.md) 定稿为准；前端从 API 获取并展示，不单独维护配置，与合约/后端可配置值保持一致（见 01 §5、01 §10 12 缝 #3）。 |

| 项目 | 选型 | 说明 |
|------|------|------|
| 框架 | Next.js | React 全栈框架，SSR/SSG 可选，API 路由可选 |
| UI | React | 组件化、TypeScript |
| 语言 | TypeScript | 类型安全 |
| 状态 | Zustand / React Query | 登录态、服务端状态、当前订单等 |
| 动效 | Framer Motion | 页面与组件动效 |
| 3D 展示 | React Three Fiber (R3F) + drei | **`/traveltrust`** 环境/交互粒子、**`MePageBackground`** 等仍挂载子树；**`/`**（**`app/(home)/page.tsx`**）为 **摄影 + 点阵 + 玻璃**，**无**全屏 R3F Landing（**88 §一**、**86 §6.1**）；资金流可视化等按产品范围。**不用于**订单操作主路径（见 **09 §2.5**、**13**） |

| DApp/钱包 | **wagmi + viem + WalletConnect v2**（见 06） | 连接钱包、签名、支付代币、调合约；EIP-712 TypedData 签名 |

## 七点五、弱网/离线/重试与幂等（写死，P0）

本节把 01 §10 17 条 #14（幂等）落到前端可执行规则，避免“弱网/超时/刷新/连点”造成重复下单或重复副作用。

**写操作必须幂等**（POST/PUT/任何产生副作用的动作）：

- **必须带 `X-Idempotency-Key`**：同一用户对同一业务动作的重复提交（连点、超时重试、刷新恢复）必须复用同一个 key。key 建议包含 `orderId + action + clientGeneratedNonce` 的稳定组合（格式由实现定稿，但必须可复用）。
- **必须带 `x-request-id`**：每次请求都要带一个 requestId（可复用或每次生成，但必须能在日志中关联）；后端会回写 `x-request-id` 与 `X-Idempotency-Key` 便于审计。
- **禁止盲目自动重试写操作**：除非确认幂等键已发送且可复用；否则仅允许用户手动重试。
- **超时/刷新恢复策略（写死）**：写操作超时后，前端不得假设失败或成功；必须进入“查询状态”路径（例如轮询 `GET /api/v1/orders/:id`）直到出现链上终态或明确失败。

**读操作可重试**（GET）：

- 允许指数退避（例如 200ms→500ms→1s→2s→5s）直到上限；网络离线时展示离线态，恢复后继续。

**与后端一致性**：后端已实现对 POST/PUT 的 idempotency 结果复用（见 04 §四）；前端必须按上述规则配合，否则幂等在用户侧不闭合。

## 七点六、Web/DApp 与 Backend 的版本绑定（写死，P0）

为避免“前端已发布但后端/SSOT 已变更”造成资损或口径不一致，必须做最小版本绑定：

- 前端启动时必须调用 `GET /meta`，读取 `api_version`、`ssot_version` 与 defaults 快照。
- **不兼容即拒绝进入关键写操作**：若 `ssot_version` 不符合前端 build 期写死的目标（或不在允许列表），则禁止下单/支付/发起争议等写操作，并提示用户刷新或切换到兼容环境（提示文案由实现定稿）。
- 版本绑定证据：发布时将 `/meta` 输出纳入 evidence bundle（见 08-2 与 Runbook）。

**实现约定（写死）**：前端 build 期必须写死期望值（否则 release 视为不合规）：

- `TRAVELTRUST_EXPECTED_API_VERSION`：期望的 `api_version`。
- `TRAVELTRUST_EXPECTED_SSOT_VERSION`：期望的 `ssot_version`，同时用于 **EIP-712 domain.version**（domain separator 不能依赖运行时拉取）。

## 七点七、构建确定性（Deterministic Build，写死，P0）

为满足 08-4 第 7 章“可验证发布”不是形式主义，必须保证：**同一 commit + 同一 Node 版本 + 同一依赖锁** → 产物哈希一致。

**写死的确定性输入**（必须能在证据里复核）：

- **Node 版本锁定**：仓库根 `.nvmrc` 或 CI 中 `node-version` 固定；CI 必须使用该版本（不得漂移到“最新 LTS”）。
- **Next.js 与构建**：发布证据必须记录 `node --version`、`pnpm --version`（或 yarn/npm）及 `next build` 的 Next 版本；构建脚本/发布说明必须声明安装方式与版本。
- **依赖锁文件强制**：必须提交并使用 `pnpm-lock.yaml`（或 `yarn.lock`/`package-lock.json`），构建时禁止 `--no-frozen-lockfile`（禁止隐式更新依赖）。
- **构建输出**：`next build` 输出目录（如 `.next`）的指纹或导出静态资源清单须纳入证据。

**可验证发布最小证据**：

- `dist/manifest.json` 与 `dist/manifest.sha256`（由前端可验证发布脚本生成）必须包含：`git commit`、Node/包管理器/Next 版本、lockfile sha256、产物列表与每个产物 sha256。
- 任意人复核时，只要 Node 与依赖锁一致，产物与 manifest sha256 必须一致；不一致则视为构建链路漂移，必须先修复再发版。

## 七点八、前端依赖供应链策略（写死，P0）

当前前端为 **Next.js（Node 构建链）**，必须满足：

- **必须有锁文件**：`pnpm-lock.yaml`/`yarn.lock`/`package-lock.json` 其一（同目录）；锁文件保证可复现。
- **frontend/ 版本策略**：门禁仅校验锁文件存在，允许 ^/~（与 npm/pnpm 常见用法一致）；其他目录的 package.json 仍禁止 ^/~。
- **依赖更新审计**：启用 dependabot（npm 规则，directory /frontend）；可选发版前执行 `./scripts/audit-deps.sh`，CI 中已加入非阻塞步骤。

门禁：CI 中 `scripts/check-invariants.sh` 校验 frontend 存在 package-lock.json；锁文件策略见 08-5。

## 七点九、浏览器存储策略（JWT/Cookie）与 CSP（写死，P0）

这不是架构偏好，是安全边界：

- **默认不在浏览器持久化 JWT**：不得把 JWT/refresh token 放入 `localStorage`/`sessionStorage`（XSS 风险不可接受）。
- **若需要会话**：必须使用 **`Secure` + `HttpOnly` + `SameSite=Strict`** 的 cookie（建议 `__Host-` 前缀），并在后端设置最小 Path、合理过期与轮换策略。
- **CSP（最小可执行）**：前端必须启用 CSP（优先用 HTTP Header；当前实现为 `index.html` meta 的最小 CSP），并禁止 `object-src`、限制 `frame-ancestors`。

说明：CSP 最终应由静态站点/CDN/后端统一以响应头写死；meta 作为最小实现与开发期基线。

## 七点十、钱包 Provider 断开/切链/换号的状态清理（写死，P0）

真实环境最常见的资损/口径不一致来自“身份漂移”：

- **chainChanged / accountsChanged 必须触发强制刷新**：一旦用户切链或切账户，必须清理当前身份与订单视图缓存，重新走“获取身份/订单”的流程；不得沿用旧地址视图继续发起写操作。
- **断连即失效**：钱包断开后，所有需要签名/链上写操作的按钮必须失效；订单页若依赖钱包身份必须回到只读态。

最小实现落在前端入口或 dapp provider 层：检测到 wallet 断开/链切换等事件后清理存储并 reload（后续实现钱包/登录后可替换为更细粒度状态机，但语义不变）；wagmi 的 `useAccount`/`useDisconnect` 等可配合。

---

## 七点十一、Gas 上限与预估（写死，P0）

- **预估必须留缓冲**：前端展示的 gas 预估必须包含安全缓冲（防止 baseFee 突增/轻微波动导致大量失败）。
- **EIP-1559 封顶**：必须写死 `maxFeePerGas`/`maxPriorityFeePerGas` 的上限策略（上限与降级动作在 Runbook/SSOT 定稿）；超过上限则提示用户“稍后再试”而不是无限重试。
- **失败可解释**：gas spike 失败必须在 UI 显示明确原因（估算不足/用户拒绝/网络拥堵），并引导用户走“查询状态”而不是假设失败。

---

## 七点十二、小数精度与四舍五入（写死，P0）

- **合约计算只用最小单位整数**（例如 USDC 6 decimals），前端展示仅做格式化。
- **展示精度与结算精度分离**：UI 可以四舍五入，但必须同时展示“链上最小单位换算后的精确值”或在关键确认页展示精确到最小单位的金额（至少在签名前事实展示）。
- **禁止前端自行改写结算金额**：任何 rounding 只能在展示层；传参/签名必须基于后端/合约给出的精确数值。

---

## 七点十三、时区展示（写死，P0）

- **服务端与证据时间一律 UTC（RFC3339）**：前端展示本地时间时必须标注“本地时区/UTC”并可切换。
- **争议窗口显示规则**：链上 disputeWindow 以 block/UTC 口径为准；若展示本地时间必须同时显示对应 UTC，防止投诉与误解。

## 九、UI/UX 设计风格与页面层级规划

**协议级约束（优先）**：所有 UI/UX 决策须符合 [13-协议级UI设计宪法](13-协议级UI设计宪法.md)。宪法锁死：资金区像银行（无渐变/炫光/跳动数字/3D 侵入）、3D 仅情绪层（不进入 EscrowDetail/Dispute/Governance）、旅游在上层/金融在下层、角色空间隔离（工作空间而非 Tab）、风格优先级「可信度 > 清晰度 > 一致性 > 美感 > 动效」、统一为**温和的科技感**；视觉关键词为**克制、信任、科技、空间感、温和旅行**；禁止 Neon Cyberpunk、极重玻璃态叠加、交易区强动效。页面结构以宪法「页面列表」与下文四层一致。

本节约定前端的**设计语言**（与宪法一致的温和科技感与信任感）、**页面分层结构**（四层）、**各层内容**与 01～04 的对应，以及 **UI/UX 顶级要求与细节规范**（9.0.5：可访问性、响应式与触控、状态与反馈、排版、动效、表单、导航、安全与信任 UX、性能、DApp 专属、国际化），并与 [01-总库总览](01-总库总览.md)、[02-架构设计](02-架构设计.md)、[03-业务流程与风控](03-业务流程与风控.md)、[04-后端与API](04-后端与API.md) 中的功能与角色一一对应，便于实现时统一风格与信息架构。

### 9.0.1 设计语言与风格（温和科技感，与宪法一致）

**定位对齐**：TrustLayer = 全球旅行 + **去中心化协议** + 安全预订 / 担保支付 / 可验证信誉（01 项目定位）。UI/UX 须同时传达**可信、透明、链上可验证**与**旅行、当地、人文**，避免纯极客或纯 OTA 风格。**资金相关区域**（订单金额、托管详情、支付/质押/争议、EscrowDetail、DisputeCenter、Governance）须遵守宪法 1️⃣：严肃、留白、信息优先、状态清晰、风险提示可见；禁止渐变按钮、炫光、跳动数字、3D 侵入。

| 维度 | 约定 | 说明 |
|------|------|------|
| **主色调与氛围** | 深色/半透明为主，科技蓝·青·紫渐变点缀；高对比可读 | 深色背景（如 #0d1117～#161b22）降低眩光、突出链上状态与数据；主色（#3b82f6 / #06b6d4 / #8b5cf6）用于 CTA、链接、状态高亮；可选浅色模式（遵循系统或用户偏好） |
| **玻璃态与层次** | 卡片/面板使用 backdrop-blur、细边框、轻微阴影 | 区分「区块」与「背景」；链上状态块、钱包连接态、订单状态条可用玻璃态区分层级 |
| **数据与链上可视化** | 状态标签、进度、confirmations、tx 链接、金额与代币符号统一 | 订单状态与 01 §1、04 status 枚举一致（含 PartiallyRefunded、Slashed、Cancelled）；pending 展示 confirmations（01 §7 UI 事实）；金额+代币（如 USDC）与 04 API 一致 |

| **图标与符号** | 钱包、链、锁、盾、勾/叉、时钟、争议等语义化图标统一 | 与 01/02 概念一致：Escrow=托管、Staking=质押、Dispute=争议；**确认行程完成（链下 API）**与 **Release（链上放款）**须在文案/图标语义上区分（04 §3.4、53） |

**DApp 与 Web 统一**：同一套设计语言；DApp 路径仅增加「连接钱包」「签名确认」等组件，不改变整体风格（与 01 §9、02 §八 业务数据同源一致）。

### 9.0.5 UI/UX 顶级要求与细节规范

以下为**企业级 UI/UX 顶级要求**，实现与验收时须满足；与 01 §7 UI 事实、§10 17 条 #14、03 超时/争议展示、04 接口与错误码一致。

#### 可访问性（Accessibility）

| 要求 | 细节 | 依据/说明 |
|------|------|-----------|
| **标准** | 至少符合 WCAG 2.1 Level AA（或当地等效）；关键流程（注册/登录、下单、支付、发起争议）须通过 a11y 自检 | 企业级产品、多地区用户 |
| **对比度** | 正文与背景对比度 ≥4.5:1，大号文字/图标 ≥3:1；状态色（成功/警告/错误）在深色与浅色背景下均满足 | 可读性、色盲友好 |
| **焦点与键盘** | 所有可交互元素可键盘聚焦；焦点顺序符合视觉与逻辑；焦点环可见（不依赖仅色差）；无键盘陷阱 | 键盘用户、辅助技术 |
| **焦点管理** | 弹窗/抽屉打开时焦点移入、关闭时还原；路由切换后焦点落于主内容或标题 | 屏幕阅读器、键盘 |
| **语义与 ARIA** | 按钮/链接/表单用原生语义；必要时 aria-label/aria-describedby/role 补足；列表、表头、状态用正确语义 | 屏幕阅读器 |
| **表单** | 每输入必有可见 label 或 aria-label；错误与必填提示与控件关联（aria-invalid、aria-errormessage）；必填项明确标注 | 04 接口校验与前端一致 |

#### 响应式与触控

| 要求 | 细节 | 依据/说明 |
|------|------|-----------|
| **视口** | 支持 320px～1920px 宽度；关键页面（列表、详情、下单、支付）在 375px 与 768px 断点可用、无横向滚动条遮挡内容 | 手机与平板优先、桌面兼容 |
| **触控目标** | 可点击/触控区域最小 44×44px（或 44pt）；相邻可点元素间距足够，避免误触 | 移动端、WCAG 2.5.5 |
| **输入方式** | 移动端优先使用合适输入类型（tel/email/number/date）；数字与金额考虑数字键盘 | 04 字段类型、体验 |

#### 状态与反馈

| 要求 | 细节 | 依据/说明 |
|------|------|-----------|
| **加载态** | 列表/详情：优先骨架屏（skeleton）而非仅转圈；按钮/提交：loading 态 + 禁用防连点（01 §10 17 条 #14） | 感知性能、防重复提交 |
| **空状态** | 列表无数据时展示明确空状态文案与 CTA（如「去选向导」「去接单」），不空白 | 引导与角色动线 |
| **错误态** | API/网络错误：用户可读文案 + 可重试或返回；与 04 错误码/文案一致；链上失败（如 reject、revert）：明确「交易未成功」、不误导为已支付 | 01 §7 UI 事实、04 错误约定 |
| **成功态** | 关键操作（支付、质押、发起争议、裁决提交）后明确成功反馈（toast/页内）；链上成功可附 tx 链接与 confirmations（01 §7） | 可验证、可追溯 |
| **超时与争议窗口** | 接单/支付/完成超时、争议截止时间从 API 获取并展示；倒计时或截止日期清晰；过期后按钮禁用并说明原因（与 03 一致） | 03、01 §10 12 缝 #3 |

#### 排版与视觉层次

| 要求 | 细节 | 依据/说明 |
|------|------|-----------|
| **层级** | 标题/正文/辅助至少三级；字号与字重区分；主操作（CTA）在视觉上优先 | 9.0.1 设计语言 |
| **数字与金额** | 金额、数量、区块号等用等宽或 tabular-nums；小数位与 04 API 一致（如 USDC 6 位）；千分位与本地化一致 | 01 状态/金额、04 字段 |
| **状态标签** | 订单/争议状态与 01 §1 状态机、04 status 枚举一致（Created, Accepted, Escrowed, Completed, Disputed, Refunded, PartiallyRefunded, Slashed, Cancelled 等）；颜色与文案统一；pending 时展示 confirmations 而非「已支付」 | 01 §7 UI 事实 P0、04 §二 2.2 orders |

#### 动效与动效偏好

| 要求 | 细节 | 依据/说明 |
|------|------|-----------|
| **时长** | 过渡动画一般 ≤300ms；页面级切换 ≤400ms；避免长于 500ms 的阻塞性动效 | 响应感、不拖沓 |
| **减少动效** | 尊重 `prefers-reduced-motion: reduce`：禁用或大幅减弱非必要动效，保留仅用于反馈的短时变化 | 无障碍、前庭敏感用户 |
| **用途** | 动效用于状态变化反馈、层级过渡，不用于纯装饰；加载、成功/失败 toasts 须清晰可辨 | 9.0.1 |

#### 表单与输入

| 要求 | 细节 | 依据/说明 |
|------|------|-----------|
| **校验时机** | 失焦或提交时校验；破坏性操作（解绑钱包、发起争议）前二次确认，文案写清后果 | 04 校验规则、01 12 缝 #11 |
| **错误展示** | 错误信息贴近控件、可读；不仅依赖颜色（辅以图标或文案） | 可访问性、04 错误码 |
| **敏感操作** | 支付、质押、openDispute、**release**：弹窗内明确展示金额、代币、合约/订单标识，并提供「取消/拒绝」选项；链下「确认行程完成」若仅 API 亦须避免误导为已放款 | 01 §7 钱包签、防误操作；04 §3.4 |

#### 导航与结构

| 要求 | 细节 | 依据/说明 |
|------|------|-----------|
| **当前页** | 导航高亮当前页面或 Tab；多步流程（下单→确认→支付）有步骤指示或面包屑 | L2 区域布局、流程清晰 |
| **返回与出口** | 弹窗/全屏流程可关闭（按钮或 Esc）；支付/签名流程用户可取消并返回 | 不强迫完成、可撤销 |
| **深度** | 关键任务（下单、支付、争议）点击深度尽量 ≤3；重要入口在 L1/L2 可见 | 01 业务流程 |

#### 安全与信任 UX

| 要求 | 细节 | 依据/说明 |
|------|------|-----------|
| **不可逆操作** | 解绑钱包、发起争议、仲裁裁决等：明确文案说明后果 + 二次确认；钱包换绑与已支付订单按 01 §10 12 缝 #11 硬规则（已支付后换绑=dispute 或新单，UI 禁止误导） | 01 §7、§10 12 缝 #11 |
| **不代付/不托管** | 文案与流程中不出现「平台代付」「托管您的私钥」等；支付/签名均表述为用户在钱包中操作 | 01 代付 P0、02 §十三 13.1 |
| **链上信息可见** | 签名前展示关键参数：金额、代币、订单/合约标识、网络；与 EIP-712 展示一致 | 01 §7、防钓鱼 |

#### 性能与鲁棒性体验

| 要求 | 细节 | 依据/说明 |
|------|------|-----------|
| **首屏与列表** | 首屏关键内容优先加载；长列表考虑分页或虚拟滚动，避免一次性渲染大量 DOM | 感知性能 |
| **请求超时** | API 或 RPC 超时时有明确提示与重试入口；不长时间白屏或转圈无反馈 | 04 超时、链 RPC |
| **离线与弱网** | 网络不可用时给出提示；恢复后可重试或刷新；不静默失败 | 旅行场景、移动网络 |

#### DApp 与钱包专属

| 要求 | 细节 | 依据/说明 |
|------|------|-----------|
| **连接钱包** | 入口清晰；支持主流钱包与 WalletConnect；连接失败时错误可读、可重试 | 01 §7、§三 技术选型 |
| **签名请求** | 每次签名前展示操作含义（支付/质押/**release**/openDispute）、金额与代币、目标合约/订单；用户可拒绝；勿将链下「确认行程完成」标成单笔链上放款 | 01 §7 钱包签、安全 UX；53、14 |
| **链与网络** | 当前链/网络标识可见；切换网络时状态与提示明确 | 多链或测试网场景 |

#### 国际化与扩展

| 要求 | 细节 | 依据/说明 |
|------|------|-----------|
| **文案** | 所有用户可见文案可配置为多语言；数字、日期、金额格式支持本地化 | 01 全球旅行定位 |
| **RTL** | 若支持 RTL 语言，布局与焦点顺序支持 RTL（可选，MVP 后可迭代） | 扩展性 |
