## 四、后端最优模块化拆分建议

### 4.1 为什么要做

| 维度 | 前端（43～46 已做） | 后端（当前） |
|------|---------------------|--------------|
| **单文件行数** | ≤400 行、超标已拆 | main.rs ~3747、chain_off.rs ~3610 |
| **按域/职责分模块** | 33～34～35、apiClient 按域拆 | 路由与 handler 全在 main.rs，业务逻辑大量在 chain_off.rs |
| **可测试性** | 组件/页面独立、可单测 | 大单体，单测与集成边界模糊 |
| **可维护性** | 新功能落点清晰 | 新接口需在巨大 main 中定位、易冲突 |

**结论**：后端**建议**进行与前端同尺度的**最优模块化拆分**，便于迭代、测试与 80/81/Schedule Engine 等新能力落点清晰。

### 4.2 拆分原则（与 43 对标）

- **单文件行数**：建议 **≤500 行**（Rust 含类型与错误处理略长于 TS，可略放宽）；**严格可采 ≤400**。
- **按领域/职责**：路由与 handler 按**领域**拆（auth、guides、orders、itineraries、discover、me、disputes、evidence、meta、health），避免单文件承载全部路由。
- **chain_off**：按**领域或用例**拆为多 mod（如 `chain_off::auth`、`chain_off::guides`、`chain_off::orders`、`chain_off::itineraries`、`chain_off::messages`、`chain_off::disputes`、`chain_off::evidence`、`chain_off::reconcile` 等），主文件只保留 `ChainOffStore`/`ChainOffState` 与聚合。
- **db.rs**：若继续膨胀，可拆为 `db::users`、`db::guides`、`db::orders`、`db::itineraries`、`db::reviews`、`db::disputes`、`db::messages` 等，入口 `db/mod.rs` 重导出。

### 4.3 建议的 crates/api 结构（目标态）

```
crates/api/src/
├── main.rs                 # 仅：启动、CORS、SSOT、中间件挂载、Router 聚合（≤400 行）
├── lib.rs                  # 可选：对外 re-export，便于集成测试
├── middleware.rs           # 幂等、traceId、限流、body limit、timeout（从 main 抽出）
├── router.rs               # 或 routes/mod.rs：聚合各域 Router（从 main 抽出）
├── routes/
│   ├── mod.rs
│   ├── health_meta.rs      # /health, /meta
│   ├── auth.rs             # /auth/*
│   ├── me.rs               # /api/v1/me, /api/v1/me/*
│   ├── guides.rs           # /api/v1/guides/*
│   ├── orders.rs           # /api/v1/orders/*
│   ├── itineraries.rs      # /api/v1/itineraries/*
│   ├── discover.rs         # /api/v1/discover/*
│   ├── disputes.rs         # /api/v1/disputes/*
│   ├── evidence.rs         # /api/v1/orders/:id/evidence
│   └── ...
├── chain_off/
│   ├── mod.rs              # Store、State、Config、聚合
│   ├── auth.rs
│   ├── guides.rs
│   ├── orders.rs
│   ├── itineraries.rs
│   ├── messages.rs
│   ├── discover.rs
│   ├── disputes.rs
│   ├── evidence.rs
│   ├── reconcile.rs        # 对账/投影相关
│   └── ...
├── db/
│   ├── mod.rs
│   ├── users_sessions.rs
│   ├── guides.rs
│   ├── orders.rs
│   ├── itineraries.rs
│   ├── messages.rs
│   ├── reviews_disputes.rs
│   └── ...
├── chain/                  # 现有
│   ├── mod.rs
│   ├── indexer.rs
│   └── outbox.rs
└── schedule_engine.rs      # 80 §4.15 Schedule Engine（档期引擎）独立模块，或 schedule_engine/mod.rs
```

**说明**：`schedule_engine` 为 80 要求的新增组件，建议**独立模块**，与 04、01/03 档期与锁定规则对接。

### 4.4 落地顺序建议

| 顺序 | 内容 | 说明 |
|------|------|------|
| 1 | **middleware 与 router 抽出** | 从 main.rs 拆出 middleware、路由聚合，main 只做启动与挂载，目标 main ≤500 行 |
| 2 | **routes/* 按域拆** | 按 04 §3.4 的 API 分组，每域一个模块，handler 内可调 chain_off / db |
| 3 | **chain_off 按域拆** | 将 chain_off.rs 按 auth/guides/orders/itineraries/messages/disputes/evidence/reconcile 拆为 chain_off/*.rs |
| 4 | **db 按表/域拆（可选）** | 若 db.rs 后续超过 600～800 行，再拆为 db/*.rs |
| 5 | **Schedule Engine** | 新增 schedule_engine 模块，实现 80 §4.15 的档期重叠、锁定生效、payment_window 软占用；接单/发布/取消时调用 |

### 4.5 验收标准（可与 41 并列或作为 48 阶段）

- [ ] main.rs ≤500 行（或 ≤400 行严格）
- [ ] chain_off 拆为多 mod，单文件 ≤500 行
- [ ] 各域路由与 handler 在 routes/* 可定位，与 04 §3.4 一一对应
- [ ] Schedule Engine 独立模块，与 80 §4.15、01/03 档期规则衔接
- [ ] 单测/集成测试可针对单模块运行（可选）

### 4.6 文档落点

- **04-后端与API**：在 §五 落地顺序或新小节中增加「后端模块化拆分」目标与与 04 §3.4 的映射。
- **09-技术架构总览**：§2.8 Rust 后端方案中可补充「模块边界：routes、chain_off、db、schedule_engine」。
- **新增阶段文档（可选）**：若单独成阶段，可新增 **48-后端模块化拆分与落地清单**（类似 43 前端模块化），含拆分原则、目标结构、勾选表与实现记录；与 41、27-P41 并列。
