## 一、文档定位

本文定义 TravelTrust 在 410 阶段的“平台规则引擎”开发规范。

410 阶段用于把大量业务规则从代码硬编码中解耦，避免“改一条规则就发版一次”的高成本模式。

## 二、建设背景

平台进入中后期后，规则复杂度会快速增长：

- 不同国家不同规则
- 不同订单不同规则
- 不同向导不同限制
- 不同等级不同权限

如果把规则直接写死在代码中，会导致：

1. 规则变更需要频繁发版，发布风险高。
2. 规则不可回放，难以审计历史判定依据。
3. 规则冲突难排查，跨团队协同成本高。
4. 规则灰度困难，实验和回滚不稳定。

## 三、系统目标

1. 规则可配置：业务规则通过配置下发，不依赖代码改动。
2. 判定可解释：每次命中可追溯规则版本与条件路径。
3. 执行可扩展：支持多域规则统一执行与组合。
4. 变更可治理：规则发布、灰度、回滚、审计闭环。

## 四、核心能力（必须具备）

必须具备：

- `rule table`
- `rule evaluator`
- `condition engine`

### 4.1 Rule Table

负责规则的结构化存储与生命周期治理。

最小能力：

- 规则标识、规则类型、规则版本。
- 作用域（国家、城市、订单类型、向导等级、角色）。
- 生效时间、失效时间、优先级。
- 状态（draft、active、paused、deprecated）。

### 4.2 Rule Evaluator

负责按上下文执行规则并输出判定结果。

最小能力：

- 输入统一上下文（user/order/guide/region/role）。
- 规则匹配与优先级决策。
- 命中结果结构化输出（allow/deny/review/limit）。
- 命中证据与解释链记录。

### 4.3 Condition Engine

负责解析和计算规则条件表达式。

最小能力：

- 条件运算（eq/ne/gt/gte/lt/lte/in/not_in）。
- 逻辑组合（and/or/not）。
- 函数与衍生字段（如风险分、订单金额区间、国家白名单）。
- 条件版本兼容与安全沙箱执行。

## 五、数据模型建议

建议最小实体：

- `rule_tables`
- `rule_versions`
- `rule_conditions`
- `rule_actions`
- `rule_scopes`
- `rule_eval_logs`

字段级要求：

- `rule_tables`：`rule_id`、`rule_name`、`rule_domain`、`status`。
- `rule_versions`：`rule_id`、`version`、`priority`、`effective_from`、`effective_to`。
- `rule_conditions`：`version_id`、`condition_expr`、`condition_ast`。
- `rule_actions`：`version_id`、`action_type`、`action_payload`。
- `rule_scopes`：`version_id`、`country_code`、`order_type`、`guide_level`、`role`。
- `rule_eval_logs`：`trace_id`、`context_digest`、`matched_rules`、`decision`、`evaluated_at`。

## 六、规则执行策略

### 6.1 作用域优先级

建议优先级：

1. 国家/司法辖区规则
2. 订单类型规则
3. 向导等级规则
4. 用户等级/角色规则
5. 通用兜底规则

### 6.2 冲突处理

- 明确 deny 优先于 allow。
- 明确高优先级规则覆盖低优先级规则。
- 明确同优先级冲突时按版本发布时间或规则 ID 稳定排序。

### 6.3 灰度与回滚

- 新规则先灰度到小范围国家或用户分群。
- 命中异常可一键回滚到上个稳定版本。

## 七、后台模块要求

后台新增一级模块：`规则引擎中心`

子模块（必须）：

- 规则列表
- 条件编辑器
- 作用域配置
- 命中日志
- 发布与回滚
- 规则冲突检测

## 八、权限模型（最小角色）

建议最小角色：

- `RULE_VIEWER`
- `RULE_EDITOR`
- `RULE_PUBLISHER`
- `RULE_AUDITOR`

高风险动作（发布/回滚）要求双人复核。

## 九、实施计划（410 阶段）

### 9.1 P0（必须）

- 落地 rule table、rule evaluator、condition engine 三件套。
- 覆盖国家/订单/向导等级/角色四类核心规则。
- 落地评估日志与审计导出。

### 9.2 P1（增强）

- 可视化条件编辑器与规则冲突检测。
- 规则灰度实验与自动回滚。

### 9.3 P2（规模化）

- 规则模板市场与跨域规则复用。
- 离线回放评估与规则效果评分。

## 十、发布门禁

1. 核心业务规则可完全脱离硬编码执行。
2. 规则命中日志可追溯、可导出。
3. 规则发布与回滚链路通过演练。
4. 冲突规则可被检测并阻断上线。

## 十一、结论

规则引擎是平台复杂度治理底座。没有 410 阶段，规则迭代会被发布周期绑死，长期不可持续。
