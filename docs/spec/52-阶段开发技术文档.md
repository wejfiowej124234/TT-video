## 二、行业行程表参考与统一表设计依据

### 2.1 网络资料与常见旅游行程表字段（摘要）

综合常见旅游行程表模板与行业实践（如行程表模板 Word/Excel、行程规划总表、景点/餐饮/交通分表），**按日维度的行程表**通常包含以下维度：

| 维度 | 常见字段/内容 | 说明 |
|------|----------------|------|
| **时间** | 日期、第 N 天、当日时间区段 | 起讫日期、天数；可选具体时刻 |
| **地点** | 城市、目的地、景点名称 | 当日主要活动地点 |
| **文字** | 行程重点、活动描述、备注 | 当日概要或详细说明 |
| **图片** | 景点图、餐饮图、封面图 | 与文字配合使用，用于展示与分享；**图片配合文字介绍**为行业常见做法 |
| **价格/费用** | 当日预算、单项价格、总预算 | 可与总预算 breakdown 关联 |
| **城市交通** | 市内交通方式（公车/地铁/租车/包车） | 当日市内移动 |
| **跨城交通** | 高铁/飞机/大巴/自驾 段间交通 | 跨城市移动（如有） |
| **餐饮** | 早餐/午餐/晚餐、推荐餐厅、价位 | 当日餐饮安排 |
| **景区** | 景点名称、开放时间、门票、介绍 | 当日游览点 |
| **住宿** | 酒店名称、地区、价格/晚、备注 | 可选，多日行程常用 |
| **备注** | 注意事项、开放时间、票务提醒 | 补充信息 |

**参考来源**（摘要）：  
- 行程表模板常见结构：行前准备（目的地、日期、天数、预算）、景點規劃（按日：景點+餐飲+交通）、住宿建議、美食推薦、交通方式（市區/跨城）、行程規劃總表（日期｜行程重點｜備註）。  
- 行业常见按日表格列：日期、行程重點、備註；或扩展为 日期｜景點｜餐飲｜交通｜住宿｜預算。  

以上作为**统一行程表**字段设计的行业依据。52 采用「按日行」为最小展示单元，每行覆盖上述维度，并**强调行程内容以图片配合文字介绍**呈现，适配 1 天至多天（如 10 天）。

### 2.2 与现有实现的对应关系

| 现有实现 | 位置 | 与统一表的关系 |
|----------|------|----------------|
| **ItineraryDayRow** | crates/api chain_off/itineraries.rs | 当前仅有 day_index、content_text、content_images；52 统一表扩展为含 城市/交通/餐饮/景区/价格 等结构化字段（或在一层保留 content 的同时增加结构化字段）。 |
| **CustomDayPlan / GuideDayPlan** | 前端 CustomItineraryModal、chain_off CustomItineraryBody | 旅行者/向导手填：city、attractions、food、hotel、city_transport、transport；52 统一表与之一致并补全「图片、文字描述、价格」等，使 AI 与手填输出同一形状。 |
| **AmountBreakdown** | chain_off、DB | 总预算拆解（hotel/catering/tickets/guide_fee/vehicle/platform_fee）；52 统一表可关联总 breakdown，并按日可选展示「当日预估」或链接到总表。 |
| **days_json / ItineraryBundle** | DB itineraries、chain_off ItineraryBundle | 52 定义**统一日行 schema**后，days_json 存储为「统一表行」数组，便于首页/市场/订单详情/Escrow 同一组件渲染。 |

## 三、统一行程表规范（数据模型与 UI）

### 3.0 图文配合原则（必守）

行程展示以**图片配合文字介绍**为默认要求，便于旅行者与向导理解、分享与决策。

| 原则 | 说明 |
|------|------|
| **每单元可配图+文** | 当日概要、每个景区、每条餐饮、城市/跨城交通、住宿等**可展示单元**均支持「至少一段文字介绍」+「可选一张或多张配图」；缺图时以文字为主，缺文时以标题/名称+图为辅。 |
| **图文一一对应** | 数据结构上建议**图文成对**：如某景区为 `{ name, intro, image? }`，某餐饮为 `{ name, description, image? }`，避免仅有图或仅有文导致展示空洞。 |
| **生成与录入** | AI 生成、旅行者手填、向导发行程时，均按上述单元产出**文字介绍 + 可选配图**；向导侧可上传实拍图+自写介绍，旅行者侧可填偏好由 AI/平台补全图文。 |

### 3.1 统一行程表「按日行」数据模型（52 规范）

以下为**单日行程行**（Unified Itinerary Day Row）的规范字段。无论 1 天还是 10 天，也无论来源为 AI 生成、旅行者创建或向导创建，最终落库与展示均采用该结构；**所有可展示项均支持图片配合文字介绍**。

| 字段 | 类型 | 必填 | 说明（图文配合） |
|------|------|------|------------------|
| **day_index** | number | 是 | 第几天（1～N） |
| **date** | string (YYYY-MM-DD) | 否 | 当日日期（有出行日期时填） |
| **city** | string | 建议 | 当日主要城市/目的地 |
| **description** | string | 建议 | **当日行程文字描述**（概要或详细）；与当日主图配合展示 |
| **images** | string[] 或 { url, caption? }[] | 否 | 当日图片列表；可选 caption 作为**该图的文字说明**，实现图文配合 |
| **attractions** | { name, intro, image? }[] 或兼容 string[] | 否 | **景区**：名称 + **文字介绍（intro）** + 可选配图；intro 必填或强烈建议，便于图文并茂 |
| **dining** | { name, description?, image?, type?, price? }[] 或兼容 string[] | 否 | **餐饮**：名称 + **文字描述（description）** + 可选配图；description 建议填写 |
| **city_transport** | string 或 { type, desc?, image? } | 否 | **城市交通**：类型 + 可选文字说明(desc) + 可选图（如车型图） |
| **inter_city_transport** | string 或 { from, to, type?, note?, image? } | 否 | **跨城交通**：起止+类型+备注+可选图（如高铁/航班场景图） |
| **hotel** | string 或 { name, area?, price?, intro?, image? } | 否 | **住宿**：名称+区域/价格+**可选文字介绍(intro)**+可选图 |
| **price_note** | string 或 number | 否 | 当日预估费用说明或金额（可与总 breakdown 关联） |
| **notes** | string | 否 | 备注（注意事项、开放时间、票务等） |

**说明**：  
- **图文配合**：attractions / dining 等数组项采用「name + intro/description + image」结构，展示时**图片与对应文字一起呈现**（如左图右文、上图下文、卡片内图+文）。  
- **兼容现有**：现有 ItineraryDayRow 的 content_text 可映射为 description，content_images 映射为 images；CustomDayPlan 的 city/attractions/food/hotel/city_transport/transport 与上表对齐后，补充 intro/description/image 等字段即可写入统一表。  
- **AI / 旅行者 / 向导**：三种来源在生成或提交时，均按上表产出**带文字介绍的单元**，并尽可能提供配图；详见 §四。

**术语约定**：文中「按日行程行数组」在 **API 响应**中可与现有兼容写作 **daily_itinerary**（如 GET /api/v1/orders/:id）；在 **DB 存储**中为 **days_json**（itineraries 表）；在 **类型与规范**中统称 **days**（UnifiedDayRow[]）。实现时三者对应同一 §3.1 结构，仅键名按上下文区分。

**可选扩展字段**（行业最佳实践对齐，不破坏现有结构）：景区/餐饮等可增加 **duration_estimate**（预计时长）、**open_hours**（营业/开放时间）、**reservation_link** / **booking_url**（预约链接）、**lat/lng** 或 **map_link**（地理/地图）；详见 §8.3。API/DB 兼容旧数据时可逐步支持。

### 3.2 统一行程表「总览」与费用（参考自由市场自定义弹窗）

| 层级 | 内容 | 说明 |
|------|------|------|
| **行程元信息** | destination、city（首日或主目的地）、total_days、travel_date（起）、end_date（止）、title、cover_image | 与现有 ItineraryBundle / 订单 itinerary 一致 |
| **按日行数组** | days: UnifiedDayRow[] | 长度 1～N，每项为 §3.1 单日行；每行可有 **price_note**（当日预估） |
| **总费用 breakdown** | amount_breakdown，见下表「独立金额项」 | 与现有后端 AmountBreakdown、前端 BudgetBreakdown/GuideQuoteBreakdown 对齐；**每个独立金额 + 整个行程总金额**均需在表中展示 |

**独立金额项（与自由市场 CustomItineraryModal 报价结构一致）**：

| 金额项 | 字段名（后端/存储） | 说明 | 前端展示名（参考 42/弹窗） |
|--------|---------------------|------|----------------------------|
| 住宿 | hotel | 住宿总费用 | 住宿 / Hotel |
| 餐饮 | catering | 餐饮总费用 | 餐饮 / Food |
| 门票/景区 | tickets | 门票/景区总费用 | 景区（门票）/ Attractions |
| 向导费 | guide_fee | 向导服务费 | 向导费 / Guide |
| 交通（市内+跨城） | vehicle | 城市交通+跨城交通合计 | 交通费 / Transport |
| 平台费 | platform_fee | 平台服务费（若有） | 平台费 / Platform |
| **整个行程总金额** | total_budget | 上述分项之和（或订单总价） | 合计 / Total |

- **旅行者侧**（CustomItineraryModal 旅行者）：与 **BudgetBreakdown** 对应——attractionsTotal、foodTotal、hotelTotal、transportTotal、guideTotal、**total**；另有 perDay、headcount、days、attractionCount、foodCount、hotelNights 等辅助展示。  
- **向导侧**（CustomItineraryModal 向导）：与 **GuideQuoteBreakdown** 对应——attractionTotal、foodTotal、hotelTotal、guideTotal、transportTotal（含 cityTransportFee、interCityFee）、**total**；另有 perDay、headcount、days。  
- **后端**（chain_off AmountBreakdown）：hotel、catering、tickets、guide_fee、vehicle、platform_fee、**total_budget**。  

统一行程表展示时：**必须展示「每个独立金额」与「整个行程金额」**，表格或费用区块与自由市场自定义弹窗的「报价明细 / 预算拆解」一致，便于用户一眼看到各项多少、总价多少。

### 3.3 统一行程表「金额表格」构建参考（自由市场自定义弹窗）

构建行程表内的**金额展示表格**时，以自由市场**自定义行程弹窗**（CustomItineraryModal）的报价/预算区块为参考，保证「每个独立金额 + 整个行程金额」一致呈现。

| 参考来源 | 位置 | 用途 |
|----------|------|------|
| **旅行者侧预算拆解** | TouristQuoteSummaryBlock、TouristBudgetMetaFields、TouristGuideAndTransportSection | 展示 景区、餐饮、住宿、向导费、交通费 等**分项金额**及 **合计（total）**、人均/每日预估 |
| **向导侧报价拆解** | GuideFormQuoteAndCoverSection、GuideFeeAndTransportSection | 展示 景区、餐饮、住宿、向导费、交通（市内+跨城） 等**分项金额**及 **总价（total）**、人均/每日 |
| **数据结构** | quoteCalculationTypes：BudgetBreakdown、GuideQuoteBreakdown | 前端计算分项与总价；提交时与后端 amount_breakdown / breakdown（guide_fee、car_fee 等）对齐 |

**表格构建要点**：  
- 列表式或表格式列出 **住宿、餐饮、景区（门票）、向导费、交通费、平台费** 每项金额（单位与币种统一，如 USDC）。  
- 最后一行/一项为 **整个行程总金额**（total_budget / total）。  
- 可选：按日预估（price_note）、人均、每日均价（perDay）等辅助信息。  
- 与 42 自定义行程弹窗的 UI 文案与顺序保持一致（如「景区」「餐饮」「住宿」「向导费」「交通费」「合计」），便于用户在不同入口看到同一套费用结构。

### 3.4 统一行程表 UI 规范（通用展示，图片配合文字 + 金额）

- **图文展示方式**：  
  - **当日层级**：description（当日描述）与 images（当日图列表）一起展示，建议「首图 + 当日概要文字」或「轮播图 + 每图可选 caption」。  
  - **景区/餐饮/住宿等单元**：每个单元以**图片配合文字**呈现——左图右文、上图下文、或卡片内「图 + 标题 + 介绍文字」；无图时仅展示文字介绍，无文时仅展示标题/名称+图。  
  - **统一原则**：同一行程表组件内，所有可展示项均采用「有图则图配文、有文则文可配图」的样式，避免纯图或纯文块。  
  - **行业最佳实践（图+文+价）**：每个可展示单元**优先呈现「图片 + 文字描述 + 价格」**——当日行展示 **price_note**（当日预估）；景区/餐饮等采用**单元卡片**（左图右文或占位块 + 名称 + 介绍 + 单价），餐饮项有 **price** 时与名称同排或紧随描述展示；费用分项与总价标签与金额间留空格，总价单独突出，便于一眼扫读。  
- **金额展示**：  
  - **每个独立金额**：住宿、餐饮、景区（门票）、向导费、交通费、平台费 分项展示，每项单独一行或一列金额（见 §3.2、§3.3）。  
  - **整个行程金额**：总价（total_budget / total）醒目展示，与分项同区或紧接在费用表格下方。  
  - 实现时从 order.itinerary 的 **amount_breakdown** 读取，或从前端 BudgetBreakdown/GuideQuoteBreakdown 传入；表格结构参考自由市场自定义弹窗（TouristQuoteSummaryBlock、GuideFormQuoteAndCoverSection）。  
- **列表形态**：按日展示，每行至少包含 day_index、date（若有）、city、description、attractions（含 intro+image）、dining（含 description+image）、city_transport、inter_city_transport（若有）、可选 hotel/price_note/notes；图片以缩略图或轮播与对应文字并排/上下展示。  
- **适配 1～N 天**：1 天时单行展示；多日时表格或卡片列表，支持折叠/展开以保持页面简洁。  
- **响应式**：移动端可收拢为「日期 + 概要 + 展开详情」，桌面端可表格或卡片并排；图文布局在移动端可改为「图在上、文在下」以利阅读。  
- **设计规范**：与 [86-UI-双系统未来风-风格与动效技术规格](86-UI-双系统未来风-风格与动效技术规格.md)（**Experience / Business 分区**）、[25-顶级UI标准-Landing-Discover-Itinerary](25-顶级UI标准-Landing-Discover-Itinerary.md)、[28-Cinematic-Glassmorphism-Web3融合规范](28-Cinematic-Glassmorphism-Web3融合规范.md)、[22-Design-Tokens](22-Design-Tokens-旅游Web3融合体系-v1.0.md) 一致；表格/卡片风格与现有 Landing、Market、Escrow 统一。**风格约束**：行程在首页/市场用 Travel 轴与可选玻璃卡片（**`/market`** 为 **86 Business 降级**），在 Escrow 详情内用 Trust 轴、银行级无玻璃；所有样式仅用 22 Tokens，动效符合 **86 §0.3** / 25 / 28；详见 §8.0。
- **可扫性**：折叠态或列表首屏应能**一眼看到关键信息**——日期、城市、当日概要、**总价或总价入口**；避免必须展开多日才知总预算。
- **无障碍**：配图提供 **alt**（名称+简短描述）；金额/日期/地点**对比度**达标；行程列表与折叠/展开**键盘可聚焦、可操作**；焦点顺序符合阅读顺序。详见 §8.4。

## 四、按旅行者/向导诉求生成行程与通用「创建行程」

### 4.1 按旅行者与向导要求生成相应行程（图文配合）

行程生成（AI 或表单）须**按旅行者侧与向导侧的不同诉求**产出内容，且**每条可展示内容均配合图片与文字介绍**。

| 角色 | 诉求要点 | 生成/录入时的图文要求 |
|------|----------|------------------------|
| **旅行者** | 目的地、天数、预算、偏好（景区类型、餐饮、交通档次）、必去点 | 生成或填写的**每日描述、景区、餐饮、交通、住宿**均应有**文字介绍**（intro/description）；图片可由 AI 或平台根据目的地/景区/餐饮补全，或旅行者上传。旅行者侧展示侧重「看得懂、可决策」的图文行程。 |
| **向导** | 带团路线、推荐景点与餐厅、自有的实拍图与讲解文案、档期与报价 | 向导发行程时，**景区/餐饮/住宿**等建议提供**向导自写介绍 + 自传图片**（实拍图、官方图）；系统将向导填写的「文字+图」落入统一表，与旅行者侧同一展示组件呈现。向导侧展示侧重「专业介绍 + 实景图」的图文行程。 |

**实现约定**：  
- **AI 生成**：根据用户输入（目的地、天数、偏好等）生成每日的 description、attractions（name+intro+可选图）、dining（name+description+可选图）、交通与住宿的说明+可选图；输出符合 §3.1 统一表，且满足「每单元有文字介绍、尽量配图」。  
- **旅行者创建**：表单中每日可填景区名/餐饮名等，**鼓励或必填简短介绍**；图片可选上传或由平台/国家库（lib/countries、cityDetails）自动关联。  
- **向导创建**：表单中景区/餐饮等支持**向导填写介绍文案并上传图片**，落库为统一表的 intro/description + image，与旅行者创建行程用同一表展示。

### 4.2 三种来源归一

| 来源 | 入口/场景 | 输出（均含图文配合） |
|------|-----------|----------------------|
| **AI 生成行程** | 首页 Landing 表单、/itinerary/new 表单 | 后端生成 daily_itinerary + amount_breakdown；**落库与返回采用 §3 统一表**，每日/每景区/每餐饮等带 description 或 intro，并可选 images；前端用统一行程表组件**图片配合文字**展示。 |
| **自由市场旅行者创建行程** | /market「自定义行程」→ CustomItineraryModal（旅行者） | 提交 POST /api/v1/itineraries/custom（creator_type=tourist）；后端写入 itineraries，**days_json 为统一表行数组**，含图文字段；市场/订单/Escrow 用同一表**图+文**展示。 |
| **向导创建行程** | /market「自定义行程」→ CustomItineraryModal（向导） | 提交 POST /api/v1/itineraries/custom（creator_type=guide）；同上，**days_json 统一表行数组**，向导填写的介绍与图片写入 intro/description/image；展示逻辑与旅行者一致，**图片配合文字介绍**。 |

**原则**：不论谁生成、几天，最终都通过**同一套「按日行」结构**展示，且**行程内容以图片配合文字介绍**呈现，避免纯图或纯文、避免多处定制表格与分支逻辑。

### 4.3 通用 Web3 旅行页面「创建行程」

- **入口**：  
  - 首页「去生成行程」→ /itinerary/new 或首页盲盒生成；  
  - 自由市场「自定义行程」→ CustomItineraryModal（旅行者/向导切换）。  
- **能力**：  
  - 支持 1～N 天（如 1 天、3 天、10 天）选择或输入；  
  - 每日可填：城市、**景区（名称+文字介绍+可选图）**、**餐饮（名称+描述+可选图）**、城市交通、跨城交通、住宿（名称+介绍+可选图）、**当日文字描述+当日图片**、价格备注；  
  - 按**旅行者**或**向导**身份，生成或录入**符合其诉求的图文行程**（见 4.1）；  
  - 与现有 lib/countries、平台定价（44）、AmountBreakdown 衔接；  
  - 提交后创建 Draft 订单并写入 itineraries，**写入格式为 §3 统一表（含图文字段）**。  
- **UI 优化**：  
  - 表单布局参考行业行程表：按日分组、景點/餐飲/交通/住宿 分区或 Tab；**每项提供「文字介绍」输入与「配图」上传/选择**；  
  - 展示时**图片配合文字**：表格或卡片内「图+标题+介绍」；日期、行程重點、備註 等列可读性优先；  
  - 图片、价格、交通等用图标或短标签区分，符合通用旅行产品习惯。

### 4.4 展示一致性

- **首页结果区**（ItineraryResultsSection）、**订单详情**（OrderDetailDrawer）、**Escrow 详情**（EscrowDetail 内行程区块）、**市场订单卡片**内行程摘要：均从 order.itinerary 读取 **days**（统一表行数组）+ **amount_breakdown**，用**同一行程表展示组件**渲染；**每个可展示单元均以图片配合文字介绍的方式呈现**；**金额**部分须展示**每个独立金额**（住宿/餐饮/景区/向导/交通/平台费）与**整个行程总金额**，与自由市场自定义弹窗的报价结构一致，保证样式与信息结构一致。

| **动效** | [28](28-Cinematic-Glassmorphism-Web3融合规范.md) §4：Travel 动效 卡片 hover 1.02、视差 6px、文字 reveal 600ms；badge 淡入 200ms、modal 250ms。**禁止**：钱包连接特效、余额数字跳动、霓虹呼吸。[25](25-顶级UI标准-Landing-Discover-Itinerary.md) + **[86](86-UI-双系统未来风-风格与动效技术规格.md) §0.3 规则 3**：页面 ~600ms、组件 &lt;300ms，统一缓动。 | 行程折叠/展开、列表出现：200ms/600ms，与 **86/25/28** 一致；禁止行程卡片炫光、数字跳动、强动效 |
| **留白与焦点** | [25](25-顶级UI标准-Landing-Discover-Itinerary.md)：单屏单焦点、留白、高端感来自克制。 | 行程列表/时间线：留白充足；不堆满多列；单屏内一个主焦点（如「当日行程」或「费用区」） |
| **协议级宪法** | [13-协议级UI设计宪法](13-协议级UI设计宪法.md)：资金区像银行、3D 仅情绪层、风格优先级「可信度 > 清晰度 > 一致性 > 美感 > 动效」。 | 金额展示区（分项+总价）信息优先、状态清晰；不因「好看」牺牲可读性 |

**一句话**：52 的 UI/UX 效果 = **行业最佳实践（8.1～8.4）在「Gentle Tech Travel + **13/86/28/22/25** 分层」约束下的实现**；不另立一套视觉语言。

### 8.1 行业最佳实践摘要（2024 前后）

综合行程规划产品（如 Kuse、ItineraryForge、Moovit、KDE Itinerary、Kiwi.com、高端 OTA/旅行品牌）的常见做法：

| 维度 | 最佳实践要点 | 来源/说明 |
|------|--------------|-----------|
| **规划阶段** | Discovery（发现目的地）→ Collection（收藏兴趣点）→ Organisation（按日编排）三阶段清晰分离 | 行程类 App 通用结构 |
| **按日展示** | 按日卡片/时间线视图；支持折叠展开、拖拽排序；多日时时间线统一视图一眼看全 | 卡片式、时间线式 day-by-day |
| **活动卡片信息** | 名称、**预计时长**、**营业/开放时间**、**预约链接**、**地理坐标/地图链接**、费用；便于执行与导航 | 行业行程模板与高端行程产品 |
| **预算展示** | **实时计算**（增删活动自动更新总价）；**分项+总价**；可选**按类目图表**、**超支提示**、多币种与汇率 | 预算跟踪模板、AI 行程产品 |
| **地图与地理** | 活动卡片关联坐标；整条路线地图展示、路线规划与导航入口 | 常见行程/导航产品 |
| **分享与保存** | 行程可分享链接、导出 PDF/图片，便于与旅伴或客户同步 | 协作与传播 |
| **情景化信息** | 根据用户当前场景展示不同内容（如值机时展示登机牌、出发时展示交通指引），信息不阻塞主屏 | Kiwi.com 等 |
| **可扫性（Scannability）** | 关键信息（日期、地点、金额、时间）一眼可见，避免大段文字才能理解 | Moovit 等对「可扫性」的反思 |
| **无障碍** | 图片 alt、对比度、键盘导航、焦点管理；符合 WCAG 的行程展示 | 通用可访问性要求 |
| **视觉叙事与留白** | 单屏单焦点、留白、统一动效节奏；高端感来自克制（见 **25**、**28**、**86 Experience / 86 Business 降级**、**22**） | 25、28、86、22；Awwwards/Stripe/Apple 对标 |

### 8.3 数据与功能缺口补充（可选扩展字段）

在**不破坏 §3.1 现有必填/建议字段**的前提下，以下为**可选扩展**，实现时可按需加入统一表或单独扩展结构（API/DB 可兼容旧数据）。

| 扩展项 | 建议字段/位置 | 说明 | 优先级 |
|--------|----------------|------|--------|
| 活动预计时长 | attractions[].**duration_estimate**?（string，如 "2h"、"30min"）；dining[].**duration_estimate**? | 便于用户安排当日节奏 | P2 |
| 营业/开放时间 | attractions[].**open_hours**?；dining[].**open_hours**?；或并入 **notes** | 避免跑空；可文本描述 | P2 |

### 8.4 UI/UX 效果优化方案（均须符合 8.0 项目风格）

以下为**效果层**优化方案，与 §3.4 通用展示规范互补。**实现时须同时满足**：① 行业最佳实践（可扫性、无障碍、时间线/卡片等）；② **8.0 本项目风格约束**（**86** Experience/Business、**22** Tokens、**28** 叙事/组件、**25** 留白与动效、**13** 宪法）。优先保证**统一表+金额+图文**再逐步增强。

| 优化项 | 方案要点 | 本项目风格约束（8.0） | 落点 |
|--------|----------|------------------------|------|
| **时间线/卡片式展示** | 按日采用**时间线**或**卡片列表**：左侧/上方日期轴，右侧/下方当日内容；卡片内「图+标题+介绍+可选时长/开放时间/链接」；多日默认折叠「第 N 天 + 城市 + 概要」，点击展开详情 | **Landing/市场**：卡片用 22 Tokens、可轻玻璃（`backdrop-blur`）；**Escrow 内**：无玻璃、Trust 轴、与 EscrowDetail 一致。留白、单焦点（25） | §3.4、52-S3/S5 |
| **可扫性** | 折叠态或列表首行展示**关键信息**：日期、城市、当日总览句、**总价**（或「总价在费用区」）；避免用户必须展开多日才能看到总预算 | 文案与数字用 `text-ink-*`/`text-travel-*`；金额用 22 字体与状态色，不炫动效（13） | §3.4 补充；52-S3 验收 |
| **无障碍** | 所有配图 **alt**（景区/餐饮名称+简短描述）；金额/日期/地点**对比度**达标（22 体系已含）；行程列表与折叠按钮**键盘可聚焦、可操作**；焦点顺序符合阅读顺序 | 与 28 社区发布条/抽屉 a11y 一致；不引入额外装饰影响焦点（13） | §3.4、52-S5 a11y 检查项 |
| **预算可视化（可选）** | 在「分项+总价」表格基础上，可选**分项占比条形图或饼图**；总价超预算上限时**轻提示**（文案或边框色） | 图表仅用 22 颜色轴（Travel/Trust/状态色）；Escrow 内预算区保持银行级克制，无渐变/炫光（28） | P2；52-S8 扩展 |
| **地图与导航（可选）** | 若活动含 **lat/lng** 或 **map_link**：行程详情区「在地图上查看」入口或外链地图 | 入口按钮用 22 主色/圆角；不嵌入赛博风地图皮肤（8.0） | P2/后续 |
| **分享与导出（可选）** | 行程详情页「分享链接」「导出 PDF/图片」 | 按钮与文案符合 28 微徽章/CTA 风格，不抢主视觉 | 后续迭代 |
| **情景化（可选）** | 订单/Escrow 按「行前/行中」展示不同摘要 | Escrow 内始终银行级、无玻璃；仅信息结构切换（28） | 后续迭代 |
| **动效与节奏** | 展开/折叠、列表出现**统一动效**：200ms/600ms、25/28 缓动；避免突兀闪烁 | **严格按 28 §4、25、86 动效预算**：卡片 hover 1.02、reveal 600ms、badge 200ms；禁止数字跳动、霓虹、钱包特效 | **25、28、86**；52-S5 与现有 Landing/Market 一致 |
