## 二、性能预算（LCP / FID / CLS）

### 2.1 目标与测量

| 指标 | 含义 | 建议目标（与 09/业界一致） | 测量方式 |
|------|------|----------------------------|----------|
| **LCP** | Largest Contentful Paint | ≤ 2.5s（良好） | Lighthouse、Chrome DevTools、或 next/core-web-vitals |
| **FID** / **INP** | First Input Delay / Interaction to Next Paint | ≤ 100ms | Lighthouse、Web Vitals 库 |
| **CLS** | Cumulative Layout Shift | ≤ 0.1 | Lighthouse、layout-shift 监听 |

**测量命令**：先 `npm run dev`（或 `npm run build && npm run start`），再在 frontend 目录执行：  
- 本地查看报告：`npm run lighthouse`（产出 `.lighthouse-report.html`）  
- CI/无头：`npm run lighthouse:ci`（产出 `.lighthouse-root.json`）  
对 `/market`、`/escrow/[id]` 可将 URL 改为 `http://localhost:3012/market`、`http://localhost:3012/escrow/1` 复跑。`.lighthouse*` 已加入 .gitignore。

|---|--------|----------|

| ✓ | 关键路径（Landing、Market、Escrow Detail）至少一次 Lighthouse 或 Web Vitals 测量并记录 | 已提供 npm run lighthouse / lighthouse:ci；本地需先 npm run dev，再执行；CI 可先 start 再跑。本次自动化尝试因本机 dev 未就绪未获数值，流程已就绪。 |

## 四、SSOT 版本校验（/meta）

### 4.1 约定（04、05 §七点六）

| 项 | 约定 | 落点 |
|----|------|------|
| **GET /meta** | 后端返回版本与 SSOT 绑定、defaults 快照（REQUEST_BODY_LIMIT_BYTES、REQUEST_TIMEOUT_SECS 等） | 04 §三、§四 |
| **前端** | 启动时调用 GET /meta，供版本绑定与 fail-closed 校验 | MetaProvider、getMeta（apiClient） |
| **失败策略** | /meta 失败时前端可降级（仅提示或限制写操作），策略由产品定稿 | 05 §七点六 |

### 4.2 验收勾选表（/meta）

| □ | 验收项 | 完成标准 |
|---|--------|----------|
| ✓ | 前端有 GET /meta 调用（MetaProvider 或等价） | MetaProvider + getMeta（apiClient）已接入 |
| ✓ | /meta 返回结构与 04 约定一致（版本、defaults 快照等） | 后端 crates/api 已实现 /meta；与 04 一致 |
| ✓ | /meta 失败时有明确行为（日志/提示/降级） | MetaProvider 失败时仅设置 error 状态、不阻塞渲染；见组件注释与 38 执行记录 |

### 5.1 约定（04、14）
