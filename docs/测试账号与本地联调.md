## 一、如何启用测试账号

后端启动时，若环境变量 **`SEED_TEST_ACCOUNTS=1`**，会自动补全缺失的测试账号（按邮箱判断：若尚无 `tourist@test.com` 或 `guide@test.com` 则创建）。

- **配置**：在项目根或 `crates/api` 下 `.env` 中增加一行：`SEED_TEST_ACCOUNTS=1`。API 启动时会自动加载该 `.env`，无需再手动设置环境变量。
- **生效**：重启 API 后，控制台会输出：`seed: test accounts created — tourist tourist@test.com / guide guide@test.com (password: Test123!)`
- **说明**：见 [README 本地联调](README.md#本地联调旅行者--向导测试账号)、[.env.example](../.env.example) 中 `SEED_TEST_ACCOUNTS` 注释。

## 三、登录失败时请检查

若提示「邮箱或密码错误」或 `login_required`，请逐项确认：

1. **后端已设置并生效**：`.env` 中已添加 `SEED_TEST_ACCOUNTS=1`，且**已重启后端**（未重启不会注入账号）。
2. **密码一致**：密码为英文与符号，**区分大小写**，必须为 `Test123!`（T 大写、末尾为感叹号）。登录时后端会对邮箱和密码做首尾去空格，复制粘贴若多出空格也会按正确内容校验。
3. **测试账号按邮箱补全**：若库里已有其他用户但缺少 `tourist@test.com` 或 `guide@test.com`，重启后端时仍会补创建缺失的测试账号；若仍无法登录，可清空库后重启：`docker compose down -v`，再 `docker compose up -d`，然后重启 API。
4. **前端能访问后端**：前端默认请求 `http://localhost:8080`。请确认 API 监听在 **8080**（后端用 8080，前端用 3012，不要混用）。若用一键脚本 `scripts\start-api-with-seed.bat` 启动，脚本会强制 `PORT=8080`；若手动启动 API，请在 `.env` 中设为 `PORT=8080`；前端 `.env` 中可设置 `NEXT_PUBLIC_API_BASE_URL=http://localhost:8080` 与 API 一致。
5. **一键重启栈（默认不清库）**：在项目根执行 **`scripts\start-api-with-seed.bat`** 会结束已有 API/前端进程、拉起 Postgres、编译并启动 API（窗口内已设 **`SEED_TEST_ACCOUNTS=1`**）、同步 **`frontend/.env.local`**、再启动前端。**不会**默认清空数据库；需清库时请先用 **`scripts\prepare-local-manual-test.bat`** 加 **`-ResetDockerDb`**，或启动前设置环境变量 **`RESET_DOCKER_DB=1`** 再运行一键脚本。
6. **CORS 报错或接口 403/401**：修改后端 CORS 或 `.env` 后，**必须重新编译并重启 API** 才生效。在项目根执行：`cargo build -p traveltrust-api`，再运行 `scripts\start-api-with-seed.bat` 或手动 `cargo run -p traveltrust-api`。若 `.env` 中设置了 `CORS_ORIGINS`，请包含 `http://localhost:3012`（未设时后端默认允许 3012/3000）。
7. **登录页/页面打不开时**：多半是前端未启动或访问地址不对。按下面逐项检查：
   - **端口要对**：前端默认跑在 **3012**，请访问 **http://localhost:3012**（不要用 3000，除非你改过 `package.json` 里 `dev` 的 `-p`）。
   - **先检查前端端口（脚本名保留「3000」历史，实际检查 3012）**：运行 **`scripts\check-3000-and-start.bat`**。若 **3012** 未监听，脚本会启动前端；若已在监听，会提示直接打开登录页。
   - **方式 A**：运行 `scripts\check-3000-and-start.bat`（先检查端口，未监听则启动）或直接运行 `scripts\run-frontend.bat`（当前窗口启动前端）；
   - **方式 B**：在项目根打开终端，执行 `cd frontend`，再执行 `npm install`（首次），再执行 `npm run dev`。等出现 `Ready on http://localhost:3012` 后，在浏览器访问 **http://localhost:3012**（首页）或 **http://localhost:3012/auth/login**（登录页，地址里不要带问号）。
   - 若浏览器仍显示「无法访问此网站」或「连接被拒绝」：确认是否有 CMD 窗口标题为 **TravelTrust-Frontend**，且窗口内无报错；若窗口闪退，请在 `frontend` 目录下手动执行 `npm run dev` 查看报错信息（如 Node 版本需 18+、端口被占用等）。
   - 若页面白屏或报错：先执行 `cd frontend && npm run build`，确认能构建通过；再执行 **`npm run dev`**（整行复制；**勿**在 CMD 里只输入 `dev`，否则会提示 `'dev' is not recognized`），用 **http://localhost:3012** 打开。

## 五、数据库接库（阶段 41）

**用途**：按 [41-后端数据库接库与落地清单](spec/41-后端数据库接库与落地清单.md) 执行后端接库，使用户/向导/订单/评价/争议/行程/聊天等持久化到 PostgreSQL（或 CockroachDB）。

### 5.1 用 Docker 启动本地 PostgreSQL（推荐）

已安装 Docker Desktop 时，在**项目根目录**执行：

```bash
docker compose up -d
```

- 会启动容器 `traveltrust-postgres`，端口 5432，库名/用户/密码均为 `traveltrust`。
- 查看状态：`docker compose ps`；停止：`docker compose down`（数据在 volume `traveltrust_pgdata` 中保留）。
- 若 5432 已被占用，可改 `docker-compose.yml` 中 `ports` 如 `"5433:5432"`，并相应修改下面 DATABASE_URL 的端口。

### 5.2 配置 DATABASE_URL

- 在项目根或 `crates/api` 下 `.env` 中设置（与上面 Docker 默认一致）：
  - `DATABASE_URL=postgres://traveltrust:traveltrust@localhost:5432/traveltrust`
- 未设置时 API 使用内存 Store，重启后数据清空；设置后自动建池、执行迁移并从 DB 回填内存（hydrate）。

### 5.3 迁移执行

- **自动执行**：API 启动时若 `DATABASE_URL` 已设，会先连接数据库，再应用 **`crates/api/migrations/` 目录下全部 SQL 迁移**（当前仓库 **21** 支，含社区、governance、幂等等；以目录为准），无需单独运行 `sqlx migrate run`。
- **手动执行（可选）**：若需在未启动 API 的情况下先跑迁移，可在仓库根执行：
  - `cd crates/api && sqlx migrate run`（需已安装 sqlx-cli，且 `DATABASE_URL` 已配置）。

### 5.4 启动验证

1. 启动 API（例如 `cargo run -p traveltrust-api` 或按 README 方式）。
2. 控制台应出现：
   - `database: connected and migrations applied`
   - `database: hydrated N users, N sessions, ... N itineraries, N order_messages into chain_off`
3. 无数据库相关报错即表示接库与 hydrate 正常；重启 API 后数据仍从 DB 加载。

### 5.5 与测试账号的关系

- 接库后若同时设置 `SEED_TEST_ACCOUNTS=1`，种子仅在「当前无用户」时执行（先 hydrate，再判断是否为空）；若 DB 中已有用户，不会覆盖，测试账号不会重复创建。

## 八、常见错误：GET /api/v1/me 返回 404

**现象**：前端打开自由市场或自定义行程弹窗时，控制台出现 `GET http://localhost:8080/api/v1/me 404 (Not Found)`（或从 `me.ts` / `useItineraryForm` 发起的请求）。

**原因**：请求已发往 8080，但该路径未返回 200。常见情况：

1. **后端 API 未启动**：8080 上无进程监听，或由其他程序占用，对未知路径返回 404。
2. **后端未监听 8080**：例如 `.env` 中 `PORT=3001`，API 实际在 3001，而前端仍请求 8080，若 8080 上有别的服务则会 404。
3. **使用了旧的可执行文件**：修改过路由后未重新编译，运行的仍是旧二进制。

**排查与处理**：

| 步骤 | 操作 |
|------|------|
| 1 | **确认后端已启动**：在项目根执行 `cargo run -p traveltrust-api`，等待出现 `Listening on 0.0.0.0:8080`（或当前配置的 PORT）。 |
| 2 | **验证 8080 是否为当前 API**：浏览器或终端访问 `http://localhost:8080/health`，应返回 body `ok`。若无法访问或不是 `ok`，说明 8080 上不是本 API 或未启动。 |
| 3 | **再测 /api/v1/me**：访问 `http://localhost:8080/api/v1/me`（不带头时通常返回 **401**，属正常）；若为 **404**，说明路由未挂上，请执行下一步。 |
| 4 | **重新编译并启动**：在项目根执行 `cargo build -p traveltrust-api`，再 `cargo run -p traveltrust-api`，确保无编译错误；然后重复步骤 2、3。 |
| 5 | **端口与前端一致**：确认 `.env` 中 `PORT=8080`（或与前端 `NEXT_PUBLIC_API_BASE_URL` 的端口一致）；前端未设置时默认为 `http://localhost:8080`。 |

**说明**：未登录时 `/api/v1/me` 会返回 **401 Unauthorized**，前端会当作未登录处理（`getMe` 返回 null）；只有 **404** 才表示「路由不存在」，需按上表排查后端是否为本 API、是否已正确编译并监听 8080。

**临时绕过**：若暂时不启动后端、仅做前端开发，可在 `frontend/.env` 或 `frontend/.env.local` 中设置 `NEXT_PUBLIC_SKIP_ME_FETCH=1`，前端将不再请求 `GET /api/v1/me`（自定义行程弹窗内头像等将不预填）。去掉该变量并重启前端后即可恢复请求。
