# DApp 架构目录（中文命名 / 企业级审计就绪）

本文档是 TravelTrust **DApp 模式**（连接钱包、EIP-712 签名、链上写操作触发路径）的“目录化架构说明”。目标：清晰回答审计/评审的三个问题：

- DApp 在仓库里落在哪里（是否独立工程）
- 签名与门禁如何 fail-closed（避免错配版本/错链/错合约）
- 关键证据产物如何留存（/meta、manifest、请求追踪头）

> 权威正文：docs/06-DApp架构总览.md（业务与交互口径）、docs/05-前端总览.md。本文只做目录索引与控制点落地。

- 当前仓库无独立 dapp crate。
- DApp 模式属于同一前端工程 crates/web。

## 3. 目录树（Code Map）

```
crates/web/src/
  wallet.rs       # EIP-1193 + chainId + EIP-712 v4 签名
  meta_gate.rs    # /meta 版本绑定门禁（Release expected_* 必填）
  api/mod.rs      # signed intent 请求 DTO + 幂等/trace headers
  pages/mod.rs    # 写操作示例：签名 → 提交 intent（受门禁保护）
  lib.rs          # provider 变化监听（身份失效事件）

scripts/
  build-frontend-manifest.sh
  verify-frontend-deterministic-build.sh
```

## 4. 关键控制点（Controls）与最佳实践

### 4.1 /meta 版本绑定（必须 fail-closed）

- 启动必调 GET /meta。
- Release 必须写死：TRAVELTRUST_EXPECTED_API_VERSION、TRAVELTRUST_EXPECTED_SSOT_VERSION。
- 不兼容时禁止任何关键写操作（例如 dispute/confirm 等）。

### 4.2 EIP-712 domain 写死（链/合约/版本）

在 pages/mod.rs 的写操作示例里，签名前会强制要求：

- TRAVELTRUST_CHAIN_ID 存在
- TRAVELTRUST_VERIFYING_CONTRACT 存在
- SSOT version 用 build-time expected 值（不得依赖运行时 /meta）

目的：防止“同一个 UI 在不同链/不同合约/不同版本域”里签出不可控的 intent。

### 4.3 幂等与追踪（写操作必带）

- x-request-id：每个请求生成（用于审计串联）
- x-message-id：写请求生成（用于后续 outbox/链上串联）
- 幂等：同时带 Idempotency-Key 与 X-Idempotency-Key（同值）

### 4.4 身份失效事件（换号/切链）

lib.rs 监听 chainChanged/accountsChanged 并清理存储 + reload。

目的：避免用户切换身份/网络后仍以旧上下文继续写操作。

---

## 5. 关键数据流（Critical Flows）

1) 应用启动 → MetaGate 调 /meta → 校验 expected versions → 不通过则 fail-closed。
2) 用户连接钱包 → 读取 chainId/accounts。
3) 生成 typed data（以 06 的契约为准）→ 请求 eth_signTypedData_v4。
4) 将签名/typed_data 等以 signed intent 形式提交到后端（api/mod.rs 定义请求 DTO）。
5) 终态以链上/后端对账为准；前端仅展示 API 同源视图。

---

## 6. 证据与验收（Evidence & Acceptance）

建议每次发版或过 Gate 时，至少归档：

- 前端 manifest.json + manifest.sha256（可验证发布）
- /meta 输出快照（或 hash）
- 一次关键写操作的 request 追踪信息（x-request-id、idempotency-key）与后端日志串联
