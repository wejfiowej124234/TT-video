## 2. 范围与边界（Scope & Boundary）

### 2.1 真实代码入口（Important Fact）

- 后端真实入口不在仓库根 backend/（它目前是空目录位）。
- **后端服务入口**：crates/api/src/main.rs
- **领域模型（国模）入口**：crates/core/src/

### 2.2 In-scope / Out-of-scope

- In-scope：HTTP API、幂等/trace header、中间件门禁、/meta、SSOT 运行时复检与审计产物、（当前）文件型 outbox 抽象。
- Out-of-scope（需显式声明）：合约真实仓库（contracts/ 目前为目录位）、节点/RPC、基础设施部署形态（但必须能在 Runbook 与 evidence 中取证关键配置与变更）。

### 3.2 crates/api/src/main.rs 的“逻辑分区”（便于审计定位）

main.rs 虽是单文件，但内部包含清晰的控制点分区（审计常问的“证据落点”基本都在这里）：

- **路由与中间件栈**：CORS、超时、body limit、request-id、message-id、幂等层等。
- **幂等实现**：Idempotency-Key / X-Idempotency-Key 的读取、严格模式要求、响应回写、缓存复用。
- **trace 贯通**：x-request-id（请求带入或生成）、响应回写与最小日志打印。
- **/meta**：返回 api_version/ssot_version 与运行时默认配置快照（供前端/DApp 版本绑定与 evidence）。
- **SSOT 运行时复检**：读取 docs/08-3-参数与门禁表.md，生成 snapshot 与 JSONL 审计日志（Runbook §10）。
- **Pause/降级控制**：PAUSE allowlist（例如只允许 GET /health;GET /meta），避免故障期继续写。

## 4. 领域模型（国模）与模块化映射

### 4.1 国模（crates/core/src/types.rs）

当前最小领域模型包括：

- 用户：User、UserRole（Tourist/Guide/Arbitrator）、KycStatus（None/Pending/Verified）
- 导游：Guide、GuideStatus（Pending/Active/Suspended）、ServiceType（WalkingTour/CarTour/...）
- 订单：Order（含 state=OrderState）
- 争议：Dispute、DisputeStatus（Open/Assigned/Resolved）、DisputeResolution（refund_ratio、slash_guide）

### 4.2 订单托管状态机（crates/core/src/escrow.rs）

- OrderState：Created → Accepted → Escrowed → Completed
- 争议与裁决路径：Disputed → Refunded / PartiallyRefunded / Slashed
- 关键不变量：仅资金终态允许评价（is_final_financial_state）

### 4.3 建议的“最优模块化”边界（以不破坏现状为前提）

目前 API 入口集中在 main.rs。为了更清晰的模块化与可审计性，建议按以下边界逐步抽离（不要求一次做完）：

- api/http：router、handlers、DTO（与 docs/04 对齐）
- api/middleware：request-id、message-id、idempotency、timeout/body-limit、pause gate
- api/services：用例编排（应用层），只调用 core + infra；必须可观测、可取证
- api/infra：db/chain/indexer/outbox 的具体实现
- core：纯业务（无 I/O），只表达规则/状态机/类型

## 5. 关键控制点（Controls）与证据（Evidence）

### 5.1 版本绑定（/meta）

- 控制目标：防止前端/DApp 与后端/SSOT 漂移。
- 落点：GET /meta 返回 api_version + ssot_version + 运行时快照字段。
- 证据：发布 evidence bundle 中保存 /meta 输出（或 hash）。

### 5.2 幂等（Idempotency-Key / X-Idempotency-Key）

- 控制目标：弱网/重复点击不造成重复写入。
- 落点：写请求读取 Idempotency-Key 或 X-Idempotency-Key；严格模式可要求必填；响应回写 key；缓存复用。
- 验收点：同一路径同一 key 的 POST/PUT 重放应返回同一响应。

### 5.3 trace 贯通（x-request-id + x-message-id）

- 控制目标：一笔业务动作可从 API 请求追溯到后续事件（txHash/logIndex/outbox）。
- 落点：请求头带入或生成 x-request-id，并在响应回写。
- 证据：日志中以 x-request-id 串联（与 01 §9 口径一致）。

### 5.4 SSOT 运行时复检（Runbook §10）

- 控制目标：运行参数不漂移；漂移可检测、可审计、可回滚。
- 落点：启动/定时运行时复检，读 docs/08-3，写 runtime snapshot 与 JSONL 审计日志。
- 证据：data/ssot_runtime_audit.jsonl、data/runtime_params_last.json（路径可被 env 覆盖）。

## 6. 审计/发布检查清单（Checklist）

1) 入口清晰：后端入口=crates/api；backend/ 为空目录位。
2) 国模清晰：核心类型与状态机在 crates/core，且 core 不依赖 I/O。
3) /meta 可复核：发布证据中留存 /meta 输出；前端/DApp 版本绑定基于 /meta。
4) 幂等可验收：Idempotency-Key 与 X-Idempotency-Key 都兼容；严格模式要求在 /meta.strict_mode 中对外可见。
5) SSOT 可取证：部署前 preflight + 运行时 audit 都有证据产物路径。
