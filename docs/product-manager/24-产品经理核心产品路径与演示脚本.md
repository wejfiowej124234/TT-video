# 产品经理核心产品路径与演示脚本

## 这份文档是干什么的

这份文档是补给零基础产品经理的一块关键内容。

当前资料夹里，融资、治理、权限、合规、增长和一级市场都已经讲了很多，但还缺一份最基础也最实战的东西：

产品经理应该怎么把产品真正走一遍，怎么给别人演示，怎么用 5 到 10 分钟讲清 TravelTrust 不是一句空话，而是一个能跑起来的产品系统。

所以这份文档解决 3 个问题：

1. 产品最核心的路径到底是什么。
2. 产品经理第一次 demo 应该怎么讲。
3. 哪些页面是品牌页，哪些页面是产品页，哪些页面是信任与社区页。

## 先记住一个大原则

TravelTrust 不是只讲融资叙事，也不是只讲链上概念。

对零基础产品经理来说，最正确的理解方式是：

1. 先看品牌与项目定位。
2. 再看真实产品入口。
3. 再看交易与托管主链。
4. 再看信誉、社区和帮助入口。

不要一上来就讲治理币，也不要一上来就讲合约。

## 产品经理第一次 demo 的正确顺序

### 第 1 段：先讲这是什么项目

先打开：

- `http://localhost:3012/traveltrust`

这一段你要讲清楚的不是功能按钮，而是 4 件事：

1. TravelTrust 是什么。
2. 它不是一个单纯发币页。
3. 它为什么同时有旅游交易、托管、争议、信誉和治理。
4. 当前页面是品牌与承接页，不是认购页。

这一段讲不清，后面所有交易、社区、信誉页面都会显得像“堆功能”。

### 第 2 段：再讲真实产品入口

再打开：

- `http://localhost:3012/`
- `http://localhost:3012/market`

这一段要讲清楚：

1. 首页负责第一印象和入口承接。
2. `/market` 才是产品真实体验入口。
3. 项目不是只有介绍页，还有真实的撮合和订单链路。

产品经理这里不要只说“这是市场页”，而要说明：

- 这是用户真正进入撮合的地方。
- 这里体现的是供需匹配，不是单纯展示海报。
- 后续订单、托管、争议都从这里延伸出去。

### 第 3 段：再讲订单与托管主链

再讲：

- `/orders/new`
- `/orders`
- `/escrow/[id]`

这一段要让别人明白：

1. 用户不是只浏览内容，而是会进入订单流程。
2. 订单之后不是立即自由结算，而是进入托管与规则约束。
3. 托管、评分、争议、证据，才是 TravelTrust 和普通旅游平台真正拉开差距的地方。

产品经理要能用一句话讲清主链：

用户进入市场选择服务后，会形成订单，订单与托管状态联动，服务完成后再进入评分、确认或争议处理，而不是简单的一次性支付。

### 第 4 段：再讲信任与信誉机制

再打开：

- `http://localhost:3012/did-rank`

这一段要讲清楚：

1. 项目不是只靠平台说自己可信。
2. 它还有信任展示层和信誉结果层。
3. DID 排行榜是外部理解“信任机制”的一个很直观窗口。

### 第 5 段：治理控制台（按需插入，不要与订单主链混讲）

若听众关心「链上怎么改参数、金库、提案」：

- 打开 `http://localhost:3012/governance`（子路径见仓库 `frontend/app/governance/`）。
- 明确这是 **协议治理 / TTG 叙事域** 的产品入口，与 **`/orders`～`/escrow`** 订单托管主链是**不同故事线**；向导保证金侧用语见 **[81](../spec/81-经济模型-向导质押与订单押金.md)**、**[07-产品经理术语表](07-产品经理术语表.md)**。

### 第 6 段：最后讲社区与帮助承接

最后讲：

- `http://localhost:3012/community`
- `http://localhost:3012/help`

这一段要讲清楚：

1. 社区不是附属页，而是承接用户、内容和互动的长期阵地。
2. 帮助中心和反馈入口说明这个产品有持续运营面，而不是只有概念展示。
3. 如果后面要做外部社群，当前产品内社区和帮助页就是最直接的承接参考。

## 给零基础 PM 的 5 分钟演示脚本

你第一次 demo，可以直接按下面讲。

### 第 1 分钟

先讲一句话：

TravelTrust 是一个围绕旅游订单、链上托管、争议处理、信誉沉淀和社区承接建立起来的系统，不是单纯的发币或宣传页项目。

### 第 2 分钟

打开 `/traveltrust`，讲项目定位、价值主张和为什么它不是普通旅游平台，也不是普通 Web3 概念站。

### 第 3 分钟

打开 `/market`，讲真实产品入口，说明这里是撮合和订单体验的开始。

### 第 4 分钟

讲订单与托管主链：从下单到订单跟进，再到托管、评分或争议处理，这是项目的核心信任闭环。

### 第 5 分钟

打开 `/did-rank`、`/community`、`/help`（若时间允许再带过 `/governance` 与订单主链的**叙事分界**），讲信誉、社区、帮助和长期运营承接。

## 产品经理最容易讲错的 7 个点

1. 把 `/traveltrust` 讲成认购页或卖币页。
2. 只讲品牌叙事，不讲 `/market` 和订单托管主链。
3. 只讲链上，不讲社区、帮助、反馈和运营承接。
4. 把 DID 排行榜讲成单纯装饰页，而不是信任展示层。
5. 把帮助中心和 FAQ 当成次要页面，忽略它们对新用户和外部沟通的重要性。
6. 没分清“当前仓库里已存在的本地开发版”和“已经正式对外发布的外部入口”。
7. 把 **`/governance`** 的治理叙事与 **`IdentityStakingPool` 系** 向导**身份质押**混成同一个「质押」故事（分路径见 **[07-产品经理术语表](07-产品经理术语表.md)**）。

## 当前还缺什么产品经理该补

基于当前仓库，和“核心产品路径”直接相关的缺口主要还有这些：

1. 缺一份可直接对外使用的 One Pager。
2. 缺一份可直接投递的 Pitch Deck。
3. 缺一份正式 FAQ 成品，而不只是帮助中心入口。
4. 缺正式生产域名与公开发布链路。
5. 缺外部社媒账号与外部社群入口。
6. 缺一份把当前产品路径整理成“投资人 / 合作方 / 社区新人”三种版本的演示脚本。

## 三种对象的演示脚本

同一套产品路径，面对不同对象时，讲法必须不同。

### 投资人版

投资人版不要一上来讲页面细节，而要先讲问题、结构和为什么这不是一次性概念项目。

建议顺序：

1. 先打开 `/traveltrust`，讲 TravelTrust 在解决什么问题。
2. 再切到 `/market`，证明这不是只有品牌叙事，而是有真实产品入口。
3. 再讲 `/orders`、`/escrow/[id]`，说明交易不是一次性支付，而是进入托管、履约、评分和争议闭环。
4. 再打开 `/did-rank`，讲信任结果如何沉淀成可展示的信誉层。
5. 最后讲 `/community` 和 `/help`，说明项目具备长期用户承接和运营结构。

投资人版 3 分钟口径：

TravelTrust 不是单纯做旅游流量，也不是单纯做 Web3 叙事，而是在旅游交易里把下单、托管、履约、争议和信誉沉淀做成一个完整系统。当前仓库里已经能看到品牌承接页、真实市场入口、订单与托管链路、信誉展示页以及社区和帮助入口，所以它更像一套正在收敛成型的产品系统，而不是一页式概念项目。

### 合作方版

合作方最关心的是接入关系、履约可信度和合作后怎么承接用户。

建议顺序：

1. 先打开 `/market`，讲合作后用户在哪进入真实交易场景。
2. 再讲 `/orders/new`、`/orders` 和 `/escrow/[id]`，说明合作不是导流后失控，而是进入托管与规则约束。
3. 再讲 `/did-rank`，说明合作方如何看到信誉和服务表现沉淀。
4. 最后讲 `/community` 和 `/help`，说明合作后的内容、反馈和用户承接路径。

合作方版 3 分钟口径：

如果合作方接入 TravelTrust，用户不是被导向一个只会展示介绍的页面，而是会进入市场、订单、托管和信誉闭环。这样合作关系就不只是“带来流量”，而是带来一套可跟踪、可约束、可沉淀信用的交易与履约结构。

### 社区新人版

社区新人最怕一开始听不懂，所以要少讲术语，多讲“用户来到这里会看到什么”。

建议顺序：

1. 先打开 `/traveltrust`，用一句话解释项目是什么。
2. 再打开 `/market`，说明这是用户真实体验产品的入口。
3. 再简单带过订单与托管逻辑，强调平台不是付完钱就结束。
4. 再打开 `/did-rank`，说明平台会沉淀信誉，而不是只看宣传。
5. 最后讲 `/community` 和 `/help`，告诉新人出了问题去哪看、去哪问、去哪反馈。

社区新人版 3 分钟口径：

TravelTrust 可以先理解成一个把旅游交易、托管保障、争议处理、信誉积累和社区承接放在一起的产品。你可以先看项目介绍，再进入市场体验产品，再理解订单和托管为什么存在，最后通过信誉页、社区页和帮助中心知道这个项目怎么长期运行。

## 产品经理看完这份后，应该能做到什么

1. 知道先 demo 哪几页，不会乱跳。
2. 能把品牌页、产品页、信任页、社区页的职责分清楚。
3. 能在 5 到 10 分钟内把 TravelTrust 的核心路径讲明白。
4. 知道当前真实已实现的是什么，未实现或未公开的是什么。
