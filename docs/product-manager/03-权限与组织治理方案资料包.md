# 权限与组织治理方案资料包

## 这份资料包解决什么问题

用于支持产品经理制定后台权限、审批流、数据权限、财务角色、合规角色和企业级组织治理方案。

如果你以前只做过前台功能产品，这份文档最重要的价值是告诉你：企业级产品不是“谁能点按钮”这么简单，还要回答“谁能审批、谁能看到哪些数据、出了事谁负责”。

## 小白先看这个结论

1. 后台权限不是一个管理员账号就能解决。
2. 财务、风控、合规、客服、运营必须拆角色。
3. 能操作和能看数据是两套权限。
4. 高风险动作必须留审批和审计证据。

## 产品经理要建立的权限分层

### 1. 后台角色权限

白话理解：先定义“谁能做什么动作”。

[70](../spec/70-管理员系统开发文档.md) 已经给出企业级后台角色基线：

- SuperAdmin
- Ops
- CS
- Risk
- Finance
- Auditor

这层解决的是谁能看、谁能改、谁能审批、谁能导出。

### 2. 财务子角色

白话理解：财务不是一个筐，里面的人负责的事情完全不同。

[70](../spec/70-管理员系统开发文档.md) 和 [200](../spec/200-阶段财务对账结算与报表.md) 说明，财务不能只叫 Finance，至少要细分：

- FINANCE_VIEWER
- FINANCE_OPERATOR
- RECON_MANAGER
- SETTLEMENT_MANAGER
- FINANCE_AUDITOR

### 3. 数据权限

白话理解：即使两个人同属于财务，也不一定都能看全部数据。

[530](../spec/530-阶段数据权限隔离系统.md) 已明确，RBAC 还不够，还要叠加：

- scope
- resource_filter
- data_policy

也就是说，角色权限和数据范围必须拆开设计。

### 4. 合规权限

白话理解：涉及法律、监管、证据的事情，不能混在普通运营后台里处理。

[500](../spec/500-阶段法律与合规日志系统.md) 要求单独处理：

- 合规导出
- 数据请求
- 证据保全
- GDPR 或区域法规

这部分不能放进普通运营后台权限里随便处理。

## 企业级组织治理建议

产品经理可基于现有规范，设计一版组织治理矩阵：

1. 谁能发起
2. 谁能审批
3. 谁能执行
4. 谁能导出
5. 谁能审计

并且明确 `No Self-Approval`，也就是申请人与审批人不能是同一个人。

## 为什么这部分不能做简单版

因为这个项目不是普通内容后台，它涉及资金、争议、导出、审计、合规和高风险操作。如果权限没拆开，后面出问题时根本追不清是谁做的。

## 建议产品经理输出

1. 后台角色矩阵
2. 财务权限矩阵
3. 数据权限范围矩阵
4. 合规请求处理流程
5. 高危操作审批链

## 必须追问的决策问题

1. 资金类动作是否全部做到了 `RBAC + 审批 + 审计` 三门禁。
2. 数据导出、证据导出、财务导出是否都带审批号与审计编号。
3. 国家、城市、业务线、法域四种 scope 是否都需要做资源隔离。
4. 合规请求和普通审计日志是否已经拆成两套体系。
5. 高危写操作审计失败时，系统是否必须硬失败而不是继续执行。
