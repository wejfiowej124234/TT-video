# Pitch Deck 初稿（页序版）

## 使用说明

这是一版页序型初稿，目标不是把视觉稿一次做完，而是先把每一页该讲什么锁住，避免后续 Deck 东拼西凑。

当前版本适合先用于内部对齐、会前排练和视觉制作前的内容定稿。

## 与技术文档对齐（会前 / 外发前必对）

页序与口播定稿前须回链：**[08-4 对外口径包](../spec/08-4-对外口径包.md)**、**[01-总库总览](../spec/01-总库总览.md)**；按页涉及治理/分配时另对 **[82-治理币文档总览](../spec/82-治理币-文档总览.md)**、**[83-区域治理与收益分配白皮书](../spec/83-区域治理与收益分配-协议白皮书.md)**、**[84-第一阶段10国Country-Pool发行参数总表](../spec/84-第一阶段10国Country-Pool发行参数总表.md)**。若 Deck 含**技术架构 / 栈 / 数据库**页，须与 **[09-技术架构总览 v1.0](../spec/09-技术架构总览-v1.0.md)** 一致。链上与产品命名边界见 **[README 快照](README.md)**、**[07-产品经理术语表](07-产品经理术语表.md)**、**[14](../spec/14-合约-API-ABI-前后端对齐.md)**。对外演示 **[33 脱敏](33-上线验收与发布门禁清单.md)**。

## 第 1 页：封面

标题建议：TravelTrust

副标题建议：A trust-based travel transaction network

这一页只做三件事：

1. 给出项目名。
2. 给出一句英文副标题。
3. 明确这是一套产品系统，不是单点概念。

## 第 2 页：一句话讲清项目

建议文案：

TravelTrust 正在构建一套面向旅游交易的信任网络，把市场撮合、托管保障、争议处理、信誉沉淀和社区承接整合成同一套产品系统。

## 第 3 页：为什么这是真问题

这一页要讲清 4 个现实问题：

1. 交易双方信息不对称。
2. 履约缺乏可信约束。
3. 争议缺少清晰处理结构。
4. 信誉难以可验证沉淀。

## 第 4 页：我们的解法

用一页图或一条链讲清：

品牌承接页 -> 市场入口 -> 订单与托管 -> 评分或争议处理 -> 信誉沉淀 -> 社区与帮助承接

## 第 5 页：产品主链

这一页建议围绕以下已确认入口展开：

1. `/traveltrust`
2. `/market`
3. `/orders`、`/orders/new`
4. `/escrow/[id]`
5. `/did-rank`
6. `/community`
7. `/help`

## 第 6 页：和普通旅游平台的不同

要强调的不是“上链”三个字，而是：

1. 不只是撮合和支付。
2. 更强调托管、履约和争议约束。
3. 更强调信誉沉淀和长期信任结构。

## 第 7 页：和普通 Web3 项目的不同

这一页要讲清：

1. 不是从代币叙事反推产品。
2. 是从真实交易与履约问题反推信任系统。
3. 重点是产品闭环，不是单点概念包装。

## 第 8 页：当前已确认存在的核心入口

建议直接列出当前仓库里已确认的本地开发版入口，并标注“开发版可演示，不等同于正式生产域名”。

## 第 9 页：系统性优势

建议写 4 点：

1. 市场与交易入口存在。
2. 托管与争议结构存在。
3. 信誉展示层存在。
4. 社区与帮助承接面存在。

## 第 10 页：当前阶段

建议表达为：

项目已具备核心产品路径与内部单源文档基础，正在把这些能力进一步收敛成对外投递和合作沟通可直接使用的标准成品包。

## 第 11 页：Go-to-Market 与承接

这一页建议讲：

1. 对外成品包建设。
2. 平台账号矩阵与统一简介。
3. 社区与帮助入口承接。
4. 渠道投递与反馈闭环。

## 第 12 页：为什么是现在

建议讲法：

当旅游交易越来越需要可信履约、平台透明度和可验证信誉时，TravelTrust 把这些原本分散的环节重新整合进一套结构里，因此现在不是讲概念的窗口，而是把系统做成可理解、可演示、可合作形态的窗口。

## 第 13 页：当前需要的合作 / 关注 / 支持

建议按 3 类写：

1. 关注产品与交易信任结构的投资人。
2. 关注接入与履约协同的合作方。
3. 关注社区建设和增长承接的生态伙伴。

## Deck 制作红线

1. 不要把 `/traveltrust` 写成认购页。
2. 不要把开发版入口写成正式上线域名。
3. 不要把治理、收益、份额和股权概念混讲。
4. 不要为了好看删掉订单、托管和争议主链。
