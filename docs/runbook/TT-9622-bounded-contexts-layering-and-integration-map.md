## 0. 你现在的感觉通常意味着什么

| 现象 | 更可能的根因 | **不一定**意味着 |
|------|----------------|------------------|
| 后端路由很多、前端页面也有，但「串不起来」 | **竖切（vertical slice）** 未闭：API 有、DB/投影未接、或 **chain_off** 环境未齐，UI 仍用 mock/空态 | 整张 **[18](../spec/18-TravelTrust-全系统架构图.md)** 画错了 |
| 注册 / 市场 / 托管「各说各话」 | **呈现层（Next）** 与 **应用层（Axum handler）** 之间缺 **契约对齐**（**[04](../spec/04-后端与API.md)**、`frontend/lib/api.ts`）或 **同一概念两个名字**（如 discover vs market） | 要换成完全不同的架构风格（洋葱/六边形全盘重写） |

**结论：** 优先补 **「集成真相」**（一条用户路径上的：页面 → `apiUrl` → 04 路径 → DB/链 → 回显），再考虑 **是否改架构图**。图若改，应反映 **部署或主链数据流变化**，而不是「前端还没接」这种实现进度（进度用 **96-20** 矩阵 + **TT-9621** 即可）。

## 2. 推荐模型：「领域边界」×「技术分层」（适合本仓库）

**不要用一张「纯洋葱图」罩住 Next + 合约 + 索引器 + Admin。** 更合适的是 **双轴**：

### 2.1 横轴 — 领域边界（Bounded Context，产品「区域」不打架）

每个边界 **对内** 自有实体与用例；**对外** 只通过 **明确 API（04）** 或 **链上合约（14）** 协作。**同一概念只有一个「主拥有者」**。

| 领域（Context） | 主职责（一句话） | 后端聚合锚（代码） | 前端主目录（示意） |
|------------------|------------------|---------------------|---------------------|
| **Identity & Access** | 注册登录会话、角色 | `routes/auth`、`routes/me` | `app/auth/*`、`app/me/*` |
| **Marketplace & Orders** | 发现、下单、状态机 | `routes/discover`、`routes/orders`、`routes/itineraries` | `app/market/*`、`app/orders/*` |
| **Escrow & Settlement** | 托管展示、链同步、评分释放 | `routes/orders`（子路径）、`orderChainSyncStatus` 等 | `app/escrow/*` |
| **Community & UGC** | Feed、帖子、会话、好友 | `routes/community` | `app/community/*` |
| **Governance & Protocol RO** | 提案、费率路由、协议只读 | `routes/governance*` | `app/governance/*` |
| **Admin & Compliance** | 监管、对账、DSAR、开关 | `routes/admin` | `app/admin/*` |
| **Trust & Growth** | 外部信号 ingest（若启用） | `routes/trust_growth` | `app/admin/trust-growth` 等 |
| **Platform Meta** | 健康检查、构建信息、限流元数据 | `routes/health_meta` | 运维/开发态为主 |

**防打架规则：**  
- **订单状态、金额、链上字段** → **Marketplace + Escrow** 以 **04** 与 **53** 为 SSOT，**社区域不写订单真值**。  
- **消息**：**订单内消息** 与 **社区会话** 分属不同 **API 前缀**（见 **96-20** 备注），产品文案必须区分。  
- **治理只读 vs Admin 写**：Admin 变更配置须有 **角色 + 幂等**；治理页默认 **只读链上/投影**。

### 2.2 纵轴 — 技术分层（从浏览器到链，「洋葱」放哪一层）

```
[ 浏览器 ]
    │  Next.js：页面、组件、客户端状态、wagmi（仅 DApp 路径）
    ▼
[ 边缘 / 传输 ]  HTTPS · CORS · rewrites（next.config）· `apiUrl` 规则
    ▼
[ 应用服务 ]    traveltrust-api：Axum router → handler → 校验/编排
    ▼
[ 领域与持久化 ] chain_off / SQLx / 投影表 / 内部任务
    ▼
[ 基础设施 ]    PostgreSQL · RPC · 合约 · 索引器 · 外部 PSP/webhook
```

- **洋葱 / 六边形** 最适合落在 **`crates/api` 内部**（领域逻辑在内，DB 与链客户端为外侧适配器）。  
- **Next** 整体是 **适配器 + 呈现**：薄页面、厚 **`lib/apiClient` + hooks**；**不要**在 `page.tsx` 里藏第二条业务状态机，否则必与后端「对不上号」。

## 3. 「串在一起」的可操作定义（生产级最小标准）

对 **任意一条** 用户主路径（例如：注册 → 上架/发现 → 下单 → 托管视图 → 完成/争议），在 **② 测试网**（或 **①** 全链路 Docker）上同时满足：

1. **契约**：请求路径与响应形状符合 **04**（含错误码）。  
2. **数据**：关键读写在 **PostgreSQL**（或当前里程碑声明的库）可追溯，**非**仅内存。  
3. **链（若该路径声明须触链）**：`GET /meta` 与链 ID/合约配置一致，索引或 chain_off 策略与 **55/110** 对读。  
4. **前端**：该路径下 **无长期 mock**；**loading / error / empty** 与真实错误码映射（**96-13 / 96-16 D4**）。

满足以上四条，再在 **96-20** 把对应行 **对齐** 从「待核验」改为「已验证 + 日期」。
