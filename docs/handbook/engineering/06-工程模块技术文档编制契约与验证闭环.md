## §1 文档定位（强制）

| 维度 | 要求 |
|------|------|
| **读者** | 程序员 / 工程师（开发、调试、维护） |
| **类型** | **Explanation**（为何如此）+ **How-to**（如何改、如何验）；**不是** Diátaxis 意义上的 **Tutorial**（手把手第一课） |
| **必须支撑** | 理解模块、修改代码、运行验证、按日志与状态排错 |
| **明确不是** | 产品说明书、博客体、营销叙事、**仅**索引式「详见 spec」而无机制说明 |

与 **[手册 00 · §2.4](../00-手册总览与编制规范.md#hb-00-diataxis)** 对齐：入门 **Tutorial** 留在 **`learn/`** 与 **[README](../../../README.md)**；**Reference 表体** 不迁入 handbook。

## §2 数据来源与清洗（强制）

| 规则 | 说明 |
|------|------|
| **spec 默认可能过时** | 从 spec 抽取时须对照 **当前代码** 与 **门禁脚本**；历史实现描述须删除或标明「已弃用 / 仅考古」 |
| **保留** | 跨版本稳定的**规则、边界、真源链接** |
| **禁止** | **整段复制** spec 原文；**复制表格**（尤其 **[04](../../spec/04-后端与API.md)** 契约表、**[93](../../spec/93-全站功能验证矩阵-域别回归清单.md)** 矩阵表体） |
| **允许** | 用**自己的话**概括机制 + **外链**到 spec 锚点与仓库路径 |

<a id="eng-06-cross-verify"></a>

### §2a 旧 spec 继承门禁（强制加硬）

下列**缺一不得**把 spec 中的字段名、状态迁移、HTTP 组合或「已实现」叙述写进 **handbook 域篇**：

| 门禁 | 最低动作 |
|------|----------|
| **04** | 涉及公共 API 的，在 **[04 §3.4](../../spec/04-后端与API.md)** 或散文窗可找到**同义**路径/码；计划变更先改 **04** |
| **93** | 涉及域验收的，在 **[93](../../spec/93-全站功能验证矩阵-域别回归清单.md)** 有对应用例族或已登记 **N/A**（见 **[02](./02-生产级文档约束与合入门禁.md)**） |
| **代码** | `rg` / 阅读 **`crates/`** 当前实现，确认符号与分支**仍存在** |
| **测试** | 至少一条 **`cargo test -p …`** 或 **`scripts/`** 与所写机制**同向**（或显式写「无自动化，仅手动：…」并经 Owner 接受） |

**禁止默认继承**：spec 中的**旧实现、旧字段、旧流程**视为**可疑**，除非已通过上表交叉确认；否则只能标「考古 / 已弃用」或**不写**。

<a id="eng-06-body-outline"></a>

## §3 单篇强制正文结构（九节 + 分层）

每一篇 **`engineering/NN-*.md`**（能力域模块文，含未来 **10～** 区段）**建议**采用下列章节顺序，便于评审与读者跳读。章节名可因域微调，但**职责须覆盖**下列信息：**标题形态**可用 **`§n`** 或数字节名（如 **50** 之 **1.～9.**），**须能映射**到下表 **L1～L9** 职责，**禁止**借编号风格新增与九节无关的「第十套契约语义」。

| 层级 | 章节（逻辑名） | 必须回答的问题 |
|------|----------------|----------------|
| **L1** | **1. 模块职责** | 解决什么问题；在系统中的角色 |
| **L2** | **2. 核心机制** | 流程 / 状态 / 交互如何工作；**为何这样设计**（取舍与不变量） |
| **L2～L3** | **3. 数据与状态模型**（若适用） | 关键状态、字段、转换关系；**须引用** **[spec/01-总库总览](../../spec/01-总库总览.md)** 或 **[spec/93](../../spec/93-全站功能验证矩阵-域别回归清单.md)** 的**锚点**，不抄表 |
| **L2** | **4. 系统关系（强制）** | 与 **04（API）**、**93（规则矩阵）**、**routes / scripts / test** 等真源的关系：谁定义、谁校验、谁实现 |
| **L2** | **5. 工程使用方式** | 如何接入 / 调用 / 修改；**模块与路径**（源码目录、入口函数、配置键名） |
| **L2** | **6. 工程验证（强制）** | **至少一条**可执行路径：`cargo test …`、`bash scripts/…`、指定 E2E / CI job、或「改路由必跑 **`run-check-04-routes`**」类**显式**规则 |
| **L3** | **7. 调试与排错（强制）** | 常见失败征象；日志键、DB 状态、相关 **93** 用例族或脚本名 |
| **L3** | **8. 边界与限制** | 系统**不**负责什么；已知约束（性能、一致性、环境闸） |
| **L1** | **9. 参考（强制）** | **仅** spec / runbook / 脚本锚点列表；**不**在参考节再造契约 |

**复杂度**：**L1** 先建立心智；**L2** 讲机制与闭环；**L3** 放边界与异常。**禁止**开篇堆细节、无层级跳写。

**粒度**：**一篇 = 一个清晰能力域**；禁止单篇跨多域硬揉；也避免碎到无法单独闭环验证。

<a id="eng-06-closure"></a>

## §5 工程闭环（验收「一篇文是否合格」）

工程师**只读本篇与链出的真源**须能完成下表四项，否则该文档**不合格**：

| 能力 | 最低证据 |
|------|----------|
| **理解模块** | L1～L2 能回答「谁驱动、谁消费、关键不变量」 |
| **修改代码** | §5 给出稳定路径与入口符号；与 **04 / routes** 无矛盾 |
| **运行验证** | §6 至少一条**当前仓库真实存在**的命令或脚本 |
| **排查问题** | §7 给出从现象到日志/状态/数据的缩小路径 |

与 **[手册 00 · §2.5 T1～T3](../00-手册总览与编制规范.md#hb-00-eng-quality)** 同向。

## §6 生命周期与文首元数据（强制）

除 **[手册 00 · §2.2](../00-手册总览与编制规范.md#hb-00-naming)** 规定的 **Version / 最后更新 / 受众 / 状态 / 与 spec 关系** 外，**模块域文**建议在文首或 §1 前用一行或表声明：

| 字段 | 取值 | 与现有文首对齐 |
|------|------|----------------|
| **状态（对外标签）** | `draft` · `active` · `deprecated` | 与 **`状态：`** 行映射：**草案** / **现行** / **弃用** |
| **与 spec 覆盖关系** | `none` · `partial` · `full` | **none**：几乎纯仓库操作说明；**partial**：解释+多外链；**full**：深度导读但仍**不**抄表 |
| **来源** | `spec/XX-…` 等 | 标**主**叙事来源，便于迁移后删 spec 时追溯 **[98 §2](../../spec/98-以代码为真源的文档体系与旧文档替代路线图.md)** |

**CI 文首**：仍以 **`bash scripts/check-handbook-frontmatter.sh`** 为准；须含 **`与 spec 关系`** 字面（见 **`scripts/gates/check-handbook-frontmatter.py`**）。

<a id="eng-06-compat"></a>

## §7 变更与兼容性（强制）

若文档描述的行为相对上一版有**语义变化**，正文须显式写明：

- 是否 **breaking**（对调用方 / 数据 / 配置）  
- 是否影响既有流程或运维习惯  
- 是否需要**迁移**（脚本、DDL、特性开关）

**未说明**时，评审默认按「**不得引入未文档化的行为变更**」处理；**真源变更**仍须走 **04 / 93 / 14 / 代码与脚本** 合入流程，见 **[02 · §2](./02-生产级文档约束与合入门禁.md)**。

## §8 术语与一致性（强制）

- 状态名、模块名、执行器、订单等**核心对象**须与 **spec/01（总库总览）、04、93** 及代码 **identifier** 一致。  
- **禁止**同义反复命名（同一概念多个「外号」）。  
- 若业界词与仓库词并存，**首次**出现时用括号对齐到仓库真名。

<a id="eng-06-evolution"></a>

## §9 可扩展性（强制）

写法上优先 **「规则 + 模式」**（不变量、扩展点、挂载约定），避免把流程写死成**唯一**线性故事，以便：

- 新增状态或事件时，只需补 **转换** 与 **真源**，不重写一篇小说  
- 新域插入时，重复用本篇 **§3** 骨架，号段遵守 **[手册 00 · §5.1](../00-手册总览与编制规范.md#hb-00-number-blocks)**

<a id="eng-06-antipatterns"></a>

## §10 反模式（禁止）

| 反模式 | 处理 |
|--------|------|
| 「系统大致是……」无边界、无可验证入口 | 退回补 §1～§6 |
| 堆砌「未来 / 可能 / 计划」且无量化 Owner 与真源 | 删除或移到 **spec** 规划文，handbook 只写**已落地**或可脚本化的**闸** |
| 索引式正文（仅罗列「见 spec xx」） | 必须补 **机制**（§2）与 **验证**（§6） |
| 复制 **04 / 93** 表体 | 一律改外链 + 概括 |
| 只写现象不写**因果链**与**责任边界** | 补 §2、§8 |

## §12 合并前清单（首篇业务域文 / 任一 `engineering/10+`）

PR reviewer 对 **NN≥10** 域篇建议逐项勾：

- [ ] **spec 来源**：文首 **来源** 或 **与 spec 关系** 可指到具体 **spec/XX**（不得「整个 spec」模糊带过）  
- [ ] **验证命令**：§6 至少一条**仓库内真实**命令或明确 CI job；默认含 **`check-handbook-frontmatter`** 当次 PR 改了 **`docs/handbook`** 对应文件时  
- [ ] **无表体复制**：全文无 **04 §3.4**、**93** 矩阵**整表/整行拷贝**（允许代码块内**短** JSON 示例，须标注示例性质）  
- [ ] **可独立阅读**：L1～L2 不依赖读者「已背下 spec」
